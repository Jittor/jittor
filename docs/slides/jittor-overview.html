01 框架是什么

七个元算子，组合出整个算子库

别的框架为每个算子写一个 kernel；计图只定义七个元算子，其余算子由它们复合而成，再由编译器针对实际形状融合、生成代码。

reindex按索引表达式重排 / 取值，卷积、池化、切片的底座
reindex_reduce重排的同时归约，反向传播的对偶形式
broadcast_to把低维张量展开到目标形状，零拷贝的存储视图
unary一元逐元素
binary二元逐元素
ternary三元选择
reduce沿轴归约
= 全部算子卷积、注意力、归一化…… 都是这七个的复合

为什么这样设计：算子数量固定，融合规则就只需要面对七种节点，编译器能把一整段复合表达式合成一个 kernel，而不是逐个调用预编译好的库函数。src/ops/ 下确实只有这七个算子文件。

01 框架是什么

一条单向流水线：从调用到 kernel

框架 API
jittor.* · torch.* · nn / autograd / optim / cuda
↓ 下沉：拼写与语义适配
统一计算图
原生 Var / Op 图 — 唯一 IR，惰性执行
↓ 图融合 + JIT 代码生成
后端 kernel
CPU · CUDA · ACL（昇腾）· ROCm · Corex（天数）

惰性执行

  • Python 侧只构图，读取 / 同步 / 显式提交时才调度
  • 因此融合器看得到整段表达式，而不是一次一个算子

按负载编译

  • kernel 针对实际形状生成并缓存，不走通用模板
  • 算子注册表按后端一行 kernel，新后端只补这一列

02 近期更新 — 性能

收益来自哪里

小模型、小 batch 的瓶颈不在算力，而在宿主提交路径：设备早就算完了，在等 Python 把下一个算子递过来。

宿主侧

  • per-thread stream　每算子宿主地板 7.89 → 4.31 µs
  • CUDA Graph 回放　整步宿主成本收成一次 2.24 µs 的 launch
  • 自动 flush 按工作量　不再按算子个数切分批次
  • 优化器批处理　不再按参数一个一个来

kernel 侧

  • rank≥5 的 permute　内层（连续那层）原本串行，warp 内一次都不合并：152 → 404 GB/s
  • cuBLASLt 走 Linear　bias 融进 GEMM epilogue，少一个 kernel、少一个算子
  • 混合 dtype 矩阵乘　按 autocast 精度解析，不再物化 [B,out,in] 临时量

也有测出来没用的：四项 per-op 记账优化（记录瘦身、去锁、标记存储视图、缓存调用点）预估 0.2–0.4 ms，同进程 A/B/A 实测 0.000–0.002 ms，全部回退。

03 Torch 兼容层

一套计算图，多个前端

把 import torch 指向计图，让按 PyTorch 写的代码不改一行跑起来。支撑它的不是第二套张量库。

兼容层做什么

  • 把 torch.* 的拼写与签名翻译成图上的节点
  • 补齐 torch 的语义约定：dtype 提升、autocast、视图与就地写、设备归属
  • 覆盖 nn / autograd / optim / cuda / library / distributed / FSDP2

兼容层不做什么

  • 不建立第二张图——IR 只有原生 Var/Op 一份
  • 不复制数学实现——kernel 仍由框架统一生成
  • 能力缺失时明确报错，而不是静默给出可疑结果

好处是直接的：所有图融合、JIT、多后端的收益，torch 前端自动继承；反过来，兼容层发现的语义缺陷修在框架里，原生前端同样受益。

04 正确性

这一轮修掉的语义缺陷

会静默出错的

  • 视图静默冻结　x.view(-1)、flatten()、widening expand 的视图停在旧数据上，并永久失去写回——无报错无告警
  • split 读错元素　非连续输入上按存储线性读，jt.split(x[:,1:], 2) 取到错误的行
  • 广播梯度形状错　+= -= *= /= 与 scatter(reduce=) 的值侧返回切片形状

会直接崩的

  • AdamW(fused=True) 在 CUDA 上崩溃　判据用了 use_acl，而它是 use_cuda 的别名，把 CUDA 送进只有 NPU 实现的算子
  • 分配器尺寸不匹配　申请按存储跨度、归还按元素数，exact-fit 分配器上会发出偏小的块
  • Tensor.set_ 必抛异常　nbytes 是属性却被当方法调用

共同点：这些都不是"跑不起来"，而是"跑起来了但结果不对"或"只在特定配置下炸"。tests/mem 的分配器契约测试从 12 失败变为全绿，正是靠把这类问题当成缺陷而不是既存现象。

04 测量纪律

三条靠踩坑换来的规矩

1 · profiler 的百分比不可兑现

  • py-spy 报某项占 8.24%，真 A/B 只有 0.9%
  • 另一项报 7.3%，实测是两倍
  • 只用它提候选，动手前必须 A/B 验证

2 · 孤立微基准同样不可兑现

  • 循环里测 v.tape() 是 1.1 µs
  • 往真实步骤插 228 个，只值 0.006 ms

3 · 跨构建比较在共享机器上不成立

  • 同一个 torch 二进制、同一脚本，相隔 20 分钟中位数差 9%
  • 某个 case 的比值 spread 达 0.488–2.268（4.6 倍）
  • 只认同进程 A/B/A 与交替配对的中位数

代价

  • 并行跑测试会改变文件间顺序，已实测让失败数从 2 变 1
  • 把"稳定的失败"变成"时有时无"，比慢更难查

04 现状

已经到哪，还差什么

已经成立

  • 十二项对比赢 6 平 5 输 1，对最好的 torch.compile 模式赢 5 平 3 输 4
  • 真实多模态模型经 vLLM-Omni 端到端跑通且速度正常
  • 性能改动全部为通用路径，模型代码零修改

还没收口

  • 卷积算法选择不稳定　同一份代码跨进程有 2.1 倍波动，cuDNN 在被占满的卡上实测一次就定终身
  • 兼容层测试跑不起来　108 个文件因包导入路径被 pytest 收集失败，日常流程里基本是死的
  • 单测启动开销　每进程 6.9 s 的 import，695 个文件串行约 80 分钟
