## 现在有什么

两个入口，都是"捕获一次、之后重放"，区别在于被捕获的东西会不会更新状态：

| 入口 | 捕获什么 | 实现 |
| --- | --- | --- |
| `jt.graph_replay(module, *example_inputs)` | 一次**推理**调用：模块是输入与参数的函数，调用结束什么都不留下 | [`python/jittor/_runtime/graph_replay.py`](https://github.com/Jittor/jittor/blob/2.0-refactor/python/jittor/_runtime/graph_replay.py) |
| `jt.capture_step(fn)` | 一整步**训练**：前向、反向、优化器更新，连同它改写的参数、动量与归一化统计量 | [`python/jittor/_runtime/step_capture.py`](https://github.com/Jittor/jittor/blob/2.0-refactor/python/jittor/_runtime/step_capture.py) |

Torch 前端把 `torch.compile(..., mode="reduce-overhead")` 接到这两者上：包模块走推理
重放，包函数走整步捕获。

`jt.capture_step` 的捕获与重放调用返回的是从录下的整步里拷出的值，与本次输入、
与步内参数之间没有 autograd 边；反向应在步函数内部完成。只要输入或步内参数要求梯度
（且不在 `jt.no_grad()` 下），步外的求导（`jt.grad`、优化器的 `step(loss)`）只要会经这些
返回值流进步内，就明确报错，而不是丢掉这一部分梯度——目标另有普通路径时也一样，如
`step(x) + x.sum()`；第一次（eager）调用的返回值照常可导。不流进步内的求导不受影响：
目标是步内没读的量、目标就是返回值本身，或经过 `stop_grad` 的返回值。不要求梯度时返回值
就是常量，可以照常喂给下游可训练模块。

此外有一条**默认开启**的自动策略（`JT_AUTO_GRAPH_REPLAY=1`）：它只看
`no_grad` 下、最外层的模块调用，只在相同形状连续出现两次之后介入，只接受 Var 输入
合计小于 `auto_graph_replay_bytes`（默认 4 MB）的调用，并且只在工作集不超过
`auto_graph_replay_retain_bytes`（默认 256 MB）时录成设备图。**输入大小是"重放省下的
建图"与"多出来的输入输出拷贝"之间的廉价判据**：实测 1 MB 输入的 mlp 0.14 -> 0.05 ms、
batch 1 的 ResNet-50（0.6 MB）5.9 -> 0.7 ms、SD1.5 一个去噪步（0.3 MB）42 -> 20 ms 都
值得进，8 MB 输入、设备受限的 mlp（0.49 -> 0.52 ms）不值得。其余一切照常执行。

录图上限约束的是**每份设备录图的额外工作集**，不是进程总显存；权重、其它模块或其它
签名的缓存不在这个单份预算里；私有输入和返回值固定缓冲也会增加实际常驻开销。
`0` 表示不限制，显式 `jt.graph_replay` 也不受自动预算
约束。通过 `jt.flag_scope(auto_graph_replay_retain_bytes=...)` 调整预算时，下次符合自动
策略的 `no_grad` 调用会释放该模块已有的普通捕获和带状态对象的捕获，再按新预算重捕；
离开 scope 后再次调用也按恢复的预算重捕。超预算只拒绝设备录图，仍可通过执行器重放并使用其内存回收机制；离开 `no_grad`
的调用继续构建可求导的普通前向。

## 护栏：捕获什么时候作废、什么时候根本不许

一张捕获的图是**一组形状、一组参数、一条 Python 路径的照片**，它自己看不出这些变了。
因此每次调用都检查，不再成立就丢弃重捕，而不是拿旧答案应付：

- 参数的形状、dtype、个数；
- 模块是不是还在同一个 training 模式；
- 有没有参数被重新绑定（优化器更新、load、设备迁移）——图读的是它捕获的那些参数 Var，
  更新会把它们换掉，否则就会**悄悄用旧权重回答**；
- 捕获的图是不是还没被 finish。**这条最要紧**：一张 finish 过的图不会报错，它会一直用
  上次算出来的值回答。

要求精确随机流的自动回放拒绝随机抽样。显式 CUDA 训练步捕获为支持的随机操作
（包括 dropout）使用每次更新的 Philox seed 与 counter，保证每次回放重新抽样，
但不保证随机流与 eager 相同。不支持的随机操作会阻止设备录图。捕获中把值读回主机
也会阻止回放，因为随后的 Python 路径可能依赖这些值。训练步捕获还要求 Python 侧的账目自己申报——
`live_array()`（每次重放前重填的小数组，如融合 AdamW 的 step 与学习率）、
`on_replay()`（每次重放前跑的钩子）、`guard()`（读数变了就重捕）、`refuse()`（直说这步
不能重放）。设备录图在每次发射前还要核对叶子有没有迁移（`graph_leaves_moved`）。

`replay.stats` / `step.stats` 报告到底发生了什么——重放了几次、退回了几次、为什么退回。
`jt.profile` 的 `prof.replay` 读同一组计数（见[性能与显存画像](../../performance/profiling.md)）。
**静默退回比不重放更坏**，所以这些计数是结论的一部分，不是可选的调试信息。


多份训练步捕获可以共享参数和优化器状态，但保留图由各自捕获拥有：新写入需要等待当前
尚未执行的读者，不能顺带调度旧捕获的训练步。捕获结束时，尚未完成的 detach 输出或
更新后读数直接使用已经执行的保留值，不能再次执行优化器。这些临时执行边界不修改
图的生命周期或 finished 标志。

拒绝捕获时，只提交该步显式输出与状态根尚未执行的计算；已经执行的保留值作为
边界，随后按普通执行完成其生命周期。该批次不通过弱同步引入旁支消费者，
也不在解除保留标记后重新执行已经完成的原地更新。

待计算的无梯度快照在物理写入前提交，并在设备录图开始前完成；快照复制不属于
后续设备图。快照的复制节点也不作为待执行优化器的额外控制输入，以免捕获阶段
在更新参数后重新计算本应返回的更新前梯度。

普通推理回放不能记录对已物化存储的原地写入；例如窗口掩码的索引写入不能只在捕获时执行，
随后回放其初始化而丢失屏蔽值。这类写入在预热阶段设置捕获护栏，避免再次执行
带副作用的前向。训练步捕获仍使用其状态写入记录机制。
尚未分配存储的临时张量更新仍可构成函数式保留图。

同一函数、同一设备的多种形状录图复用一个私有临时内存池。执行器重放先为该池预热，
之后各张设备图只保留地址约束，共享顺序执行时可复用的中间缓冲和工作区；参数、
持久状态、输入迁移与复制返回值使用普通分配器。池在跨线程或流使用时建立执行依赖，
最后一个拥有者和设备图释放后回收空闲设备段；仍活跃的张量保留其存储。可观察的
返回值在池之外复制，后续回放不会改写此前返回的结果。

对于少量固定 batch 形状，每个签名保留一份步函数。反向、优化器更新和梯度清理放在
步函数内部，指标、文件写入和纯主机调度放在外部；需要观察的梯度快照作为显式输出返回。
Adam 同组尚未暴露的整数计步共享回放增量；暴露或改写计数器时实化其值，保留外部
Tensor 与 NumPy 别名的权威性。回放还检查组内步数是否一致；不一致时按普通更新执行，
不能用一个共享步数计算所有参数的偏差修正。序列化保存实际计步，不保存共享增量关系。
编译模式测速必须注明模式，将预热／捕获成本和回放计数与普通 eager 结果分别报告。

训练步也可重放封闭、显式放置在 CPU 的普通张量前缀，经显式 H2D 边界连接到设备图。
前缀计算和传输在每次调用中重新执行，并计入整步耗时；不缓存输入相关的标量或 mask。
opaque code、主机随机数和未证明的设备依赖仍阻止录图。准入预算额外计入前缀的保留
字节上界。每次前缀执行后复核边界地址；地址迁移会先释放旧录图，再通过执行器执行
这一训练步，避免使用旧地址或把优化器更新执行两次。`_graph_has_host_prefix` 和
`_graph_host_prefix_bytes` 可用于核对是否实际采用此路径，不能将预算上界当作实测峰值。

显式训练步捕获还可将普通、只读设备表达式产生的 `where`／`nonzero` 索引作为前缀。
每步都在设备录图之外重新计算索引，并将选中数量读回主机；索引内容和数量均保持动态。
预检查在优化器／随机数 prologue hook 推进之前核对边界形状与地址；数量不兼容时，先
丢弃旧 IR，再恰好执行一次 eager 训练步。若后续 replay hook 再次改变边界，则在训练图
发射前报错，避免重试造成计数推进两次。opaque、随机或修改状态的依赖仍不准入。
推理重放不启用这一动态前缀契约。

同一形状 guard 也覆盖执行器预热、关闭设备录图和录图超预算时的 IR 回放；原生根引用
不额外创建 Python Tensor holder。不能证明准入的动态条件在算子构造时便切回普通
执行，使优化器更新尚未作为 kept 操作执行；不能等更新完成后再拒绝并重复执行它。

CUDA 融合 Adam／AdamW 从小型设备头读取实时步数、学习率、found-inf、betas、衰减和
epsilon，调度器改变这些值不再强制重新捕获。不具备该能力的后端继续使用原有 guard；
耦合 Adam 的权重衰减改变计算路径，仍需使旧捕获失效。

训练步内部的 DDP buffer 广播必须保留为图依赖。分组 NCCL 的结果记录为状态写入，
完整训练步通过捕获准入后再提交到原存储；只在 tracing 时执行物理拷贝，会导致之后的
重放省略广播。已有别名和各 rank 的本地 BatchNorm 统计仍须保持原有语义。

捕获可采用不同于 eager 的执行策略：中等规模 FP32 Linear 可以使用计时选定的
cuBLASLt GEMM，因为 Function 建图开销只支付一次。对于头数较多的短序列 FP32
训练 attention，在分数矩阵有明确大小上限时使用矩阵计算路径，避免分块反向的重算；
长序列继续使用节省显存的内核。这些选择保持 dtype、TF32 设置和 dropout 语义，
但会改变临时存储和首次编译开销，因此数值、显存与稳态速度需要一起验证。

## 测量协议与历史结果

同一个 decode 步，eager 与重放在**各自独立的进程**里测、每次换输入、每个答案都和 eager
对过：

| tf-d512-L8 decode b1s1 | 耗时 |
| --- | --- |
| eager | 2.54–2.67 ms |
| 重放 | 1.57–1.79 ms |
| 参考 PyTorch | 1.37–1.43 ms |

约 1.5x，跨运行可复现；差距关掉了大部分，但没有关完。其它形状**没有**列进来，因为在
这台机器上测不稳：b8s256 前向在两个相差约 2x 的状态之间跳（14.06 ms 或 6.49 ms），
eager 一侧也一样，prefill 同理。**量你自己的模型。**

避免以下两种测量错误：

- **把捕获的那个 Var 再喂回去等于什么都没测。** 输入就是捕获的 Var 时重放跳过输入拷贝，
  没有新输入写进去，图根本不重新执行——调用退化成把它已经持有的输出拷一份，而且答案
  还是对的。b8s256 这样"重放"出 6.8 ms 对 eager 的 14.0 ms。
- **在一个进程里测两臂测的是顺序。** 后跑的那一臂从热状态开始：让两臂跑完全相同的
  eager 代码（拒绝重放），第二次测出 1.57 ms，第一次 2.74 ms。

**重放不是白拿的钱。** 运行时本来就重叠得好的图重放会更慢——一个 mlp 前向 eager
0.33 ms、重放 0.42 ms，一个卷积栈持平。`measure=True` 可以在捕获时自动 A/B 一次、
输了就永久拒绝，但它**默认关闭**：这次测量扰动它所测的进程，让之后每次重放发射 219 个
kernel 而不是 132 个，包装器因此慢 30%——比它要保护的那点边际更大。

## 不要从哪里开始

- **不要从"把前端做薄"开始**。天花板量过：前端只占建图的 25%，全拿掉也不够。
- **不要用 `Op::duplicate()` 做回放**。它在 `Op` 基类里返回 `nullptr`，
  全树只有 `BroadcastToOp` 和 `ReindexOp` 两个实现了，不是通用原语。
- **不要指望减少节点数**。省一个 broadcast 节点值整步的 2%。
- **不要事后撤销 finish**。`finish_pending_liveness()` 开头就是
  `if (is_finished()) return;`，清掉标志会让它**第二次释放同一批输入的 pending
  liveness**，引用计数下溢、随后 use-after-free。保图是**第一次执行就不 finish**
  （`keep_graph`），不是执行完再撤销。

## 为什么是这条

对真 PyTorch 的十二项对位里，规律是**设备受限的赢、主机受限的输**：卷积 0.66/0.85、
b8s256 训练 0.51 都赢；decode（batch 1 seq 1）输 1.97，d1024 decode 输 2.05。
主机受限那几条的成因量过五遍，结论一致：

1. **阶段拆解**：decode 一步 2.70 ms 里，Python 建图约 1.6 ms，发射核函数
   0.54 ms，规划只有 0.12 ms。
2. **逐算子设备时间**（两边同法量：把上百次同一算子排进队列不中途同步再除）：
   gemm 1.00x、transpose 0.99x、elementwise 1.07x——设备侧不是问题。
3. **节点数**：省掉一个 broadcast 节点只值整步的 2%，节点数不是杠杆。
4. **前端天花板**：把 `nn.Module` / functional 整层拿掉，一个 block 从
   202.1 降到 151.4 us——前端只占建图的 25%。
5. **地板**：即使前端为零，decode 也要 1.21（建图）+ 1.0（执行器）= 2.2 ms，
   对 torch 的 1.37 仍然是 1.6x。

所以剩下的全部在「每一步都用 Python 重新构造同一张图」这件事本身。`ExecPlan` 早就是
一个可以留着的值（`src/core/exec_plan.h`：规划只读图并写 batch 编号，不分配、不发射），
缺的是**让图在执行之后活下去、能换输入、并且在不再成立时拒绝回放**。
