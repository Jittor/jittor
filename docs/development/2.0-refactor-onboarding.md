# 2.0 重构开发导览

[开发与维护](index.md) · [English](2.0-refactor-onboarding.en.md)

这份导览帮助开发者沿着调用链找到源码与验证入口。仓库规则以根目录的 `AGENTS.md` 为准；准备环境时先看[贡献指南](contributing.md)。

## 从问题找到源码

| 问题域 | 规范目录与职责 |
| --- | --- |
| 张量、Module 与运行时组合 | `python/jittor/_core/`、`_runtime/`；维护对象、图和公开命名空间 |
| 运算、梯度与神经网络 | `python/jittor/ops/`、`autograd/`、`nn/`、`optim/`；描述计算和训练更新 |
| 编译与执行 | `python/jittor/build/`、`src/`、`backends/`；生成、编译和执行目标设备算子 |
| Torch 风格 API | `compat/torch/`、`compat/shim/`；处理 API 语义、安装事务和 shim 部署 |
| 分布式训练 | `python/jittor/distributed/` 与兼容层；处理通信、参数分片和状态保存 |
| 验证与可复用工具 | `tests/`、`compat/tests/`、`tools/`、`benchmarks/` |

一般调用链是 Python 接口构图，再由运行时调度原生算子和设备 kernel。表面上的 Python API 问题可能来自 dtype、存储别名、设备位置或执行器状态，定位时需要沿着这条链检查。

具体源码归属见[源码架构](source-architecture.md)，目录和打包边界见[仓库布局](repository-layout.md)。下游专属实现与测试在 `JittorEcosystem` 的独立仓库维护，入口见根 README；主仓不放置 `adapters/`。

## 修改与验证

先用最小复现明确行为，再确定修复属于原生核心、Torch 兼容层还是独立 adapter。兼容层设计见[兼容原则](compatibility/principles.md)与[前端对象边界](compatibility/frontend-boundaries.md)；算子实现见[JIT 算子源码](runtime/jit-operator-source.md)和[存储与别名](runtime/storage-layout.md)。

原生模式和 Torch 模式使用独立进程。首次编译串行执行，并为并行任务分配独立缓存。验证按[测试体系](testing/test-system.md)选择范围，修改后先运行 core 层，再运行受影响功能和实际设备的定向测试：

```bash
python tools/run_test_suite.py --tier core
bash tools/check_repo_layout.sh
JITTOR_TORCH_SHIM=1 PYTHONPATH=python python -m pytest -q tests/structure
```

CPU 结果只证明 CPU 范围。加速后端支持需要真实设备执行、数值与梯度检查以及 fallback 检查；性能结论另外遵循[性能协议](../performance/benchmarking.md)。报告应说明源码身份、配置、设备和验证边界，不能用导入成功代替计算验收。

## 保存资料与协作

可复用机制说明按主题写入 `docs/`，中英文页面成对维护。任务、缺陷与阶段性验证结果写入 GitHub issue/PR；没有发布授权时只保留本地记录。历史材料通过固定提交引用，缓存、原始日志、模型、独立实验和工作树留在仓库外的 `$JITTOR_LAB_ROOT`。具体路径规则以 `AGENTS.md` 为准。

提交前检查差异，只暂存本次任务文件，使用简明英文提交信息。推送和创建 PR 遵循用户授权。
