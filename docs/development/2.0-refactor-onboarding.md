# Jittor 项目开发者导览

本文面向第一次参与 Jittor 开发的贡献者，帮助读者在较短时间内建立对项目的整体认识。文档关注 Jittor 如何组成、主要模块分别解决什么问题、一次修改通常如何推进，以及遇到问题时应该去哪里查资料。

本文不替代 API 参考、算子实现说明、设备使用指南和具体验证报告。阅读本文之后，读者应当能够判断一个问题大致属于哪个模块，找到相应的源码和验证入口，并按照项目约定开始一次修改。

## 一、Jittor 是什么

Jittor 是一个面向深度学习的高性能框架。它提供 Python 动态图接口，用于表达张量计算、神经网络和训练流程；同时通过 C++、CUDA 以及其他后端在实际设备上执行计算。Jittor 的一个核心特点是即时编译（JIT）和元算子：用户在 Python 中组合操作，框架根据实际计算和设备生成、编译并缓存底层代码。

因此，Jittor 不是一组只在 Python 层调用现成 kernel 的接口。它包含从 Python API、计算图和自动微分，到运行时、编译器、设备管理、后端 kernel 和分布式通信的完整链路。修改其中一层时，通常需要同时考虑它与上下游边界的关系。

### 一次计算大致如何发生

可以用下面的流程理解 Jittor 的执行模型：

```text
用户 Python 代码
    ↓
Jittor 张量、Module 和自动微分接口
    ↓
计算图与运行时状态
    ↓
算子注册、元算子展开和即时编译
    ↓
C++ / CUDA / 其他后端实现
    ↓
目标设备执行与编译缓存复用
```

这条链路带来几个新人需要尽早掌握的事实：

- 第一次 `import jittor` 可能会初始化运行时并编译核心组件。
- 第一次使用某个算子或某种编译配置时，可能会继续触发 JIT 编译。
- 编译缓存是运行模型的一部分，而不是可以随意提交到仓库的临时文件。
- CPU 路径成功不能自动证明 CUDA、ROCm 或 NPU 路径可用；目标后端需要在真实设备上验证。
- 读取 `.numpy()`、`.item()` 或其他需要结果的接口可能会等待尚未完成的设备计算。

### 原生能力、兼容层和下游适配

Jittor 的代码大体可以分为三类能力。原生能力定义框架本身的张量、自动微分、神经网络、运行时和后端行为；兼容层让 Torch 风格代码、Triton、FSDP2 等已有接口能够接入 Jittor；下游适配则处理 Transformers、Diffusers、PEFT、MMCV/MMEngine、verl、vLLM 等具体生态库的调用方式。

这三类能力有不同的归属。原生能力应进入框架核心或对应的原生包，通用的 Torch 风格适配进入 `jittor.compat.torch`，项目专用的接口转换进入相应 adapter。这样可以避免为了支持一个下游项目而把专用逻辑放进核心框架，也可以让兼容层建立在稳定的原生能力之上。

## 二、项目的大体框架

从整体上看，Jittor 可以分为 Python 接口层、运行时与编译层、原生核心与后端层，以及测试、文档和工具层：

```text
Python 接口层
├── 核心张量与运行时
├── 神经网络与自动微分
├── 原生数学和数据结构能力
└── Torch / Triton / 分布式兼容层
          ↓
运行时与编译层
├── JIT 编译和代码生成
├── 图执行与自动微分支持
├── 设备和运行时状态
└── 编译缓存与诊断
          ↓
原生实现层
├── C++ 核心
├── CUDA / ROCm / ACL 等后端
├── 通信和分布式支持
└── 外部库与扩展接口
```

仓库顶层目录可以按下面的方式理解：

| 目录 | 主要职责 |
| --- | --- |
| `python/` | Jittor Python 包、公开 API、运行时和编译入口 |
| `src/` | 共享 C++ 核心、执行器、自动微分基础设施和运行时实现 |
| `backends/` | CUDA、通信以及其他设备后端的源码和资源 |
| `compat/` | 跨框架兼容项目和公共适配实现 |
| `tests/` | 核心行为、兼容性、设备和结构测试 |
| `examples/` | 示例程序和教程配套代码 |
| `docs/` | 长期维护的用户与开发者文档 |
| `refactor-wip/` | 当前整改阶段的架构、研究、测试和验证材料 |
| `tools/` | 测试入口、结构检查、构建和维护脚本 |
| `benchmarks/` | 性能基准和比较协议 |
| `adapters/` | 部分下游生态的具体适配入口 |

这些目录的生命周期和用途不同。长期有效的说明应放在 `docs/`，整改阶段的架构和验证材料放在 `refactor-wip/`，实验缓存、原始日志和大体积产物放在仓库外的实验目录中。

### Python 接口层

Python 层负责提供用户和上层生态使用的抽象，包括张量、`Module`、神经网络层、优化器、自动微分、FFT、线性代数、概率分布和稀疏能力。它同时负责参数检查、公开名称组合、计算图描述，以及和下层运行时的连接。

Python 层并不意味着计算在 Python 中完成。对于一个普通算子，Python 代码通常只描述计算和参数，真正的执行仍会进入运行时、JIT 编译器和目标后端。

### 运行时与编译层

运行时与编译层负责把 Python 层表达的计算变成实际设备上的执行，包括运行时初始化、设备选择、计算图执行、自动微分支撑、算子注册、代码生成、C++/CUDA 扩展编译、缓存和诊断。

这一层也是理解许多“看起来像 API 问题”的关键。有些行为表面上来自 Python 属性，实际受启动配置、设备状态、编译策略或缓存命中情况影响。修改这部分代码时，应区分启动级配置、运行时开关、算子局部编译选项和只读诊断信息。

### 原生核心与后端层

原生核心和后端层负责真正执行计算。`src/` 中的 C++ 代码提供共享的执行器、运行时状态、自动微分和生命周期管理；`backends/` 中的代码负责 CUDA、通信库和其他设备路径；各类 kernel、模板和注册逻辑则把抽象运算落到具体硬件。

后端改动必须关注实际设备行为。能导入 Python 包、能构造一个对象或能在 CPU 上得到结果，都不能替代目标设备执行、设备与 CPU 对拍以及 fallback 检查。

### 兼容和生态层

兼容层连接 Jittor 与已有的 Torch 风格代码及下游项目。它处理 API 名称、参数语义、模块状态、序列化、分布式行为和设备路径之间的差异。下游适配则进一步处理特定项目的模型、训练流程或服务接口。

遇到生态兼容问题时，先判断问题属于哪一层：是 Jittor 原生计算能力缺失，是 Torch 风格 API 的语义适配问题，还是某个下游项目的调用方式尚未接入。这个判断决定了修改应放在核心、`jittor.compat.torch` 还是 adapter 中。

## 三、主要模块分别在解决什么问题

下面按问题域介绍主要模块。这里的目标是帮助新人建立方向感，而不是列出所有函数和类。

### 1. 核心张量与运行时

`python/jittor/_core/` 是原生 Python 核心接口的主要归属，负责张量、`Module`、函数式自动微分上下文、钩子、flags 和诊断等基础能力。`python/jittor/_runtime/` 管理命名空间组合、安装顺序、运行时状态和历史别名。

`python/jittor/build/` 负责编译器、代码生成和扩展构建；`python/jittor/serialization/` 负责原生模型和参数的保存、加载及安全序列化。C++ 侧的执行器、设备状态、遍历和生命周期管理主要位于 `src/runtime/`。

这一组模块解决的是“框架如何启动、如何组织状态、如何把 Python 世界连接到原生执行”的问题。

### 2. 张量运算与数学能力

`python/jittor/ops/` 负责张量、索引、形状、拼接和归约等基础运算，是许多上层模块共同依赖的运算层。`autograd/` 提供函数式自动微分，`fft/` 提供可导的频域运算，`linalg/` 负责分解、求解、范数和矩阵计算，`distributions/` 负责概率分布，`init/` 负责参数初始化，`sparse/` 负责稀疏张量和稀疏神经网络能力。

这些模块共同解决的是“如何表达、组合并对各种数值计算求导”的问题。修改这里的行为时，通常需要考虑广播、dtype、形状、梯度、设备和序列化等多个维度。

### 3. 神经网络与训练能力

`python/jittor/nn/modules/` 保存有状态的网络层和模型组件，`python/jittor/nn/functional/` 保存无状态的神经网络运算，`nn/backends/` 提供对可选后端能力的调用适配，`optim/` 提供优化器和训练更新，`distributed/` 提供分布式启动、通信和 rendezvous 辅助，`contrib/` 提供贡献算法和较高层的组合工具。

一个典型的训练过程可以理解为：

```text
数据 → nn.Module → 基础张量运算 → 自动微分 → optimizer
                         ↓
                  后端执行与同步
```

因此，新增一个网络层往往不只涉及一个 Python 文件，还可能涉及基础算子、梯度、设备 kernel、状态保存和训练轨迹测试。

### 4. 兼容层和下游适配

`compat/torch/` 是 Torch 风格 API 的规范源码目录，以 `jittor.compat.torch` 导入，负责名称、参数和行为层面的适配。`compat/shim/` 管理 Torch shim 的运行时与部署，`compat/triton/` 负责 Triton API 或相关计算路径的桥接，`compat/fsdp2/` 负责 FSDP2 相关的分布式语义。

`adapters/` 和相关兼容代码面向具体生态库。它们通常需要同时验证导入、前向、反向、状态兼容、设备执行和下游训练或推理流程。下游适配应遵循 `downstream-library-adaptation` skill 中的分流和设备验证流程。

### 5. 后端和设备支持

Jittor 的设备支持可以按能力域理解：CPU 提供基础执行和容易复现问题的参考路径；CUDA 提供 GPU kernel、融合算子、设备内存和通信；ROCm 提供 AMD GPU 路径；Ascend/NPU 通过 ACL/CANN 等组件连接设备；MPI、NCCL、HCCL 等组件支持分布式通信。

不同后端不一定拥有完全相同的算子覆盖和性能特征。后端开发通常需要完成真实设备执行、CPU/设备数值对拍、梯度验证、fallback 检查和必要的性能协议，而不是只让 Python 接口“看起来可用”。

### 6. 测试与性能验证

Jittor 的测试不是单一的 pytest 命令，而是按风险分层的验证体系：单元测试验证局部行为，兼容测试验证与 Torch 或下游项目的语义一致性，设备测试验证真实后端执行，训练轨迹测试验证多步状态变化，性能测试验证固定协议下的速度和资源使用，结构门禁验证目录、包和源码边界没有被破坏。

测试通过的范围必须与结论一致。CPU 通过不代表加速后端通过，单步前向通过不代表训练状态和梯度轨迹通过，导入成功也不代表没有 CPU fallback。

## 四、如何在项目中协作

### 开始工作前

开始一个任务时，先确认当前分支、提交和工作区状态，再阅读与任务相关的架构、环境和已知问题文档。对于整改中的任务，应查看 `refactor-wip/architecture/refactor-board.md`，必要时继续阅读同目录下的交接和分工文档。

在修改代码前先写一个最小复现或最小验证。这样可以区分真实缺陷、环境问题和已有行为，也能帮助确定需要覆盖的设备和测试范围。

### 修改代码时

项目遵循“先验证，再修复”的工作方式。找到问题后，应先定位规范实现和现有兼容别名，再在正确的归属域中修改。不要通过第二份实现、宽泛异常捕获或隐式 CPU fallback 来掩盖边界问题。

公共行为变化需要定向回归测试。涉及共享语义时，应扩大到 CPU 和相关加速后端。新增计算必须在声明支持的真实 device 上执行；仅有导入成功或 CPU 结果不足以证明后端支持。

Jittor 使用 JIT 编译缓存和文件锁。首次编译应串行完成；并行任务使用不同的 `JITTOR_HOME` 或 `cache_name`；unittest 和 benchmark 不要共享同一编译缓存。实验目录、缓存、模型和原始日志应放在 `$JITTOR_LAB_ROOT` 下，不要放入主仓库。

### 验证和提交时

一个常见的修改流程是：

```text
最小复现
  → 定向测试
  → CPU 回归
  → 目标设备验证
  → 相关生态或性能门禁
  → 结构检查
  → 只提交当前任务文件
```

提交前应运行与变更相关的检查，至少确认仓库布局和结构测试通过。只暂存当前任务涉及的文件，不使用 `git add -A`。提交信息使用简明中文。除非有明确要求，不要主动 push 或修改远端分支。

### 协作资料和任务状态

`refactor-board.md` 是整改任务的唯一状态源；`refactor-handoff.md` 记录接手和交接信息；`refactor-dispatch.md` 记录任务分工；`agent/manuals/known-issues.md` 管理仍然活跃的问题；`refactor-wip/results/` 保存带有提交、环境、命令和验证范围的可复现结论。

不要在多个文档中复制同一份项目状态，也不要在 `agent/` 下另建看板或结果树。稳定的开发说明放在 `docs/`，整改期材料放在 `refactor-wip/`，过期信息应删除或归档。

### 可复用的 skill

Skill 是面向特定工作类型的可复用操作说明和工具集合。当前与 Jittor 开发最直接相关的 skill 包括：

- **`jittor-dev-context`**：开始 Jittor 开发任务时，定位项目上下文、环境规则、架构文档、已知问题和验证入口。
- **`downstream-library-adaptation`**：接入或验证 Transformers、Diffusers、PEFT、MMCV/MMEngine、verl 等下游库时，判断问题属于 Jittor 核心、`jittor.compat.torch` 还是 adapter，并按设备阶梯执行验收。

其中，`jittor-dev-context` 是大多数 Jittor 开发任务的入口；涉及下游生态时，应优先使用 `downstream-library-adaptation`，不要在其流程之外直接新增 adapter。

## 六、按任务进入项目

最后可以用下面的索引快速选择阅读入口：

| 我想做什么 | 建议先看 |
| --- | --- |
| 修改基础张量算子或梯度 | `python/jittor/ops/`、`autograd/`、对应后端和测试体系 |
| 增加一个网络层或训练能力 | `nn/modules/`、`nn/functional/`、`optim/`、训练测试 |
| 增加或修复 Torch API | `compat.torch`、Torch 兼容原则、对拍测试 |
| 接入一个下游生态库 | `downstream-library-adaptation`、`adapters/`、设备门禁 |
| 修改 JIT 或编译流程 | `python/jittor/build/`、`src/`、JIT 算子说明 |
| 修改 CUDA、ROCm 或 NPU 行为 | `backends/`、设备指南、真实设备验证报告 |
| 处理构建、缓存或运行时问题 | `environment.md`、`storage-layout.md`、调试文档 |
| 记录一项验证结论 | `refactor-wip/results/` 及其报告模板 |

Jittor 的代码量较大，但新人不需要一开始读完整个仓库。先从问题域确定模块，再沿着“Python 接口 → 运行时 → 原生实现 → 测试验证”的链路阅读，通常比从某个函数一路追进去更容易建立正确的整体认识。
