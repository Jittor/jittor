# 2.0 refactor developer overview

[Development](index.en.md) · [中文](2.0-refactor-onboarding.md)

This overview helps contributors follow a call from its public API to the implementation and validation entry points. The root `AGENTS.md` owns repository rules. Start with the [contribution guide](contributing.en.md) to prepare an environment.

## Find the source owner

| Area | Canonical directories and responsibilities |
| --- | --- |
| Tensors, Module and runtime composition | `python/jittor/_core/`, `_runtime/`; objects, graphs and public namespaces |
| Operations, differentiation and neural networks | `python/jittor/ops/`, `autograd/`, `nn/`, `optim/`; computations and training updates |
| Compilation and execution | `python/jittor/build/`, `src/`, `backends/`; generation, compilation and device execution |
| Torch-style APIs | `compat/torch/`, `compat/shim/`; API semantics, installation transactions and shim deployment |
| Distributed training | `python/jittor/distributed/` and compatibility owners; communication, sharding and checkpoint state |
| Validation and reusable tools | `tests/`, `compat/tests/`, `tools/`, `benchmarks/` |

A Python interface usually builds a graph, and the runtime dispatches native operations and device kernels. An apparent Python API failure may originate in dtype, storage aliases, placement or executor state. Trace those owners along the call chain.

See [source architecture](source-architecture.en.md) for ownership and [repository layout](repository-layout.en.md) for packaging boundaries. Downstream-specific implementations and tests live in separate `JittorEcosystem` repositories linked from the root README; the main repository does not contain `adapters/`.

## Change and validate behavior

Establish a minimal reproducer, then decide whether the fix belongs to native Jittor, the Torch frontend or a separate adapter. Read the [compatibility principles](compatibility/principles.en.md) and [frontend boundaries](compatibility/frontend-boundaries.en.md) for frontend work, or [JIT operator sources](runtime/jit-operator-source.en.md) and [storage and aliases](runtime/storage-layout.en.md) for operation work.

Native and Torch modes run in separate processes. Serialize the first compilation and allocate separate caches to parallel tasks. Select tests using the [test system](testing/test-system.en.md): start with the core tier, then exercise affected features and actual devices.

```bash
python tools/run_test_suite.py --tier core
bash tools/check_repo_layout.sh
JITTOR_TORCH_SHIM=1 PYTHONPATH=python python -m pytest -q tests/structure
```

CPU results establish CPU behavior. Accelerator support requires actual device execution, value and gradient checks, and fallback checks. Performance claims also follow the [benchmark protocol](../performance/benchmarking.en.md). Evidence must identify sources, configuration, device and scope; importing a package does not validate computation.

## Keep records and collaborate

Maintain reusable explanations by topic under `docs/`, with paired Chinese and English pages. Track tasks, defects and staged validation in GitHub issues/PRs; retain local records when publication is not authorized. Reference historical material through fixed commits. Keep caches, raw logs, models, independent experiments and worktrees outside the checkout under `$JITTOR_LAB_ROOT`, following the root `AGENTS.md` rules.

Review the diff before committing, stage only task files, and use a concise English commit message. Pushes and PR creation require the user's authorization.
