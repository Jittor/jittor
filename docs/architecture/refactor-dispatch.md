# 怎么派活给接手的模型

2026-09-08 更新。配套 [交接说明](refactor-handoff.md)与
[当前布局交接](../../agent/manuals/layout-handoff-4.15.md)。

当前用户优先级是先完成架构迁移，形成多人开发的稳定底座；性能调优后移。
按完整依赖批次实现、集中验证和整合，不再逐小改提交、逐小改跑整套测试。

> **2026-09-03 状态：第 1 节的 WIP/残留收尾已经完成。** 五个远端 `wip/*` 已验证合入并删除，相关
> worktree 全部干净；不要再执行第 1 节，直接按最新交接说明第 6 节开始下一波。

上一轮是被额度打断的，不是做完的。这份说明只解决两件事：**让下一轮在任何时刻被打断都不亏**，
以及**让你用尽量少的话把状态交代清楚**——状态都在文档里，你不需要复述。

下文 `$LAB` 指 `$JITTOR_LAB_ROOT/refactor`。

## 0. 一句话的 goal

要它自己一直推到底，用这句：

```
在 2.0-refactor 分支上干活（工作目录 $LAB/coord，不要在主树里改代码），按
当前布局交接与 docs/architecture/refactor-plan.md 推进架构迁移。先稳定
Runtime/Backend、存储、dtype、独立Torch和目录边界，再处理性能与剩余功能。
最多 root 加三个 subagent；隔离互相冲突的工作树，按完整架构批次整合和验证。
更新看板与接口交接，区分实现就绪、待合入、待验收、部分实现和未实现。
最终按原需求逐条证明完成，不以提交数或改表格状态作为完成。
```

任务表用于跟踪，不代替验收。统计只读任务行，并包含 `5.02b`、`5.02c` 等派生编号；
总项和子项存在重叠依赖，不能用条目数推导工时或完成百分比。历史波次文字不参与统计。

分支与工作目录必须写进 goal，理由见交接说明第 0 节。

## 1. 第一次会话的结果（2026-09-03 已完成）

五个 WIP 已验证合入并删除，工作树残留已收尾，14 个相关 worktree 已审计为干净，看板的旧活动态已

## 2. 之后每一波：给量，不给「剩下的」

```
读 docs/architecture/refactor-handoff.md、refactor-plan.md、refactor-board.md 和 $LAB/AGENT-BRIEF.md。

这一波最多 root + 3 个 subagent，按当前架构依赖和真实剩余实现面分区。
已就绪的改动先整合，不扩大同时悬而未决的跨层接口。

- 按完整依赖批次实现和提交，集中做必要验证，不用小提交数量代替进度。
- 每个 agent 只用派给它的那张卡与那段核，缓存目录各用各的。
- 收工前把看板改对。
```

每批按实际代码重新确认分区，不能照抄历史分区名。隔离树完成只表示可以整合，
合入时必须保留主树同期接口变化；不要用整文件取一侧解决跨层冲突。

## 3. 随时可以发的一句：干净地停

```
先停下来收尾：能推的都推了，看板改对，交接文档更新到反映现在的状态，然后告诉我停在哪。
```

这句不需要上下文，额度告急时直接发。上一轮如果每次中断前都发过这句，就不会有十一处残留
需要靠翻 `git status` 复原。

## 4. 验收问什么

**不要问「做完了吗」**——答案永远是做完了。问有确切答案、能对照的：

- 看板上现在几行已合并、几行进行中？进行中的分别在谁手里？
- 几处未提交残留？在哪几个 worktree？
- 这一波的提交号列出来，哪几个跑过 CUDA？

再抽查一条修「静默算错」的任务：

```
<编号> 你说合并了。把那个提交里新增的测试名字告诉我，以及它在修复前是怎么失败的。
```

答不出「修前怎么失败」，说明那条没有真测试——计划第 0 节要求的是修前失败、修后通过。

## 5. 会让它跑偏的话

| 别说 | 为什么 | 改成 |
| --- | --- | --- |
| 「把剩下的都做了」 | 百余条任务会让它开一大堆 subagent，中断时残留满地 | 给分区与条数 |
| 「顺便把 X 也改了」 | 未协调的跨层修改会覆盖并行工作 | 明确依赖与 owner 后纳入同一完整批次 |
| 「这个测试红了，修一下」 | 分支起点本来就有已知失败（看板顶部有清单），它会去修一个本来就坏的东西 | 先问：这条在分支起点是否也红 |
| 「用 git stash 存一下」 | stash 栈是所有 worktree 共用的，这轮两个 agent 的 WIP 整包对调过 | 保留隔离树和可审查的 diff，不丢弃工作区文件 |
| 「force push 一下」 | 分支上有九个来源的提交，覆盖掉就找不回来了 | rebase 再推 |

## 6. 出了错怎么让它自查

```
<描述现象>。先不要改代码：告诉我这个现象在 <某个已知好的提交> 上是否也出现。
不出现的话，用 git bisect 定位到具体提交再说。
```

这轮所有「大面积失败」最后都不是大面积——一次是损坏的 JIT 缓存，一次是磁盘满，一次是
Python 字符串里内嵌的 C++ 没跟着改。先分清是回归还是环境，再动代码。

## 7. 每一波结束时看一眼

有没有三个以上 agent 各自重新查明了同一件事？有就说明漏了一个 skill。
计划第 0 节要求这类知识当场写进 `agent/skills/`，与产生它的任务同一个提交——攒到最后就写不出来了。
