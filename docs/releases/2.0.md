# Jittor 2.0 Migration Notes

## Breaking Changes

### Private Torch runtime aliases have been removed

`jittor._torch_leaf_params`, `_torch_retained`, `_torch_tensor_state`,
`_active_optimizers`, `_current_optimizer`, `_torch_shim_runtime_state` and
`_transform_getitem_to_index_depth` are no longer runtime contracts. Both
independent and legacy activation keep tensor bookkeeping in Runtime-owned
state; activation status is queried through `jittor.compat.shim.activation_status()`.
Compatibility implementations use `get_tensor_state()` / `latest_optimizer()`
and the context-local getitem scope. Application code should use Tensor
gradient APIs and optimizer instances instead of private registry attributes.

### Tensor semantics: 0-d results, integer promotion, and one non-in-place method

Three changes alter what existing native-Jittor code computes, not just what it
imports. Torch-mode code is unaffected: the compatibility layer maps these to
PyTorch's own semantics, which is what they were changed to match.

**Indexing down to a scalar now yields a 0-d Var.** `a[1, 2]` has `ndim == 0`,
where 1.x padded an empty shape to `(1,)`. Code that relied on the padding --
`a[i, j].shape[0]`, or concatenating single elements -- has to say so
explicitly. This is also what makes NumPy-compatible promotion possible:
`float64 * float32` is now `float64` rather than being silently narrowed.

**Integer promotion follows kind and width instead of byte count.**
`uint8(200) + int8(1)` is `int16` (value 201, not a wrapped 8-bit result), and
`uint8 * (1/255.)` is `float32`. 1.x took the wider of the two byte counts and
or-ed the sign bits, which turned mixed-sign arithmetic into a silent wrap.

**`Var.scatter` returns a new Var.** It was in place in 1.x. `x.scatter(...)`
leaves `x` untouched; use the return value, or `x.scatter_(...)` for the in-place
spelling.

### 26 heuristic `x.foo_()` in-place aliases are gone

1.x generated an in-place method for anything whose first parameter looked like
a tensor. That produced 85 aliases, several of which were not in place at all:
`isnan_`, `norm_`, `sort_` and `tolist_` returned non-Var values while their
names promised mutation.

The generated set is replaced by a declared whitelist of 48 methods. The
spellings that disappeared and are most likely to appear in existing code are
`exp_`, `log_`, `sin_`, `cos_`, `tanh_`, `relu_`, `div_`, `neg_`, `round_`,
`floor_`, `ceil_`, `sum_`, `mean_`, `max_`, `min_`, `argmax_`, `sort_`,
`norm_`, `isnan_`, `tolist_`, `matmul_`, `reshape_`, `all_`, `any_`, `float_`
and `int_`. Rewrite as `x.assign(x.exp())`, which is what the generated alias
did.

`all_` and `any_` were removed for a second reason: they are reduction
primitive names, not mutating methods, and the trailing underscore made them
read as the latter.

Torch mode keeps every one of these -- `torch.Tensor.exp_()` works and mutates
in place -- so downstream PyTorch code does not need changes. Note that the
compatibility layer serves them through `__getattr__`, so `hasattr` reports
`False` while the call succeeds.

### Arguments that used to be accepted and ignored now warn or raise

1.x accepted a number of PyTorch-shaped keyword arguments and silently did
nothing with them. Passing a non-default value now warns or raises instead of
returning a result computed under different settings than the caller asked
for. Affected: `inplace=` on the activations, `instance_norm`'s running-stats
arguments, `zero_init_residual` on the ResNets, `compute_uv`/`driver` on `svd`,
`check_errors` on `inv_ex`, `zero_infinity` on `ctc_loss`, `sorted` on `topk`,
`stable` on `sort`, `generator` on the Kaiming initializers, `pin_memory` and
`persistent_workers` on `DataLoader`, `strict` on `vjp`/`jvp`, and
`dtype`/`device` on `fftfreq`.

`MaxPool3d(ceil_mode=True)` output shapes changed for the same class of reason:
1.x produced one plane more than PyTorch because it omitted the "drop a window
that lies entirely in the padding" correction. `MaxUnpool3d`'s default
`output_size` follows from it, so a round trip through both still matches.

### Namespace surface is declared rather than incidental

The root package and `jittor.nn` now export a declared `__all__`. Names that
existed only because of star imports are gone: `jt.np` is the one most likely
to appear in existing code (use `numpy` directly), and `dir(jt.nn)` no longer
contains any underscore-prefixed entries.

Flags are split by lifetime: `jt.config` is a read-only snapshot of what was
decided at startup, `jt.runtime` holds the switches that may change during a
run. `jt.flags` still works.

### User errors are now catchable exceptions

Invalid shapes, dtypes and indices raise Python exceptions instead of calling
`LOGf`, which aborted the process. Code that guarded against those cases by
avoiding them still works; code that relied on the process dying does not.
Internal invariant violations remain assertions -- the distinction is the point
of the change, so an exception escaping from a Jittor call is now always a
statement about the caller's input.

### Native Jittor and Torch compatibility now activate separately

Plain `import jittor as jt` keeps native Jittor semantics and no longer claims
the top-level `torch` namespace. Torch mode is selected by the deployed shim,
`JITTOR_TORCH_SHIM=1`, an explicit `jittor.compat.shim.activate()` call, or the
historical `import jittor.torch_compat` activation path. A local
`import jittor as torch` alias alone no longer changes process mode.

This restores pre-2.0 native contracts such as `Var.data` returning a shared
NumPy view. In Torch mode, `Tensor.data` remains a detached Tensor alias and its
in-place updates stay on the active device. Applications must not switch from
native to Torch mode after model execution has begun because compatibility
installation changes process-wide class APIs.

### Torch compatibility no longer replaces the Jittor package version

`jittor.__version__` now always reports the installed Jittor distribution
version (`1.3.11.0` for this release line), including when the deployed Torch
entry point is used and `torch is jittor`. Code that needs the emulated PyTorch
API level must use `jittor.__torch_version__` or
`torch.version.__version__`; both currently report `2.11.0`.

Required Torch compatibility installers always fail with a named install step,
even when `JITTOR_TORCH_STRICT_BOOTSTRAP` is disabled. That switch controls the
optional shim runtime bootstrap only; it cannot hide an incomplete core API.
The deployment CLI verification command reports the Torch API version through
`torch.__torch_version__` and `torch.version.__version__`, not the Jittor
backend version exposed as `torch.__version__` by the same-module entry point.

### `jittor.vcompiler` retired

Jittor 2.0 removes the experimental `jittor.vcompiler` package and its
`build()` decorator. Importing that package compiled a private C++ static-graph
extension as a side effect, and the API had no in-repository consumer or stable
compatibility contract. Source checkouts and installed wheels now both report
no module specification for `jittor.vcompiler`.

There is no drop-in replacement for its cached static-graph decorator. Use
normal Jittor graph execution for model code. Extension authors who need a
custom operation should use the maintained `jittor.compile_custom_op` or
`jittor.compile_custom_ops` interfaces and explicitly test forward and backward
behavior on each supported backend.

### Repository-only payload moved out of the wheel

Operational scripts, release utilities, examples, and notebooks now live under
root `tools/` and `examples/`. They remain available in the source distribution
but are no longer importable members of the runtime wheel. Installed-environment
validation uses `python -m jittor.selftest`.

MyST Markdown under `examples/notebooks/` is the canonical tutorial source.
Generated `.ipynb` files are no longer versioned or shipped in the source
distribution; `python -m nox -s tutorials` materializes them in external state
and runs the maintained offline CPU smoke set.

The legacy Clang alignment pass under `jittor/extern/llvm` and its unused
`jittor.compiler.compile_extern()` build hook have been removed. The hook was
not called by the runtime, and retaining the private LLVM plugin made Clang
startup depend on an unmaintained compiler-internal ABI without improving the
active JIT path.
