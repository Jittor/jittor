# Jittor 2.0 发布说明

这条发布线有两个使用方式：**原生 Jittor**（`import jittor as jt`，元算子 + 统一图 +
即时编译）和**一层 Torch 兼容前端**（`import torch` 指向 Jittor，让按 PyTorch 写的代码
不改一行跑起来）。后端为 CPU、NVIDIA CUDA 与华为昇腾 ACL；ROCm 与天数 Corex 的代码在
树里但**没有设备验证**。每一项支持的验证位置见[平台支持](../guides/platform-support.md)，
用户可见的开口项见[已知限制](../guides/known-limitations.md)。

**版本号尚未确定**：`jittor.__version__` 目前仍是 `1.3.11.0`，而这条线称为 2.0。
这是一个发布节点上要做的决定，三个候选与各自的代价写在本页末尾的「发布前待定的事项」
一节，本页不替维护者选。

## 亮点

- **`import torch` 就能跑。** 独立的 Torch 命名空间（`torch is not jittor`），
  transformers / diffusers / peft / ms-swift / mmcv / torchmetrics 的用例与独立安装的
  真实 PyTorch 逐梯度对拍，CPU 与 CUDA 都比；nightly 门禁把它守住。见
  [Torch 兼容](../compatibility/torch.md)。
- **昇腾 910B 是一等后端。** ACL/HCCL 后端有 fail-closed 的 NPU 门禁（真实设备、
  禁止 CPU 回退），一次冷缓存全量验证记在
  [Ascend 910B3 验证](../results/2026-08-28-ascend-910b-validation.md)。
- **图重放与整步捕获。** 重复的推理图不再每次重建，训练步可以整体捕获重放；
  CUDA 与 ACL 都能录成设备图。见[静态图重放](../development/static-graph-replay.md)。
- **报错是可捕获的异常，不再是进程中止。** 非法形状、dtype 与索引抛 Python 异常；
  内部不变量仍然是断言。
- **装不上、编不动有专门的诊断。** `python -m jittor_utils.preflight` 一次列出所有
  缺失项并说明哪些 Jittor 能自己解决；`jittor_utils.env_manifest` 列出全部环境变量；
  `jittor_utils.clean_cache` 按组清缓存。

## 新增能力

- **Torch 兼容层**（`compat/`，独立发行物 `jittor-torch`）：独立命名空间、部署命令
  `jittor-torch-shim`、`torch.utils.cpp_extension`、bf16/fp16 autocast 与 GradScaler、
  `torch.func`、`torch.linalg`、`torch.distributions`、`torch.fft`、`torch.load` 与
  safetensors 的直接读取。可选适配器发行物 `jittor-torch-adapters`
  （Transformers / TorchMetrics / vLLM）。
- **昇腾 ACL 后端**（`backends/acl/`）：原生算子发射路径、设备图录制（`aclmdlRI`）、
  CANN 原生 sort/argsort/topk 与 multinomial、HF32 卷积、显式的不支持 dtype 报错。
- **图重放与捕获**：`jt.graph_replay`（重放推理图）与 `jt.capture_step`（整步捕获），
  自动策略由 `JT_AUTO_GRAPH_REPLAY` 控制，默认开启且只在 `no_grad` 下生效。
- **流水执行**：构图与设备执行重叠（`JT_AUTO_FLUSH_OPS` / `JT_AUTO_FLUSH_BYTES`），
  以及 CUDA 上的异步执行 worker（`JT_ASYNC_EXECUTION`）。代价已量过，见
  [流水执行](../notes/pipelined-execution.md)。
- **原生 complex64**：`jittor_core` 的一等 dtype，公开 API 接受并返回原生复数 Var，
  剩余的桥接与限制登记在[复数 dtype](../notes/complex-dtype.md)。
- **不依赖 MPI 的分布式**：`python -m jittor.distributed.launch` 的 torchrun 式启动器、
  TCP/文件 rendezvous、NCCL 与 HCCL 集合通信、FSDP2。
- **性能分析**：`jt.profile`，设备时间经 CUPTI（`jittor[profile]` extra）；没有 CUPTI
  时报告「设备时间不可用」而不是编一个数出来。见[性能分析](../notes/profiling.md)。
- **CUDA 12 组件 wheel**：`jittor[cuda12]` 安装固定版本的 CUDA 12.2 运行时与
  cuDNN ≥ 8.9.7 < 10（含 cuDNN 9，可与现代 torch 共存）；`JITTOR_CUDA_WHEEL_STRICT=1`
  拒绝不完整的组件栈。**Jittor 仍然不会替你下载 `nvcc`。**
- **环境变量分成两个命名空间**：`JT_BUILD_*` 决定编译产物，`JT_*` 决定运行行为；
  旧的无前缀名仍然生效并在启动时提示一次。
- **`jittor.models` 补上现代视觉骨干**：`vit_b_16` / `vit_b_32` / `vit_l_16`、
  Swin、ConvNeXt、MaxViT 等。
- **NumPy 2.x 与 Python 3.13** 是维护中的路径：Python 3.13 的 wheel 门禁在 NumPy 2.x
  下运行。

## 破坏性变更与移除

### 移除了 Torch 运行时的私有别名

`jittor._torch_leaf_params`、`_torch_retained`、`_torch_tensor_state`、
`_active_optimizers`、`_current_optimizer`、`_torch_shim_runtime_state` 和
`_transform_getitem_to_index_depth` 不再是运行时契约。独立模式与历史别名模式都把
张量记账放在 Runtime 拥有的状态里；激活状态通过
`jittor.compat.shim.activation_status()` 查询。

兼容层实现改用 `get_tensor_state()` / `latest_optimizer()` 和上下文局部的 getitem
作用域。**应用代码应该使用 Tensor 的梯度 API 和优化器实例，而不是私有注册表属性。**

### 张量语义：0 维结果、整数提升、以及一个不再原地的方法

有三处改动会改变现有**原生 Jittor** 代码算出来的结果，不只是改变它导入什么。
Torch 模式不受影响——兼容层把这些映射到 PyTorch 自己的语义，而这正是它们改成
现在这样的原因。

**索引到标量现在得到 0 维 Var。** `a[1, 2]` 的 `ndim == 0`，而 1.x 会把空形状补成
`(1,)`。依赖那个补齐的代码——`a[i, j].shape[0]`，或者把单个元素拼起来——现在必须
显式写出来。这同时也是 NumPy 兼容的类型提升得以成立的前提：`float64 * float32`
现在是 `float64`，不再被静默收窄。

**整数提升按种类与位宽，不再按字节数。** `uint8(200) + int8(1)` 是 `int16`
（值为 201，不是回绕后的 8 位结果），`uint8 * (1/255.)` 是 `float32`。1.x 取两者
字节数的较大值再把符号位或起来，这会把混合符号的运算变成一次**静默回绕**。

**`Var.scatter` 返回新 Var。** 它在 1.x 里是原地的。`x.scatter(...)` 不再改动 `x`；
请使用返回值，或用 `x.scatter_(...)` 这个原地写法。

### 26 个靠启发式生成的 `x.foo_()` 原地别名被删除

1.x 会给任何"第一个参数看起来像张量"的函数生成一个原地方法，一共造出 85 个别名，
其中若干**根本不是原地的**：`isnan_`、`norm_`、`sort_` 和 `tolist_` 返回的是非 Var
值，名字却承诺了修改。

生成的这一批被一份**声明式的 48 个方法白名单**取代。消失的拼写里最可能出现在现有
代码中的是：`exp_`、`log_`、`sin_`、`cos_`、`tanh_`、`relu_`、`div_`、`neg_`、
`round_`、`floor_`、`ceil_`、`sum_`、`mean_`、`max_`、`min_`、`argmax_`、`sort_`、
`norm_`、`isnan_`、`tolist_`、`matmul_`、`reshape_`、`all_`、`any_`、`float_`、`int_`。
改写成 `x.assign(x.exp())`——这正是原来生成的别名所做的事。

`all_` 和 `any_` 还有第二个原因：它们是**归约原语的名字**，不是修改型方法，末尾的
下划线让人读成后者。

**Torch 模式保留全部这些**——`torch.Tensor.exp_()` 可用且原地生效——所以下游
PyTorch 代码不需要改动。注意兼容层通过 `__getattr__` 提供它们，因此 `hasattr` 会
报 `False`，但调用是成功的。

### 过去被接受然后忽略的参数，现在会警告或报错

1.x 接受了一批 PyTorch 形状的关键字参数却什么也不做。现在传入非默认值会警告或报错，
而不是**返回一个在与调用者所要求的不同设置下算出来的结果**。

涉及：激活函数的 `inplace=`、`instance_norm` 的 running-stats 参数、ResNet 的
`zero_init_residual`、`svd` 的 `compute_uv`/`driver`、`inv_ex` 的 `check_errors`、
`ctc_loss` 的 `zero_infinity`、`topk` 的 `sorted`、`sort` 的 `stable`、Kaiming
初始化器的 `generator`、`DataLoader` 的 `pin_memory` 与 `persistent_workers`、
`vjp`/`jvp` 的 `strict`，以及 `fftfreq` 的 `dtype`/`device`。

`MaxPool3d(ceil_mode=True)` 的输出形状因同类原因发生变化：1.x 比 PyTorch 多产生一个
平面，因为它漏掉了"丢弃完全落在 padding 里的窗口"这条修正。`MaxUnpool3d` 的默认
`output_size` 由它推出，所以两者往返仍然对得上。

### 命名空间是声明出来的，不是附带产生的

根包和 `jittor.nn` 现在导出声明式的 `__all__`。仅仅因为 star import 而存在的名字
消失了：最可能出现在现有代码里的是 `jt.np`（请直接用 `numpy`），并且
`dir(jt.nn)` 不再包含任何下划线开头的条目。

Flag 按**生命周期**拆分：`jt.config` 是启动时决定内容的只读快照，`jt.runtime` 放
运行期间可以改变的开关。`jt.flags` 仍然可用。

### 用户错误现在是可捕获的异常

非法的形状、dtype 和索引会抛 Python 异常，而不是调用 `LOGf` 直接中止进程。原本通过
避开这些情况来防御的代码照常工作；依赖"进程会死"的代码不再成立。

**内部不变量的违反仍然是断言**——这个区分正是本次改动的意义所在：**从 Jittor 调用
里逃出来的异常，现在永远是在陈述调用者输入的问题。**

### 原生 Jittor 与 Torch 兼容分别激活，别名安装模式移除

普通的 `import jittor as jt` 保持原生 Jittor 语义，**不再占用顶层 `torch` 命名空间**。
Torch 模式由已部署的 shim、`JITTOR_TORCH_SHIM=1`、显式调用
`jittor.compat.shim.activate()`，或历史的 `import jittor.torch_compat` 路径选中。
单纯写一个 `import jittor as torch` 的本地别名**不再改变进程模式**。

把 Torch API 装到原生 `jittor` 模块上的那种**别名安装模式已经移除**，不再是一种可选
形态：`activate(independent_namespace=False)`、`JITTOR_TORCH_INDEPENDENT=0` 和直接调用
`compat.torch.install(jittor)` 都会抛出迁移错误。`JITTOR_TORCH_INDEPENDENT` 今天
**不需要设**；设成假值会让 `import torch` 直接失败（`compat/shim/preflight.py` 的
`require_independent_frontend()`，以及部署的 `torch/__init__.py` 开头那条检查）。

这恢复了 2.0 之前的原生契约，例如 `Var.data` 返回共享的 NumPy 视图。Torch 模式下
`Tensor.data` 仍是 detach 的 Tensor 别名，其原地更新留在当前设备上。

**应用不得在模型开始执行之后再从原生模式切换到 Torch 模式**，因为兼容安装会改变
进程级的类 API。

### Torch 兼容不再替换 Jittor 的包版本号

`jittor.__version__` 现在**始终**报告已安装的 Jittor 发行版本（本发布线为
`1.3.11.0`），即使用的是部署的 Torch 入口、`torch is jittor` 时也一样。需要被模拟的
PyTorch API 级别时，请用 `jittor.__torch_version__` 或 `torch.version.__version__`，
两者当前都报告 `2.11.0`。

必需的 Torch 兼容安装器**总是**以具名的安装步骤失败，即使
`JITTOR_TORCH_STRICT_BOOTSTRAP` 被关闭。那个开关只控制可选的 shim 运行时引导，
**不能掩盖不完整的核心 API**。部署 CLI 的校验命令通过 `torch.__torch_version__`
和 `torch.version.__version__` 报告 Torch API 版本，而不是同模块入口以
`torch.__version__` 暴露的 Jittor 后端版本。

### `jittor.vcompiler` 退役

Jittor 2.0 移除了实验性的 `jittor.vcompiler` 包及其 `build()` 装饰器。导入那个包会
**作为副作用**编译一个私有的 C++ 静态图扩展，而该 API 在仓库内没有消费者，也没有
稳定的兼容契约。源码 checkout 和已安装的 wheel 现在都报告 `jittor.vcompiler` 无模块
规格。

它那个带缓存的静态图装饰器**没有直接替代品**。模型代码请使用正常的 Jittor 图执行。
需要自定义算子的扩展作者应使用维护中的 `jittor.compile_custom_op` 或
`jittor.compile_custom_ops` 接口，并在每个受支持的后端上显式测试前向与反向。

### 仅供仓库使用的内容移出 wheel

运维脚本、发布工具、示例和 notebook 现在位于顶层 `tools/` 和 `examples/`。它们仍在
源码发行物中，但**不再是运行时 wheel 的可导入成员**。已安装环境的校验用
`python -m jittor.selftest`。

`examples/notebooks/` 下的 MyST Markdown 是教程的规范来源。生成的 `.ipynb` 不再纳入
版本管理，也不随源码发行物分发；`python -m nox -s tutorials` 会在仓库外生成它们并
运行维护中的离线 CPU 冒烟集。

`jittor/extern/llvm` 下遗留的 Clang 对齐 pass 及其未被使用的
`jittor.compiler.compile_extern()` 构建钩子已被移除。该钩子运行时从未被调用，而保留
这个私有 LLVM 插件会让 Clang 启动依赖一个无人维护的编译器内部 ABI，对活跃的 JIT
路径毫无帮助。

### 课堂脚本与遗留安装脚本删除

`jittor_utils.class`（SKEY 课堂环境配置）与 `jittor_utils.student_queue`（课堂排队）
连同它们的别名与 `.pyi` 条目一并删除。同批删掉的还有 `tools/install/legacy/`
（`install.sh`、`install_llvm.sh`、`install_mkl.sh`）、`tools/benchmarks/legacy/`、
一个自述失败的梯度探针，以及一份无人引用的 introspection 例外清单（`6c3d741e`）。

这些都没有替代品，因为它们服务的流程已经不存在：安装走
`python -m pip install jittor`（见
[README](https://github.com/Jittor/jittor#install)），装不上的诊断走
`python -m jittor_utils.preflight`。

同一次清理把八个维护者探针收进
[`tools/probes/`](https://github.com/Jittor/jittor/blob/master/tools/README.md)，
它们打印两条等价计算（或两个设备、两次往返）在哪里不一致，是问题总账引用的证据来源，
**不是测试**。

### `python/jittor/utils/` 拆开，C++ 源码移出 Python 包

`python/jittor/utils/` 不再存在：面向用户的 `jtune` 与 NVTX 工具迁到
`jittor.tools`，仓库维护脚本迁到顶层 `tools/`（`fdf3b759`）。`jittor_utils` 现在是
一层很薄的引导，真正的实现在 `jittor/build/utils/`，公开的
`python -m jittor_utils.<工具>` 入口不变（`4d70f190`）。

C++ 与 CUDA 源码同时**移出了 Python 包**：内核在顶层 `src/`，每个后端在
`backends/<名字>/`。源码 checkout 在 `python/jittor/` 的同级目录找它们，wheel 仍把
它们装成 `jittor/src/` 与 `jittor/backends/<名字>/`，所以**已安装环境的路径没有变**；
改动的是源码树。理由与硬路径不变量见[仓库布局](../development/repository-layout.md)。

## 升级须知

1. **原生代码先看这三条语义变更**：索引到标量得到 0 维 Var、整数提升按种类与位宽、
   `Var.scatter` 不再原地。Torch 模式不受影响。
2. **把 `x.foo_()` 的拼写对一遍白名单**：生成的那 26 个别名没了，改写成
   `x.assign(x.foo())`。
3. **别再设 `JITTOR_TORCH_INDEPENDENT`**，并重新部署旧环境里生成的 `torch` 入口
   （`jittor-torch-shim`，然后 `jittor-torch-shim --check`）。
4. **检查被忽略过的关键字参数**：过去被接受然后忽略的参数现在会警告或报错，这意味着
   你的某些调用一直没有生效。
5. **版本号跳变会触发一次全量重编**（版本是 JIT 缓存路径的第一级分量）。首次 import
   的代价、缓存位置和怎么搬走它，见
   [README](https://github.com/Jittor/jittor#install) 的「首次运行会发生什么」。
6. **声明加速器支持之前先在设备上跑一遍。** 导入成功与 CPU 回退都不构成证据；
   ACL 的测试在 `backend_fallback=error` 下跑就是这个原因。

## 发布前待定的事项

下面不是已经做出的改动，而是发布节点上要由维护者决定的事项；本页不预先替维护者选择。

### 版本号

`jittor.__version__` 仍是 `1.3.11.0`（`python/jittor/__init__.py`），而这条发布线称为 2.0。
包版本只有这一处真源（`pyproject.toml` 的 `dynamic = ["version"]` 读取
`jittor.__version__`），所以它同时决定 wheel 名、PyPI 上的版本和 `pip install jittor==` 的
写法；`compat/pyproject.toml` 与 `adapters/pyproject.toml` 各自写着同一个版本号，后者还钉着
`jittor-torch==1.3.11.0`。三个候选：

- **改为 `2.0.0`。** 名实相符，主版本号的提升也如实传达了上文列出的破坏性变更。要同批修改：
  三个 `pyproject.toml`/`__init__.py` 里的版本与依赖钉、
  `compat/tests/torch/test_torch_shim_aliases.py` 对 `jittor.__version__` 的硬编码断言、发布
  tag 的写法（`.github/workflows/release.yml` 断言 tag 去掉前缀 `v` 后等于 wheel 版本），并重新
  生成 `tools/release/baselines/wheel-contents-final.txt`（其中 `jittor-1.3.11.0.dist-info/*`
  的条目会改名）。版本是 JIT 缓存路径的第一级分量（`jt1.3.11` 这样的目录），所以每个用户都会
  全量重编一次。
- **保持 `1.3.11.0`，到发布节点再定。** 零改动、不重编，代价是文档说 2.0 而
  `pip show jittor` 说 1.3.11.0。
- **把包版本与 API 世代分开。** `__version__` 跟随发布节奏，另加一个有单一真源并由结构测试
  钉住的世代标识；不动 wheel 名、tag 与缓存路径，也不触发重编。先例就在兼容层：
  `jittor.__version__` 报告发行版本，`jittor.__torch_version__` 与
  `torch.version.__version__` 报告所模拟的 PyTorch API 级别。

与选择无关的一点：缓存目录只取版本去掉最后一段（`version_dir_name()`），不按最后一级分区
**不是缺陷**——编译缓存按源码内容哈希，版本相近而源码不同的两次构建只会重编改动的部分。
