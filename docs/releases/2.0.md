# Jittor 2.0 Migration Notes

## Breaking Changes

### Native Jittor and Torch compatibility now activate separately

Plain `import jittor as jt` keeps native Jittor semantics and no longer claims
the top-level `torch` namespace. Torch mode is selected by the deployed shim,
`JITTOR_TORCH_SHIM=1`, an entry script using `import jittor as torch`, or the
historical `import jittor.torch_compat` activation path.

This restores pre-2.0 native contracts such as `Var.data` returning a shared
NumPy view. In Torch mode, `Tensor.data` remains a detached Tensor alias and its
in-place updates stay on the active device. Applications must not switch from
native to Torch mode after model execution has begun because compatibility
installation changes process-wide class APIs.

### Torch compatibility no longer replaces the Jittor package version

`jittor.__version__` now always reports the installed Jittor distribution
version (`1.3.11.0` for this release line), including when the deployed Torch
entry point is used and `torch is jittor`. Code that needs the emulated PyTorch
API level must use `jittor.__torch_version__` or
`torch.version.__version__`; both currently report `2.11.0`.

Required Torch compatibility installers always fail with a named install step,
even when `JITTOR_TORCH_STRICT_BOOTSTRAP` is disabled. That switch controls the
optional shim runtime bootstrap only; it cannot hide an incomplete core API.
The deployment CLI verification command reports the Torch API version through
`torch.__torch_version__` and `torch.version.__version__`, not the Jittor
backend version exposed as `torch.__version__` by the same-module entry point.

### `jittor.vcompiler` retired

Jittor 2.0 removes the experimental `jittor.vcompiler` package and its
`build()` decorator. Importing that package compiled a private C++ static-graph
extension as a side effect, and the API had no in-repository consumer or stable
compatibility contract. Source checkouts and installed wheels now both report
no module specification for `jittor.vcompiler`.

There is no drop-in replacement for its cached static-graph decorator. Use
normal Jittor graph execution for model code. Extension authors who need a
custom operation should use the maintained `jittor.compile_custom_op` or
`jittor.compile_custom_ops` interfaces and explicitly test forward and backward
behavior on each supported backend.

### Repository-only payload moved out of the wheel

Operational scripts, release utilities, examples, and notebooks now live under
root `tools/` and `examples/`. They remain available in the source distribution
but are no longer importable members of the runtime wheel. Installed-environment
validation uses `python -m jittor.selftest`.

MyST Markdown under `examples/notebooks/` is the canonical tutorial source.
Generated `.ipynb` files are no longer versioned or shipped in the source
distribution; `python -m nox -s tutorials` materializes them in external state
and runs the maintained offline CPU smoke set.

The legacy Clang alignment pass under `jittor/extern/llvm` and its unused
`jittor.compiler.compile_extern()` build hook have been removed. The hook was
not called by the runtime, and retaining the private LLVM plugin made Clang
startup depend on an unmaintained compiler-internal ABI without improving the
active JIT path.
