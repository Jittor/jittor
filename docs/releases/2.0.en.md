# Jittor 2.0 release notes

This release line has two ways to use it: **native Jittor** (`import jittor as jt`, meta-operators + unified graph +
just-in-time compilation) and **a Torch compatibility frontend** (`import torch` points at Jittor, letting code
written for PyTorch run without changing a line). The backends are CPU, NVIDIA CUDA, and Huawei Ascend ACL; ROCm and
Iluvatar Corex code is in the tree but has **no device validation**. For where each supported item is validated, see
[Platform support](../guides/platform-support.en.md); for user-visible open items, see
[Known limitations](../guides/known-limitations.en.md).

**Version**: `jittor.__version__` is `2.0.0`, and the `jittor-torch` and `jittor-torch-adapters`
distributions are synchronized to `2.0.0`. For the wrap-up items still needed at the release node, see the
[release wrap-up checklist](#release-wrap-up-checklist) at the end of this page.

## Highlights

- **`import torch` just works.** An independent Torch namespace (`torch is not jittor`); transformers / diffusers /
  peft / ms-swift / mmcv / torchmetrics cases are compared gradient by gradient against an independently installed
  real PyTorch, on both CPU and CUDA; the nightly gate guards it. See
  [Torch compatibility](../compatibility/torch.en.md).
- **Ascend 910B is a first-class backend.** The ACL/HCCL backend has a fail-closed NPU gate (real device,
  CPU fallback forbidden); a full cold-cache validation is recorded in
  [Ascend 910B3 validation](../results/2026-08-28-ascend-910b-validation.en.md).
- **Graph replay and whole-step capture.** Repeated inference graphs are no longer rebuilt every time, and a
  training step can be captured and replayed as a whole; both CUDA and ACL can record device graphs. See
  [Static graph replay](../development/static-graph-replay.en.md).
- **Errors are catchable exceptions, no longer process aborts.** Illegal shapes, dtypes, and indices raise Python
  exceptions; internal invariants remain assertions.
- **Installation and compilation failures have dedicated diagnostics.** `python -m jittor_utils.preflight` lists all
  missing items at once and says which Jittor can solve itself; `jittor_utils.env_manifest` lists all environment
  variables; `jittor_utils.clean_cache` clears caches by group.

## New capabilities

- **Torch compatibility layer** (`compat/`, separate distribution `jittor-torch`): independent namespace, deployment
  command `jittor-torch-shim`, `torch.utils.cpp_extension`, bf16/fp16 autocast and GradScaler,
  `torch.func`, `torch.linalg`, `torch.distributions`, `torch.fft`, `torch.load`, and direct reading of
  safetensors. Optional adapter distribution `jittor-torch-adapters`
  (Transformers / TorchMetrics / vLLM).
- **Ascend ACL backend** (`backends/acl/`): native operator emission path, device graph recording (`aclmdlRI`),
  CANN-native sort/argsort/topk and multinomial, HF32 convolution, explicit errors for unsupported dtypes.
- **Graph replay and capture**: `jt.graph_replay` (replay inference graphs) and `jt.capture_step` (capture a whole
  step), with the automatic policy controlled by `JT_AUTO_GRAPH_REPLAY`, enabled by default and effective only under
  `no_grad`.
- **Pipelined execution**: graph construction overlaps device execution (`JT_AUTO_FLUSH_OPS` / `JT_AUTO_FLUSH_BYTES`),
  plus an asynchronous execution worker on CUDA (`JT_ASYNC_EXECUTION`). The cost has been measured; see
  [Pipelined execution](../notes/pipelined-execution.en.md).
- **Native complex64**: a first-class dtype of `jittor_core`; the public API accepts and returns native complex Vars.
  Remaining bridges and limitations are recorded in [Complex dtype](../notes/complex-dtype.en.md).
- **Distributed without MPI**: a torchrun-style launcher at `python -m jittor.distributed.launch`,
  TCP/file rendezvous, NCCL and HCCL collective communication, FSDP2.
- **Profiling**: `jt.profile`, with device time via CUPTI (the `jittor[profile]` extra); without CUPTI
  it reports "device time unavailable" rather than inventing a number. See [Profiling](../notes/profiling.en.md).
- **CUDA 12 component wheels**: `jittor[cuda12]` installs a pinned CUDA 12.2 runtime and
  cuDNN ≥ 8.9.7 < 10 (including cuDNN 9, which can coexist with modern torch); `JITTOR_CUDA_WHEEL_STRICT=1`
  rejects an incomplete component stack. **Jittor still will not download `nvcc` for you.**
- **Environment variables split into two namespaces**: `JT_BUILD_*` determines build artifacts, `JT_*` determines
  runtime behavior; the old unprefixed names still work and print a notice once at startup.
- **`jittor.models` gains modern vision backbones**: `vit_b_16` / `vit_b_32` / `vit_l_16`,
  Swin, ConvNeXt, MaxViT, and more.
- **NumPy 2.x and Python 3.13** are maintained paths: the Python 3.13 wheel gate runs under NumPy 2.x.

## Breaking changes and removals

### Removed private aliases of the Torch runtime

`jittor._torch_leaf_params`, `_torch_retained`, `_torch_tensor_state`,
`_active_optimizers`, `_current_optimizer`, `_torch_shim_runtime_state`, and
`_transform_getitem_to_index_depth` are no longer runtime contracts. Both independent mode and legacy alias mode keep
tensor bookkeeping in Runtime-owned state; activation status is queried through
`jittor.compat.shim.activation_status()`.

The compatibility layer implementation uses `get_tensor_state()` / `latest_optimizer()` and a context-local getitem
scope instead. **Application code should use a Tensor's gradient API and optimizer instances, not private registry
attributes.**

### Tensor semantics: 0-D results, integer promotion, and one method that is no longer in place

Three changes alter what existing **native Jittor** code computes, not just what it imports.
Torch mode is unaffected -- the compatibility layer maps these to PyTorch's own semantics, which is
exactly why they were changed to be this way.

**Indexing to a scalar now yields a 0-D Var.** `a[1, 2]` has `ndim == 0`, whereas 1.x padded the empty shape to
`(1,)`. Code that relies on that padding -- `a[i, j].shape[0]`, or concatenating single elements -- must now be
written explicitly. This is also the prerequisite for NumPy-compatible type promotion: `float64 * float32`
is now `float64` and is no longer silently narrowed.

**Integer promotion is by kind and bit width, not byte count.** `uint8(200) + int8(1)` is `int16`
(value 201, not the wrapped 8-bit result), and `uint8 * (1/255.)` is `float32`. 1.x took the larger
byte count of the two and OR'd the sign bits, which turned mixed-sign arithmetic into a **silent
wraparound**.

**`Var.scatter` returns a new Var.** It was in-place in 1.x. `x.scatter(...)` no longer modifies `x`;
use the return value, or the in-place spelling `x.scatter_(...)`.

### 26 heuristic-generated `x.foo_()` in-place aliases were removed

1.x generated an in-place method for any function whose "first argument looked like a tensor", producing 85
aliases in total, several of which **were not in-place at all**: `isnan_`, `norm_`, `sort_`, and `tolist_`
returned non-Var values while their names promised a mutation.

The generated batch is replaced by a **declarative allowlist of 48 methods**. The disappeared spellings most likely
to appear in existing code are: `exp_`, `log_`, `sin_`, `cos_`, `tanh_`, `relu_`, `div_`, `neg_`,
`round_`, `floor_`, `ceil_`, `sum_`, `mean_`, `max_`, `min_`, `argmax_`, `sort_`,
`norm_`, `isnan_`, `tolist_`, `matmul_`, `reshape_`, `all_`, `any_`, `float_`, `int_`.
Rewrite them as `x.assign(x.exp())` -- exactly what the generated alias used to do.

`all_` and `any_` have a second reason: they are **reduction primitive names**, not mutating methods, and the
trailing underscore makes people read them as the latter.

**Torch mode keeps all of these** -- `torch.Tensor.exp_()` is available and works in place -- so downstream
PyTorch code needs no changes. Note that the compatibility layer provides them through `__getattr__`, so `hasattr`
reports `False` even though the call succeeds.

### Parameters formerly accepted then ignored now warn or raise

1.x accepted a set of PyTorch-shaped keyword arguments and did nothing with them. Passing a non-default value now
warns or raises, instead of **returning a result computed under different settings than the caller asked for**.

Affected: activation functions' `inplace=`, `instance_norm`'s running-stats parameters, ResNet's
`zero_init_residual`, `svd`'s `compute_uv`/`driver`, `inv_ex`'s `check_errors`,
`ctc_loss`'s `zero_infinity`, `topk`'s `sorted`, `sort`'s `stable`, the Kaiming
initializer's `generator`, `DataLoader`'s `pin_memory` and `persistent_workers`,
`vjp`/`jvp`'s `strict`, and `fftfreq`'s `dtype`/`device`.

`MaxPool3d(ceil_mode=True)` output shapes change for the same class of reason: 1.x produced one more
plane than PyTorch because it missed the "drop windows that fall entirely inside padding" correction. `MaxUnpool3d`'s
default `output_size` is derived from it, so the two still round-trip correctly.

### Namespaces are declared, not incidental

The root package and `jittor.nn` now export declarative `__all__`. Names that existed only
because of star imports are gone: the one most likely to appear in existing code is `jt.np` (use `numpy` directly),
and `dir(jt.nn)` no longer contains any underscore-prefixed entries.

Flags are split by **lifecycle**: `jt.config` is a read-only snapshot fixed at startup, and `jt.runtime` holds
switches that can change during a run. `jt.flags` remains available.

### User errors are now catchable exceptions

Illegal shapes, dtypes, and indices raise Python exceptions instead of calling `LOGf` to abort the process. Code that
defended itself by avoiding these cases works as before; code that relied on "the process will die" no longer holds.

**Violations of internal invariants are still assertions** -- this distinction is the point of the change: **an
exception escaping a Jittor call now always states a problem with the caller's input.**

### Native Jittor and Torch compatibility activate separately; alias install mode removed

A plain `import jittor as jt` keeps native Jittor semantics and **no longer occupies the top-level `torch`
namespace**. Torch mode is selected by a deployed shim, `JITTOR_TORCH_SHIM=1`, an explicit call to
`jittor.compat.shim.activate()`, or the legacy `import jittor.torch_compat` path.
A local alias alone, `import jittor as torch`, **no longer changes the process mode**.

The **alias install mode**, which mounted the Torch API onto the native `jittor` module, **has been removed** and is
no longer an option: `activate(independent_namespace=False)`, `JITTOR_TORCH_INDEPENDENT=0`, and calling
`compat.torch.install(jittor)` directly all raise migration errors. `JITTOR_TORCH_INDEPENDENT` today
**does not need to be set**; setting it to a false value makes `import torch` fail outright (`require_independent_frontend()` in
`compat/shim/preflight.py`, and the check at the top of the deployed `torch/__init__.py`).

This restores the pre-2.0 native contract, e.g. `Var.data` returns a shared NumPy view. In Torch mode
`Tensor.data` remains a detached Tensor alias, whose in-place updates stay on the current device.

**An application must not switch from native mode to Torch mode after a model has begun executing**, because the
compatibility install changes process-level class APIs.

### Torch compatibility no longer overrides Jittor's package version

`jittor.__version__` now **always** reports the installed Jittor distribution version (`2.0.0` for this release
line), even when using the deployed Torch entry point where `torch is jittor`. When you need the emulated
PyTorch API level, use `jittor.__torch_version__` or `torch.version.__version__`;
both currently report `2.11.0`.

Required Torch compatibility installers **always** fail with a named install step, even when
`JITTOR_TORCH_STRICT_BOOTSTRAP` is off. That switch only controls optional shim runtime bootstrap; it
**cannot mask an incomplete core API**. The deployed CLI's check command reports the Torch API version through
`torch.__torch_version__` and `torch.version.__version__`, not the Jittor backend version exposed as
`torch.__version__` by the same module entry.

### `jittor.vcompiler` retired

Jittor 2.0 removes the experimental `jittor.vcompiler` package and its `build()` decorator. Importing that package
would **as a side effect** compile a private C++ static-graph extension, and the API had no consumers inside the
repository and no stable compatibility contract. Source checkouts and installed wheels now both report no module
spec for `jittor.vcompiler`.

Its cached static-graph decorator **has no direct replacement**. Model code should use normal Jittor graph
execution. Extension authors who need custom operators should use the maintained `jittor.compile_custom_op` or
`jittor.compile_custom_ops` interfaces, and test forward and backward explicitly on every supported backend.

### Repository-only content moved out of the wheel

Operations scripts, release tooling, examples, and notebooks now live in the top-level `tools/` and `examples/`. They
remain in the source distribution but are **no longer importable members of the runtime wheel**. To validate an
installed environment, use `python -m jittor.selftest`.

The MyST Markdown under `examples/notebooks/` is the canonical source for the tutorials. Generated `.ipynb` files are
no longer version-controlled and are not shipped in the source distribution; `python -m nox -s tutorials` generates
them outside the repository and runs the maintained offline CPU smoke set.

The legacy Clang alignment pass under `jittor/extern/llvm` and its unused
`jittor.compiler.compile_extern()` build hook have been removed. The hook was never called at runtime, and keeping
this private LLVM plugin would make Clang startup depend on an unmaintained compiler-internal ABI, with no benefit to
the active JIT path.

### Classroom scripts and legacy install scripts removed

`jittor_utils.class` (SKEY classroom environment configuration) and `jittor_utils.student_queue` (classroom queueing)
are removed along with their aliases and `.pyi` entries. The same batch removed `tools/install/legacy/`
(`install.sh`, `install_llvm.sh`, `install_mkl.sh`), `tools/benchmarks/legacy/`,
a gradient probe that documented its own failure, and an unreferenced introspection exception list (`6c3d741e`).

None of these has a replacement, because the processes they served no longer exist: installation goes through
`python -m pip install jittor` (see
[README](https://github.com/Jittor/jittor#install)), and installation-failure diagnosis goes through
`python -m jittor_utils.preflight`.

The same cleanup collected eight maintainer probes into
[`tools/probes/`](https://github.com/Jittor/jittor/blob/master/tools/README.md); they print where two equivalent
computations (or two devices, two round trips) disagree, and are the evidence source cited by the issue ledger,
**not tests**.

### `python/jittor/utils/` split up, C++ sources moved out of the Python package

`python/jittor/utils/` no longer exists: the user-facing `jtune` and NVTX tools moved to
`jittor.tools`, and repository maintenance scripts moved to the top-level `tools/` (`fdf3b759`). `jittor_utils` is
now a thin bootstrap layer, with the real implementation in `jittor/build/utils/`, and the public
`python -m jittor_utils.<tool>` entry points unchanged (`4d70f190`).

C++ and CUDA sources also **moved out of the Python package**: kernels are in the top-level `src/`, and each backend
is in `backends/<name>/`. A source checkout finds them in a sibling directory of `python/jittor/`; the wheel still
installs them as `jittor/src/` and `jittor/backends/<name>/`, so **paths in installed environments are unchanged**;
what changed is the source tree. The rationale and hard-path invariants are in
[Repository layout](../development/repository-layout.en.md).

## Upgrade notes

1. **For native code, check these three semantic changes first**: indexing to a scalar yields a 0-D Var, integer
   promotion is by kind and bit width, and `Var.scatter` is no longer in place. Torch mode is unaffected.
2. **Check `x.foo_()` spellings against the allowlist**: the 26 generated aliases are gone; rewrite them as
   `x.assign(x.foo())`.
3. **Stop setting `JITTOR_TORCH_INDEPENDENT`**, and redeploy the `torch` entry generated in old environments
   (`jittor-torch-shim`, then `jittor-torch-shim --check`).
4. **Check keyword arguments that were ignored**: parameters formerly accepted then ignored now warn or raise, which
   means some of your calls were never taking effect.
5. **The version jump triggers one full recompile** (the version is the first path component of the JIT cache). For
   the cost of the first import, the cache location, and how to move it, see
   "What happens on first run" in the [README](https://github.com/Jittor/jittor#install).
6. **Run on the device before declaring accelerator support.** A successful import and CPU fallback are not
   evidence; this is why ACL tests run with `backend_fallback=error`.

## Release wrap-up checklist

The version is set to `2.0.0` (`__version__` in `python/jittor/__init__.py`, the single source of truth for the package
version, which `pyproject.toml` reads via `dynamic = ["version"]`; `compat/pyproject.toml` and
`adapters/pyproject.toml` are synchronized to `2.0.0`, the latter pinning `jittor-torch==2.0.0`). Still needed before
tagging the release:

- Tag with `v2.0.0`: `.github/workflows/release.yml` asserts that the tag with its prefix removed equals the wheel's
  `Version`.
- Regenerate `tools/release/baselines/wheel-contents-final.txt`: it still records the `# source-wheel` header and
  `jittor-1.3.11.0.dist-info/*` entries collected from the `jittor-1.3.11.0` wheel. Content comparison ignores
  `.dist-info`, so regular gates are unaffected, but release packaging (`nox -s packaging`)
  recollects from the real `2.0.0` wheel and re-reviews entry by entry.
- The version is the first path component of the JIT cache (`version_dir_name()` takes the version minus its last
  segment, so the directory name changes from `jt1.3.11` to `jt2.0`), so after upgrading, each user's first import
  triggers one full recompile. That the cache directory is not partitioned by the last segment **is not a defect** --
  the compilation cache hashes source content, so two builds with close versions but different sources recompile only
  the changed parts.
