# CUDA V2 decode host-path control — 2026-10-16

On CUDA GPU0, Qwen2.5-0.5B-Instruct FP16 TP1/batch1, vLLM core 0.24, 4096 input + 64 greedy output, CUDA Graph decode, a separate light cProfile pass covered one warmup and three measured requests. Both engines generated the same three 64-token sequences. This is **not** a throughput comparison: cProfile perturbs wall time.

Across 256 decode steps, native PyTorch `prepare_inputs` accumulated about **0.061 s** and `sample_tokens` **0.121 s**; Jittor accumulated about **0.171 s** and **0.374 s**. Jittor's `async_copy_to_gpu` accounted for **0.071 s** of input preparation, versus native **0.016 s**. Jittor's output initialization and post-update each appeared in about **0.102 s** of nested sampling time, versus native output initialization **0.017 s** and post-update **0.011 s**. These are nested cProfile times, not additive GPU or request times. A default-off `JITTOR_VLLM_EXPERIMENTAL_NATIVE_POST_UPDATE=1` candidate replaced the Jittor/Triton bridge's one-token state-update launch with a `jt.code` CUDA op. Its one GPU0 run completed three measured 64-token requests, all exactly matching native, with median **222.50 ms** and **290.67 output tok/s**. The following candidate-file/flag-off control produced two measured requests and then a worker segmentation fault at `batch1_measure2`; it is not a valid A/B or evidence that the candidate caused the crash. Both parent and worker terminated and GPU0 returned to idle. The original `buffers.py` was restored byte-for-byte to SHA256 `dfdf9e2ed43acab0bdff4112a4132a8431abc1d5783eecc03de0336457d75c1a`; syntax and `git diff --check` passed. A fresh restored-file baseline then completed all three requests, graceful shutdown, median **207.91 ms** and **306.80 tok/s**. Candidate is not promoted: no demonstrated speedup, and the interrupted control leaves the cause of the crash unresolved. Candidate staging file exists locally at `.codex-remote-edit/fa2-paged-decode/buffers-postupdate.py`; it is **not** the remote active implementation.

The existing default-off `JITTOR_TORCH_DIRECT_HOST_COPY=1` flag was also checked in an immediate candidate→baseline→candidate sequence on GPU0 using the same model/prompt/Graph shape and one warmup plus three measured requests per fresh engine. All three engines completed and shut down gracefully. All nine measured 64-token outputs matched each other and the separate native oracle. Candidate aggregate output rates were **306.23** and **297.80 tok/s**; baseline was **303.66 tok/s**. Candidate median request times were **209.99** and **213.01 ms**, baseline **210.54 ms**. This small, inconsistent difference is not a demonstrated speedup; the flag remains off by default. JSON: `_state/vllm-compare-20261013/qwen25-05-matched-4k64-jittor-direct-host-copy-{j0a,base-j0b,j0c}-gpu0-20261016.json`.

A further no-direct → direct → no-direct check isolated the existing `JITTOR_VLLM_DIRECT_NUMPY_H2D` default-on path. All three fresh Jittor engines completed three measured requests and exited gracefully; all nine token sequences matched the native oracle exactly. On GPU0, aggregate rates were **298.17**, **301.77**, and **300.17 output tok/s** respectively; median request times were **213.81**, **212.13**, and **212.72 ms**. The direct path therefore gives only about a 1% gain in this scenario, not the roughly 25% needed to close the gap. A subsequent same-GPU native PyTorch run measured **405.70 tok/s**, median **157.21 ms**, with matching token sequences. The direct Jittor result is **74.4%** of native throughput, or **1.35×** the median request time. This order is not an ideal alternating J/N/J/N strict A/B, and small shifts between engine runs are visible; use it to reject a large H2D-only explanation, not to claim sub-percent causality. The V2 sampled-token readback was checked with `JITTOR_VLLM_EXPERIMENTAL_ASYNC_FETCH` off → on → off, again in fresh engines on GPU0 with the identical 4096+64 prompt and nine exact native-matching output sequences. Aggregate rates were **306.31**, **308.67**, **310.04 tok/s**; median requests **208.46**, **206.42**, **206.11 ms**. The middle async result lies between the controls, so this experiment finds no reliable gain or regression from that switch. The inter-run drift itself is several tok/s and precludes claiming a 1% optimization from the earlier H2D test. Keep the existing default; investigate the larger host/GPU scheduling gap instead.
