## Experimental parallel paged decode (2026-10-15)

The device timeline for Qwen3-0.6B `math` 4096+64 showed 1,764 Jittor fused paged-decode launches totaling 157.26 ms versus native FlashAttention split-KV decode plus merge totaling about 55.45 ms. GEMV totals were already essentially equal (Jittor 106.97 ms, native 107.15 ms). Therefore the next CUDA change targets the paged decode kernel, not prefill FA2 or GEMV.

An opt-in `JITTOR_VLLM_EXPERIMENTAL_SPLIT_DECODE=16` path in `backends/cuda/kernels/nn/kv_cache_cuda.py` partitions each decode head across 16 CTAs and merges stable softmax partials in a second kernel. It preserves the fused KV-cache write and reads the current token directly from the fresh key/value inputs, avoiding a cross-CTA write/read race. The default remains the existing fused kernel (`=0`). Graph-persistent partial buffers are keyed by KV-cache object identity and static shape; the vLLM runner releases them **after** CUDA Graph reset during shutdown, since native `jt.Var` cannot be weak-referenced.

With H2D batching off, GPU 2, the same Qwen3-0.6B FP16 `math` 4096+64 request was run in baseline/split/split/baseline order, 10 measured requests per leg, one warmup per engine. All 40 measured 64-token sequences matched the independent PyTorch oracle exactly, and each worker exited gracefully. The second split leg briefly overlapped a small unit test, so its latency may be slightly perturbed.

| Path | Request median | TTFT median | Decode ITL median |
| --- | ---: | ---: | ---: |
| Jittor baseline 1 | 387.78 ms | 62.76 ms | 5.135 ms |
| Jittor split 1 | 275.44 ms | 62.59 ms | 3.358 ms |
| Jittor split 2 | 280.23 ms | 63.98 ms | 3.409 ms |
| Jittor baseline 2 | 388.71 ms | 63.53 ms | 5.145 ms |
| PyTorch oracle, adjacent 10 requests | 231.51 ms | 48.28 ms | 2.929 ms |

The first split leg reaches about 84.1% of native output throughput (the baseline is about 59.7%) for this specific request. In a separate 100-request 4096+64 stress run, split decode returned 100/100 exact 64-token outputs and shut down cleanly. A long-context kernel test covering batch 3 with lengths 17/4096/4097 and split counts 4/16 passed; existing FP16/BF16 short-context fused-decode tests and graph-teardown ordering tests also passed.

The device profile confirms where the gain came from: split partials took 46.70 ms and merge 2.56 ms across 1,764 calls each, versus 157.26 ms for the old fused kernel. These aggregate decode kernel times are now close to native's approximately 55.45 ms. Profiled whole-request wall times include profiling overhead and should not be compared directly with the unprofiled table above.

Qwen3-8B FP16, `math` 4096+64, three measured requests each, produced the same 64 native token IDs on all repetitions. The split path median was 1.741067 s versus Jittor baseline 1.887826 s and native 1.657329 s, approximately 95.2% native output throughput. This is a preliminary workload-specific result, not a production-stability claim. More multi-shape stress, larger batches, other models, TP>1, and longer soak tests remain necessary before making the split path default.

The next Qwen3-0.6B FP16 batch-shape-switch test captured both 1 and 4 and executed batch 1→4→1, three measured requests per stage, with 128 input + 64 output tokens. Jittor split decode and independent native PyTorch each completed; all 18 corresponding request outputs were 64/64 token-identical, and both worker sets shut down cleanly. Jittor median batch times were 189.75, 246.22, and 191.88 ms versus native 155.98, 169.12, and 155.89 ms. These are hot request times. In that particular cold engine creation, Jittor took 119.9 s to initialize versus native 14.6 s, including two graph captures and other warmup; CPU contention and cold compilation were not isolated, so this startup gap needs a separate repeat rather than being attributed to decode execution.

A first TP2 check on CUDA GPUs 0+2, Qwen3-0.6B FP16 128+64, split 16, produced two 64-token outputs identical to the independent native TP2 oracle and all four workers exited with code 0. The two measured request medians were Jittor 264.15 ms versus native 141.26 ms (53.5% native throughput). Jittor engine creation took 679.67 s on the cold rank-local JIT caches versus native 17.28 s; this extreme cold-start result is reported separately from request latency and needs a warmed-cache rerun. The cold-cache split result and warm-cache baseline were not interleaved, so the measured 53 ms regression is directional until a warmed-cache A/B is repeated.

## Output-sync and metadata follow-up (2026-10-15)

On GPU 0 with the same Qwen2.5-0.5B FP16, batch 1, 4096+64 *math* prompt, H2D batching off and split-16/strong-graph-alias decode, a post-initialization, opt-in replacement of `AsyncGPUModelRunnerOutput`'s global `jt.sync_all(True)` event-record barrier with `jt.sync_all(False)` plus targeted host-copy `Var.sync()` kept all 64 native token IDs on the warmup and all three measured requests. It is **not** a demonstrated optimization: adjacent baseline/candidate/baseline median hot-request times were 311.797/303.218/298.910 ms (2/3/3 measured requests), all token-identical. The second baseline was faster than the candidate; do not promote the opt-in patch. Native PyTorch on the same GPU and prompt measured 159.165 ms request, 0.312 ms `_prepare_inputs`, and 0.160 ms `sample_tokens`. Instrumentation and changing GPU/CPU load may affect exact times; these stage numbers are diagnostic, not additive request-time accounting.

An isolated Jittor CUDA metadata-copy test, using persistent CPU and GPU int32 buffers with 1000 ordered writes per round and a final device sync, found `_copy_into` about 1.59 microseconds per call at 1--256 elements and direct `_write_inplace` about 1.00 microseconds; both passed final-value checks over eight rounds. At 4096 elements they took about 1.95 and 1.34 microseconds. The sub-microsecond isolated saving cannot explain the roughly 1.2 ms per-step `_prepare_inputs` gap by itself. The cProfile attribution of 0.892 s to 1536 `_copy_into` calls across 128 profiled steps evidently includes in-model graph/dependency work and/or profiling effects, not intrinsic copy-call cost. A graph-aware stage trace is needed before changing this low-level copy path. The isolated script is in `_state/vllm-compare-20261013/bench_metadata_copy_20261015.py`.

## Experimental callback-based output fetch (2026-10-15)

An opt-in `JITTOR_VLLM_EXPERIMENTAL_LEGACY_ASYNC_FETCH=1` patch replaces the legacy vLLM output wrapper after CUDA Graph capture. For simple one-token/no-logprobs/no-routed outputs it submits `jt.fetch` into a callback-owned NumPy buffer, lets the lazy graph submit without a global blocking sync, and waits for that buffer only when the scheduler actually consumes token IDs. Unsupported shapes fall back to the original wrapper. H2D batching remains off, and the candidate is **default-off** pending longer stress and more models. Five targeted unit tests pass; correctness so far is specific to the real-model cases below.

On RTX 4090 GPU 0, Qwen2.5-0.5B-Instruct FP16, TP1/batch1, 4096-token `math` input + 64 greedy output, split-16 decode and strong graph alias, the candidate took 202.146 ms median over two measured requests versus a prior same-GPU Jittor baseline of 298.910 ms and native PyTorch's 159.165 ms. All 64 generated token IDs matched native in both candidate requests; median decode ITL was 2.488 ms candidate versus 4.112 ms baseline and 1.955 ms native. The candidate reaches about 78.7% of native output throughput for this workload, up from about 53.3%. These runs were adjacent but not a repeated interleaved A/B/A, so their magnitude is preliminary.

On GPU 2, the same model at 512+256 returned all 256 native token IDs in each of three candidate requests. Jittor candidate median request time was 672.656 ms and native PyTorch 529.442 ms (about 78.7% native throughput). Jittor workers exited gracefully. The native generation completed but its worker missed vLLM's five-second default shutdown grace and received SIGTERM, so the native JSON is marked failed for lifecycle despite valid generated outputs; a rerun with a longer shutdown grace is needed before treating that leg as a fully clean benchmark.

On GPU 4, the candidate and native PyTorch each completed a batch-shape switch 1→4→1 with two measured requests per stage, 128+64 `math`, and 64-token outputs **exactly matching at every corresponding prompt and request**; both worker sets exited cleanly. Median batch times (Jittor/native) were 203.864/127.092 ms at the first batch 1, 188.579/149.292 ms at batch 4, and 172.977/139.749 ms after returning to batch 1. Throughput ratios were 62.3%, 79.2%, and 80.8%. The first stage is noticeably slower than the return stage even in a hot engine, so these two-repetition stage medians must not be read as a stable independent batch-1 estimate. The test establishes this shape-switch correctness sample, not production stability or a 100-request soak.

## Chunked prefill beyond 8192 tokens (2026-10-15)

Qwen3-0.6B FP16 TP1/batch1 with a 16384-token `math` input and 64-token greedy output exposed a separate long-context failure. With the direct full-prefill FA2 option and split-32 decode, Jittor failed on the second 8192-token prefill chunk: `paged_attention.py` fell back to dense causal scores/mask when Q length was 8192 and KV length was 16384. The lazy graph attempted an `int32[8192,16384]` mask and then a 512-MiB float32 allocation, causing OOM. This is not evidence that FA2 was absent for the first chunk or that the model lacks 16K context.

### Batch-2 long-context regression and fixed-batch experiment

The first Qwen3-0.6B FP16 batch-2 16384+64 real-model run exposed two separate slow paths. The equal-length batched prefill entered the dense-score/mask branch even with the chunked-FA2 flag. Routing it through FA2 made both 64-token outputs native-exact and cut Jittor measured request time from **4.431 s** (one request sample) to **3.311–3.332 s** (three requests). Native was **1.172 s** in its first matching request sample. A profile of the revised prefill path still found **2.083 s** across 1680 calls to Jittor's old `paged_attention_decode` kernel: unlike batch-1, batch-2 Graph decode had not selected the previously optimized fused-cache split-decode path.

A **default-off, fixed-batch-only** `JITTOR_VLLM_EXPERIMENTAL_FIXED_BATCH_FUSED_DECODE=2` route now accepts capture metadata only when both batch-2 slots are full one-token decode requests and invokes the existing cache-write plus split-32 attention. It is not a dynamic-batch production path: a padded/smaller request replay still needs separate validation. With this flag, three measured Jittor requests took **1.532/1.503/1.508 s**, all six 64-token outputs were native-exact, and workers exited cleanly. The native reference was **1.172 s**, so the candidate reaches about **78% native output throughput** for this shape. The two TTFTs in Jittor were approximately **0.383/0.993 s**, versus native **0.371/0.737 s**; the second prefill remains slower.

The fixed-batch Jittor device profile (profiled request **1.567 s**) showed **1.402 s GPU busy**, including about **471 ms** FA2 prefill and **309 ms** split-decode partials. The matching native profile (request **1.163 s**) showed **1.152 s GPU busy**, including about **477 ms** FA2 prefill and **293+7 ms** decode/merge. Thus the main kernels are now similar, but Jittor still has roughly **250 ms** extra device work not yet fully attributed and about **150 ms** more request span beyond GPU-busy time. Extra Jittor slice/transpose/cache-gather kernels are plausible contributors, not an established complete explanation. These profiled figures are diagnostic, not replacements for unprofiled throughput. A subsequent batched FA2 call and a separate direct-fresh-Q/K/V full-prefill candidate each returned exact outputs but held request time near **1.50–1.52 s**; the direct-fresh-Q/K/V candidate was removed. The batched FA2 path remains under the default-off chunked flag and passed a separate NumPy causal reference unit test for two full 32-token requests.

An adjacent three-request native/Jittor repeat on GPU 0 with the same batch-2 16384+64 shape reported **1.15551/1.52314 s** median batch time; all six Jittor 64-token outputs exactly matched native and both engines shut down gracefully. This repeat yields about **75.9%** native output throughput, versus about 78% using the earlier one-request native reference. The fixed-batch fused route remains default-off and is not yet validated for request admission/retirement or padded graph replay.

### H2D batching lifetime regression recheck (2026-10-15)

The unsafe `JITTOR_VLLM_EXPERIMENTAL_BATCH_H2D_SYNC=1` route remains **default-off**. On CUDA GPU 3, Qwen3-0.6B FP16 V2, TP1/batch1, 512 input + 256 output, the first diagnostic stress leg completed 100/100 requests with 256 identical output IDs and graceful worker shutdown. This did **not** establish a fix: a second 200-request leg failed at measured request 19 with a worker SIGSEGV; a third failed at request 73 with `JT_OP_LIFETIME_INVALID`, and a fourth failed at request 1 with another SIGSEGV. The failed legs have no valid throughput result. The program's failure phase was recorded in each JSON, and the third leg's full diagnostic log is `qwen3-512x256-h2d-deathsite-gpu3-r200b-20261015.log` under `_state/vllm-compare-20261013`.

The diagnostic registry previously recorded `note_op_destroyed`'s own return address, which always named `Op::~Op` and could not locate the release. That default-off instrumentation now records the destructor's caller and resolves it with `dladdr` only on failure. The third leg identified a destroyed **`GetitemOp`** still referenced in `count_fuse` (`last_dead_id=3120177`, deleting destructor in Jittor core). A GDB-attached fifth leg failed with SIGSEGV inside `build_exec_plan`, called from `Executor::run_sync`/`sync_all`; this is the same general raw-graph-planning lifetime area, although the exact pointer's identity at this SIGSEGV is not proven. `Executor::run_sync` currently takes `batch_hold` **after** `build_exec_plan`, leaving a window in which the planner's raw `Op*`/`Var*` can be released. Concurrent graph mutation is a plausible mechanism, not yet established as the sole cause. Keep H2D off until a lifetime fix survives repeated long-token stress and a no-H2D control.

Two narrower hypotheses were tested and rejected, rather than enabled: `JT_ASYNC_EXECUTION=0` was confirmed active in the log but still SIGSEGVed at measured request 89; a temporary default-off `JT_EXPERIMENTAL_PLAN_ROOT_HOLD=1` retained all sync roots before `build_exec_plan` but SIGSEGVed at request 5. The root-hold flag and its flag-policy entry were reverted exactly after this failure. Holding only requested roots is therefore insufficient; the next lifetime candidate must account for intermediate graph nodes and concurrent mutation during planning, and requires an isolated correctness/stress gate before any timing claim.

A further default-off `JT_EXPERIMENTAL_PLAN_GRAPH_HOLD=1` candidate locked the graph while collecting a batch and held every visited Var/op output through compilation, releasing the lock before fusion. It still SIGSEGVed at measured request 24 in the same 512+256 stress, after an expensive cold Jittor rebuild and successful CUDA Graph capture. This does not rule out every possible planner lifetime fix, but it rejects that precise lock/hold placement. `exec_plan.cc`, `exec_plan.h`, `executor.cc`, and `flag_policy.py` were all restored byte-for-byte to their pre-candidate SHA-256 versions; H2D batching stays default-off. No candidate performance claim is made.

### Official FA2 paged-KV append/decode feasibility (isolated, 2026-10-16)

A GPU2 isolated probe tested upstream FA2 `fwd_kvcache` with Qwen2.5-like FP16 GQA (14 Q heads, two KV heads, D64), 512 existing tokens, one appended token and 256-token pages. For **independent contiguous** K/V page arrays, the output matched an FP32 NumPy reference within **4.6e-6**. By default the new KV token was *not* visible in the original Jittor Vars: the torch-extension shim clones unmarked inputs, so FA2's in-place cache update landed in a temporary. Marking both page arrays with the existing per-tensor mutable flag made the new K/V entries exact; the diagnostic per-tensor borrow flag did likewise. This confirms a boundary ownership issue, not absent FA2 arithmetic support.

The actual vLLM layout is **interleaved** `[blocks, 2, page, kv_heads, dim]`. A separate read-only control confirmed that `cache[:,0]` and `cache[:,1]` yield the expected initial values; the fault appears only at the extension boundary. The Torch shim's `Tensor::stride(d)` in `compat/shim/cpp_extension/include/torch/extension.h` computes a *contiguous* stride from the shape, whereas these sliced storage views are not contiguous. This supplies a concrete mechanism for the invalid extension view. Passing these views directly with a borrowed marker increased reference error to about **0.0113**; new cache entries were absent, and previously initialized view entries differed by as much as **0.408** after the call. A further diagnostic read of a cloned view also migrated the cache alias to CPU, causing FA2's CUDA-device check to reject it; that run produced no arithmetic result. No production FA2 decode adapter was changed or enabled, and no end-to-end speed claim follows. Probe/launcher: `_state/vllm-compare-20261013/probe_fa2_paged_kvcache_20261016.{py,sh}` and `probe_jittor_device_20261016.py`. A safe solution needs an explicitly mutable, stable GPU cache borrowing contract **and** a compatible page-major K/V layout or stride-correct interleaved wrapper, followed by multi-token cache-persistence tests before performance A/B.

The follow-up changed the tracked shim's `Tensor::stride(d)` to return Jittor Var's actual `storage_stride(d)` through a new out-of-line `vh_storage_stride` bridge; no serving adapter or decode selection changed. With that change and the *diagnostic-only* per-tensor borrow marker, the **interleaved** layout passed two consecutive FA2 paged-KV append+decode steps: output maximum absolute errors **4.58e-6/4.82e-6** against FP32 references, both newly written K/V tokens exact in the original cache, and earlier cache contents unchanged. A new C++ extension regression test, `compat/tests/torch/test_cpp_extension_storage_stride.py`, checks the physical strides of both interleaved views and a dense control; it passed **1/1** under the Jittor CUDA shim. A real Qwen2.5-0.5B FP16 TP1/V2 16384+64 regression on GPU2 then completed two hot requests in **420.319/419.952 ms**, both **64/64 native-oracle token exact**, with graceful worker shutdown. That is a regression check of the existing decode path, not a measured FA2-decode speedup. JSON: `_state/vllm-compare-20261013/qwen25-05-v2fetch-off-stride-smoke-16k64-gpu2-20261016.json`. ### Official FA2 paged-decode serving probe (2026-10-16)

The pinned upstream FA2 v2.8.3 checks `page_block_size % 256 == 0` in `csrc/flash_attn/flash_api.cpp`; the vLLM 0.24 cache default is **16 tokens/page**. An actual Jittor-shim `fwd_kvcache` call on page 16 returned `Paged KV cache block size must be divisible by 256`, while the same call on page 256 produced a finite `[1,1,14,64]` output. This is a hard layout incompatibility for a direct swap on the current default vLLM cache. Probe: `_state/vllm-compare-20261013/probe_fa2_real_page_20261016.py`, run via `probe_fa2_paged_kvcache_20261016.sh` with `FA2_TEST_PAGE=16` or `256`.

It uses official FA2 `fwd_kvcache` with interleaved mutable-borrow KV views, appends current K/V, and reads `seq_lens - 1` as the pre-append length. It explicitly requires CUDA FP16, batch=1, page divisible by 256 and head dimension 64/128; Graph capture also requires a separate `JITTOR_VLLM_EXPERIMENTAL_FA2_PAGE_GRAPH=1` probe flag and `JT_AUTO_GRAPH_REPLAY=0`.
