## Protocol and environment

All numbers below are offline `vllm.LLM.generate` or `engine.step` wall times, not HTTP latency or isolated GPU kernel time. A fresh process loads one backend, warms one request, then repeats identical deterministic requests. Engine startup, weight loading, graph capture/JIT warmup and shutdown are excluded from steady-state timing. The oracle process asserts it is real PyTorch rather than the shim; both sides use the same local model weights, dtype, token IDs, visible physical devices, vLLM 0.24.0, greedy temperature zero, disabled prefix cache, and eager mode on NPU / decode-only CUDA Graph on CUDA. Raw JSON/logs and launch scripts are unversioned under `$JITTOR_LAB_ROOT/_state/vllm-compare-20261013/` on CUDA and the corresponding NPU `_state/` directory.

CUDA was measured sequentially on one RTX 4090, physical GPU 2. Each model used FP16, TP1, one batch, 128 input + 64 output tokens, one warmup and three measured requests. Median full-request time is reported below. Each of the three measured outputs for each model matched the corresponding PyTorch output for all 64 token IDs. GPU 6 became occupied by another user's renderer during a separate exploratory A/B and those timing samples are excluded.

| CUDA model | Jittor request | PyTorch request | Jittor/PyTorch output throughput |
| --- | ---: | ---: | ---: |
| Qwen3-0.6B | 221.0 ms | 155.6 ms | 70.4% |
| Qwen2.5-0.5B-Instruct, default V1 | 259.5 ms | 126.7 ms | 48.8% |
| SmolLM2-360M-Instruct | 189.3 ms | 124.8 ms | 65.9% |

The model-runner control matters. vLLM 0.24's default V2 architecture list contains `Qwen3ForCausalLM`, but not `Qwen2ForCausalLM`; the earlier assumption that Qwen2 was already on V2 was wrong. Forcing Qwen3 to V1 changed Jittor's same-protocol median from 221.0 to 280.9 ms while PyTorch stayed about 156 ms. Forcing Qwen2 to V2 instead reduced Jittor from 259.5 to 201.1–201.7 ms (about 22% lower request latency), with PyTorch V2 at 129.2 ms. All measured 64-token greedy outputs remained exact. The V2 Qwen2 candidate also worked without the experimental strong graph alias; that alias is needed by the V1 Graph path, not by this V2 probe.

The experimental Qwen2 V2 path was also checked with fixed batch=4 (128+16, TP1), Jittor 80.5 ms vs PyTorch 41.5 ms; all eight measured sequences matched. TP2 batch=1 (128+16) on the same two physical GPUs gave Jittor 63.3 ms vs PyTorch 42.0 ms, with both measured sequences exact and clean shutdown. A single-engine TP1 graph-shape sequence `1→4→1→4` completed without illegal address, and all 20 measured sequences matched PyTorch. This is bounded evidence, not proof of long-running graph-lifetime stability or support for every Qwen2 feature. Because Qwen2 is not in vLLM's default V2 support list, this path remains opt-in and model-specific pending broader sampling, logprobs, request turnover and long-run graph-switch tests.

CUDA four-card coverage used Qwen3-0.6B instead of Qwen2.5-0.5B because the latter's 14 attention heads are not divisible by TP4 and vLLM rejects it before engine startup. On the same physical RTX 4090 GPUs 2–5, FP16, TP4, batch=1, 128+16, decode-only Graph, one warmup and two measured requests, Jittor's median was 68.798 ms (232.6 output tok/s) versus PyTorch's 44.165 ms (362.3 tok/s), or 64.2% relative throughput. Both 16-token outputs matched exactly; all four Jittor workers exited with code 0 and no retained shared-memory blocks. The first Jittor TP4 starts spent minutes compiling fresh per-rank Jittor/NCCL caches and were excluded; copying compiled cache directories to new paths proved invalid (`jit_utils` rebuild-on-import). Fresh serial per-rank cache preparation allowed the final complete run. This is one fixed-shape, short-output success, not proof of dynamic four-card stability.

The same TP4 Qwen3 setup was extended to 128+64, again one warmup and two measured requests. Jittor's median was 214.726 ms (298.1 output tok/s), PyTorch's 137.936 ms (464.0 output tok/s), or 64.2% relative throughput. Both 64-token outputs matched exactly (128/128 generated IDs across measured requests), and Jittor shutdown passed. Four-card fixed-batch long decoding is therefore correct in this bounded test, but remains substantially slower than PyTorch.

The adapter now exposes `JITTOR_VLLM_EXPERIMENTAL_QWEN2_V2=1`, which transactionally adds only `Qwen2ForCausalLM` to vLLM's V2 architecture list. It does not force V2 globally or affect other models when absent. With that switch alone (without the global vLLM override or strong graph alias), Jittor's TP1 128+64 median was 200.6 ms and all three 64-token sequences matched the independent PyTorch V2 run. The same switch passed a TP2 single-engine `1→4→1→4` sequence with clean worker shutdown and all 20 measured sequences identical to PyTorch. The focused policy contract passed three unit tests: disabled behavior, model specificity/rollback, and fail-closed behavior if the upstream policy changes.

Longer TP2 decoding was then checked with the scoped switch, physical GPUs 2 and 3, batch=1, 128 input + 64 output, one warmup and two measured requests. Jittor took 192.880 ms median (331.8 output tok/s), native PyTorch V2 124.885 ms (512.5 output tok/s), or 64.7% relative throughput. Both 64-token outputs were exactly identical to the native run; both workers exited cleanly. A different science prompt at TP1, 128+64, produced 199.601 ms for Jittor and 128.606 ms for PyTorch (64.4% relative throughput), also with both 64-token outputs exact. These samples are separate processes rather than a randomized long-duration A/B, so the ratio is indicative rather than a confidence interval.

A code prompt at TP1, 32+64, produced 192.416/130.324 ms Jittor/PyTorch, with two more 64-token sequences exact (67.7% relative throughput). Thus the V2 improvement is not restricted to the original arithmetic prompt. A non-synchronising stage trace on Qwen2.5 V2, 128+16, found median `sample_tokens` 1.944/0.395 ms and `AsyncOutput.__init__` 1.399/0.056 ms Jittor/PyTorch. These host spans are nested and must **not** be added to request latency. Jittor's sample cProfile showed 51 native `Var.numpy()` calls totalling 50 ms over 48 traced steps, consistent with synchronous output readback. Device profiling of a 16-token request found Jittor/PyTorch GPU busy 30.03/31.79 ms, but first-to-last CUDA activity span 71.30/44.49 ms. The gap therefore cannot be attributed to slower model arithmetic alone: Jittor's wider GPU idle gaps and synchronous readback/host scheduling are material. Device profiling perturbs latency and these numbers are diagnostic, not a fresh throughput benchmark.

Longer context worsened the ratio: Qwen2.5 V2 TP1 batch=1, 512 input + 64 output on physical GPU 2 took 225.644 ms Jittor versus 129.804 ms PyTorch (57.5% relative throughput), with both 64-token measured sequences exactly identical. The median decode ITL was 3.250/1.894 ms; the 512-token Jittor path therefore scales worse than the earlier 128-token path, even though first-token time stayed near 19 ms Jittor and 9 ms PyTorch in these runs.

Subsequent device profiling of a separate 16-token request narrows the long-context regression. At KV≈128, Jittor's fused `reshape_cache_paged_attention_decode` took 2.717 ms over 360 launches, while PyTorch's split-K attention plus combine took 2.527+1.069=3.596 ms. At KV≈512, the corresponding Jittor kernel rose to 8.912 ms, but PyTorch's two kernels stayed near 2.595+1.132=3.727 ms. Jittor GPU busy time rose from 30.030 to 40.436 ms, compared with PyTorch 31.789 to 33.873 ms. These are profiler-perturbed device totals, not request latency, but they show an additional long-KV GPU-kernel bottleneck alongside the previously observed host scheduling gaps. Disabling the fused Jittor path with the existing `JITTOR_VLLM_FUSED_CACHE_DECODE=0` switch did not improve the complete 512+64 request: 227.316 ms versus the nearby fused 225.644 ms; both retained exact 64-token outputs.

An opt-in CUDA fused-decode occupancy experiment now accepts `JITTOR_VLLM_EXPERIMENTAL_FUSED_DECODE_WARPS=8|16|32` (default 8). On Qwen2.5 V2 TP1, 512+64, an interleaved 16→8→16→8 sequence produced medians 215.501→223.200→207.335→223.667 ms. A subsequent 32-warp run gave 200.288 ms, and a 128+64 32→8 pair gave 196.683→203.916 ms. Every completed candidate's two 64-token outputs matched the native oracle exactly. The focused CUDA numerical test passed for FP16 and BF16 at all three warp counts, checking both KV-cache writes and attention output against NumPy. The qh host load varied markedly (up to about 224) during these runs, so these are exploratory per-process A/B measurements rather than confidence intervals; the default remains 8 pending wider model/batch regression tests.

Device profiling confirms a real kernel gain: at KV≈512 over 360 launches, Jittor's fused attention fell from 8.912 ms at 8 warps to 3.434 ms at 32 warps. Jittor GPU busy time fell from 40.436 to 34.959 ms, while the first-to-last kernel span fell only from 75.308 to 72.534 ms under variable host load. Native PyTorch's corresponding attention+combine totaled 3.727 ms, GPU busy time was 33.873 ms, and kernel span 44.308 ms. Thus the 32-warp variant nearly closes the device-attention gap for this Qwen2.5 long-context case, but the much larger idle/host-scheduling gap remains; the profiler run's complete 16-token request median barely changed (72.681→71.895 ms) and should not be conflated with the non-profiled 64-token A/B.

On a second CUDA model, Qwen3-0.6B TP1 128+64, the adjacent 32→8-warp request medians were 217.903→219.819 ms (less than 1%). The 32-warp run's two 64-token outputs matched the independent PyTorch oracle. Since Qwen3's original 8-warp device attention was already close to native split-K attention at this shorter context, the Qwen2.5 long-KV gain must not be generalized into a blanket multi-model speedup.

A separate output-thread readback prototype attempted to `clone` the sampled token, submit it without a device-wide wait, then defer `.numpy()` until `AsyncOutput.get_output`. The first Qwen2.5 V2 warmup crashed its worker with a native segfault before any measured request, so it failed correctness/lifetime acceptance. Repository allocator guidance notes that Jittor `clone` can establish a storage alias; thus the prototype's assumption of an independent snapshot was unsound, although the log does not establish that aliasing was the sole cause of the crash. The prototype was fully reverted; `buffers.py` was restored to its pre-experiment SHA256 `e745416f417dc4f357c39ab85b29d5b695d589a88e6218b2f52509dd9fbea913`. No throughput number or speedup is claimed. The failed run remains in the unversioned state directory under tag `defer-d2h-128a` for future graph/output-thread lifetime analysis.

After reverting, the normal Qwen2.5 V2 TP1 128+16 path completed two measured requests, matched the 16-token PyTorch oracle twice, and shut down cleanly (`postrevert-smoke`). Its 62.013 ms median is a recovery check rather than an A/B comparison under the same host load.

The follow-up readback candidate uses Jittor's existing `fetch` side-stream transfer instead of moving a Jittor Var onto the output thread. A callback copies the fetched host bytes into a NumPy-owned array and signals a Python event; the output thread waits only on that event. It is opt-in via `JITTOR_VLLM_EXPERIMENTAL_ASYNC_FETCH=1` and applies only to the already-specialized stable decode path with static sampled-token counts, no logprobs, and no NaN output. Prefill and general sampling retain the original path. A small allocator-pressure probe performed 10/10 correct tiny fetches in each of CPU/CUDA × default/no-SFRL/NFEF configurations, but this is not a long-running allocator proof; a focused fake-callback test also verified that the returned NumPy bytes are copied before `FetchOp` frees its staging allocation.

Qwen2.5 V2 TP1 128+16 then gave 57.542 ms with async fetch versus 62.578 ms adjacent default; both measured candidate outputs matched all 16 PyTorch token IDs and shutdown passed. For 128+64, async→default→async medians were 179.654→199.305→181.714 ms, or about 9% lower latency in both candidate rounds relative to the intervening default. All four candidate 64-token outputs were exact and the workers exited cleanly. These per-process, two-request samples still span variable shared-host load and are not confidence intervals. A single-engine shape sequence 1→4→1→4 completed cleanly and matched the PyTorch oracle at all 320 generated IDs across eight measured requests; its first batch=1 measurement included cold-state cost and is excluded from any performance claim.

The second-model check was Qwen3-0.6B TP1 128+64: async fetch 202.105 ms versus adjacent default 224.691 ms, with both candidate 64-token outputs exactly matching PyTorch and clean shutdown. Qwen2.5 V2 TP2 on physical GPUs 2 and 3, also 128+64, gave 177.393 ms versus adjacent default 208.958 ms, with two more exact 64-token outputs and clean two-worker shutdown. An earlier TP2 default under a separate shared-host load was 192.880 ms, so the 208.958 ms adjacent sample is not a stable universal baseline; the TP2 speedup magnitude remains provisional. Unit tests cover disabled behavior, prompt-logprob synchronous fallback, callback-owned host bytes, transactional rollback, and callback failure waking the waiter (3/3 focused tests). A further ten-measurement Qwen2.5 TP1 run (after one warmup) matched the 64-token PyTorch oracle in all 640 generated IDs, shut down cleanly, and had median 178.243 ms. This is stronger repeated-request evidence, but not a long-running service test.

Qwen3-0.6B TP4 on physical GPUs 0, 1, 2, and 4 also completed the 128+64 async-fetch path: 201.707 ms median over two measured requests, both exact at all 64 output IDs against the independent PyTorch TP4 oracle, and all four workers exited cleanly. Fresh per-rank compilation made engine initialization take 319.59 s; that startup cost is excluded from request timing. This is a correctness/lifecycle extension, **not** a strict TP4 performance A/B against the older oracle measured on GPUs 2–5. The CUDA flag remains opt-in pending broader feature and long-service coverage.

The third CUDA model was SmolLM2-360M-Instruct TP1, 128+64 on physical GPU 2. Async→default→async→native two-request medians were 179.042→199.333→170.161→128.043 ms; both async rounds matched the independent native PyTorch oracle for every one of their 64 generated IDs and shut down cleanly. This extends the positive result beyond Qwen architectures. Candidate latency was 10.2–14.6% below the intervening default, with 71.5–75.2% native-relative output throughput, but all per-process medians remain susceptible to shared-host variation.

The combined Qwen2.5 V2 TP1 long-context experiment (512+64) enabled both 32-warp fused decode and async fetch. In candidate→default→native→candidate order on the same physical GPU 2, the four two-request medians were 178.596→225.656→130.167→196.776 ms. Each candidate's two 64-ID outputs exactly matched the native oracle and all processes shut down cleanly. Relative to the adjacent default, candidate latency was 12.8–20.9% lower; its native-relative output throughput was 66.2–72.9%. The 18.2 ms difference between candidate repeats on this shared host makes this an exploratory A/B, not a stable confidence interval or 90%-of-native result.

After async fetch, a non-synchronizing 128+16 stage trace gave Jittor/native request wall 56.609/43.588 ms. Median per-step CPU spans were `execute_model` 1.718/0.466 ms, `prepare_inputs` 0.395/0.235 ms, `prepare_attn` 0.130/0.044 ms, `sample_tokens` 0.695/0.399 ms, and `AsyncOutput.__init__` 0.131/0.056 ms. Stages nest and GPU work overlaps them, so these differences cannot be summed. A separate device-profiler run reported Jittor/native GPU busy 30.078/31.779 ms but first-to-last kernel span 64.332/46.250 ms, with profiler-perturbed request wall 65.470/47.757 ms. The remaining gap is therefore dominated by GPU idle/host publication intervals rather than heavier model kernels for this short-context case. cProfile of the Jittor candidate found 79 `copy_to_uva` calls across 34 traced steps, including 79 `cuda.synchronize()` calls totaling 77 ms of nested CPU wait. This identifies a candidate cause, **not** an automatically removable 77 ms: the sync protects temporary host-source lifetime and prior standalone `UVA_COPY_SYNC=0` had only a noisy ~1% request gain. When `JITTOR_VLLM_UVA_COPY_SYNC=0` was combined with async fetch for Qwen2.5 128+64, the first warmup timed out waiting 20 seconds for the token-fetch callback in `WorkerAsyncOutputCopy`. The failed, explicitly opted-in test was stopped and all its processes exited. It has no performance result and cannot be enabled as an optimization. The adapter now rejects this specific unsafe switch combination before running; four focused tests cover the guard and the safe path. A post-guard Qwen2.5 128+16 real-model smoke completed at 56.536 ms median, twice exact at all 16 IDs against the native oracle, with clean shutdown.

A second H2D experiment replaced the full-device sync with `jt.sync([result])`, preserving a blocking wait for the copy's target Var. With async token fetch enabled, its first Qwen2.5 128+64 warmup likewise timed out after 20 seconds in `WorkerAsyncOutputCopy`. This suggests that target-Var completion alone does not preserve the current lazy-graph/fetch publication sequence; it does **not** prove a specific allocator bug. The job was stopped, its worker exited, and the target-sync code and unit test were fully reverted. The safe full-device sync remains the default and required choice for this candidate.

Sampling cProfile of the async-fetch candidate (Qwen2.5 128+16, 32 traced steps including warmup) put about 38 ms of nested CPU time in `sample_tokens`, including 19 ms in `sample`, 12 ms in `postprocess_sampled`/`post_update`, and 5 ms in async output construction. To test whether a plain-greedy FP32 logits copy and modifier checks were material, a CUDA-only opt-in branch directly ran argmax on the original logits only when there were no logprobs, NaN reporting, penalties, logit bias, bad words, min-p, top-k, or top-p. On Qwen2.5 V2 TP1 128+64, the candidate and adjacent original async-fetch path took 179.223 and 178.366 ms; two 64-ID outputs matched each other and the previously validated native oracle. With no measurable gain, the branch was fully reverted and is not retained as an optimization.

A second sampling experiment replaced the TP1/batch-1, one-token `post_update` Triton bridge with a Jittor `jt.code` CUDA kernel and explicit nonblocking publication of its existing state outputs. cProfile confirmed that `post_update` CPU time fell from about 12 to 2 ms over 32 traced steps, and the Triton bridge calls disappeared. However, Qwen2.5 128+16 request wall was 57.467 ms versus the recent 56.536 ms safe async-fetch path; a 128+64 run was 179.056 ms versus the adjacent safe path's 178.366 ms. Both candidate runs were token-exact and shut down cleanly, but end-to-end improvement was absent. The experimental native kernel was fully reverted; this is direct evidence that reducing an isolated CPU stage is insufficient when publication and GPU work overlap differently.

Expanded `copy_to_uva` cProfile callers showed that, across the same 34 traced steps, 49 calls came through `UvaBackedTensor`: 34 from `BlockTables.apply_staged_writes`, four from `RequestState.apply_staged_writes`, and the rest from sampling metadata initialization/updates. A content-keyed cache of `prompt_len`/`prefill_len` reduced total calls only from 79 to 77, and Qwen2.5 128+64 async-fetch request time was 189.253 ms versus 179.356 ms adjacent baseline; both outputs were exact. That cache and its temporary test were removed. A more targeted, CUDA-only cache for the host-written `BlockTables.num_blocks` array then removed the regular block-count publication, but its first Qwen2.5 128+64 warmup timed out after 20 seconds waiting for the asynchronous token-fetch callback. The test was stopped and its worker exited; the cache and its temporary test were removed. The observation is consistent with the current full-device sync also being part of the fetch/graph publication sequence, but it does not by itself identify the precise CUDA event dependency. No unsynchronized metadata cache is enabled by default.

`FetchOp` source inspection showed a conditional pending-fetch publication path based on input readiness. Two CUDA-only probes attempted to make that dependency explicit before registering fetch: a nonblocking `jt.sync([sampled_token_ids], False)` and a blocking `jt.sync([sampled_token_ids])`. The nonblocking pre-submit alone remained correct at 56.493 ms for Qwen2.5 128+16, but **both** variants timed out waiting for the fetch callback on the first warmup when combined with `num_blocks` caching. The timeout jobs and workers exited after controlled termination. These negative results do not prove that the FetchOp readiness test alone caused the stall; a later event-queue or cross-stream dependency may still be missing. Both experimental branches were fully removed. The supported async-fetch candidate retains the existing synchronized metadata path and the startup guard against `JITTOR_VLLM_UVA_COPY_SYNC=0`.

A separate CUDA targeted-sync trial replaced one device-wide sync with a target-Var sync. On the unoccupied GPU, Qwen3 A/B/A medians were 237.8/223.0/221.0 ms and Qwen2.5 medians were 257.7/259.5/254.3 ms; the effect was inconsistent or small relative to host variation. Its code was fully reverted, preserving the source file's original SHA256. It is not an accepted optimization.

The existing opt-in `JITTOR_TORCH_DIRECT_HOST_COPY=1` was retested on the new Qwen2 V2 path: 198.681 ms candidate versus 196.629 ms adjacent default, both 128+64 with two measured requests. It did not help in this configuration and was not enabled by the policy.

An experimental pure-greedy shortcut skipped the FP32 logits copy and inactive sampling-parameter kernels when temperature/top-k/top-p/min-p and all modifiers were neutral. It really executed (sample cProfile dropped `apply_sampling_params` from 14 ms/48 traced steps to zero), and its two 64-token requests exactly matched PyTorch. Yet request latency was 197.044 ms versus the adjacent 196.629 ms default. The output readback instead occupied more of the host span, so no end-to-end gain was established. The shortcut was fully reverted and is not part of the adapter.

`JITTOR_VLLM_UVA_COPY_SYNC=0` was also tried with Qwen2 V2; it gave 194.331 ms versus the nearby 196.629 ms default and retained both exact 64-token outputs. A ~1% two-request gain does not justify weakening the publication/lifetime guarantee for mutable host metadata; the switch was not promoted and the default remains synchronised.

The later metadata-publication experiments did **not** produce a safe optimization. CProfile attributed 34 of 79 `copy_to_uva` calls in a 34-step trace to `BlockTables.apply_staged_writes` refreshing `num_blocks`. Caching that buffer, while retaining the opt-in async output fetch, made the fetch callback time out during warmup. Explicit nonblocking or blocking `jt.sync([sampled_token_ids])` before registration did not resolve the timeout. A synthetic `jt.fetch` probe showed that `jt.sync_all(False)` could leave its Python callback pending, while `jt.sync_all(True)` delivered it; source inspection found that the Jittor executor flushes the callback event queue on its blocking device-sync path. Calling `jt.sync_all(True)` from vLLM's output thread temporarily made a 128+16 request succeed, but a 128+64 warmup then segfaulted the native worker. The output-thread sync, `num_blocks` cache, and their temporary tests were all reverted; they must not be enabled or treated as an accepted acceleration. This is a graph/fetch publication and thread-ownership issue, not evidence that the metadata cache is semantically safe.

After the rollback, the remaining opt-in async-fetch path passed four focused unit tests and a fresh same-GPU Qwen2.5 V2 128+64 check: Jittor 177.138 ms versus native PyTorch 130.684 ms median, or 73.8% relative output throughput. Both measured 64-token sequences matched exactly and both processes shut down cleanly. A 128+16 check was likewise exact at 56.813/40.344 ms. These are recovery and bounded performance checks, not proof of production stability or a 90% result.

A subsequent same-GPU, long-context warp-count A/B held the async-fetch candidate fixed and changed only `JITTOR_VLLM_EXPERIMENTAL_FUSED_DECODE_WARPS`. The harness used FP16, TP1, batch=1, 512 input + 64 output tokens, one warmup and three measured requests for Qwen2.5-0.5B; process order was 16→32→16→32. Jittor medians were 185.977→179.985→187.572→177.090 ms; a fresh native PyTorch run was 129.798 ms. All 12 measured Jittor sequences matched the native oracle at all 64 generated IDs and all workers exited cleanly. The 32-warp option reduced Jittor latency by roughly 3–6% versus adjacent 16-warp runs, but still reached only 72.1–73.3% of native output throughput.

The same long-context experiment on Qwen3-0.6B used process order 8→32→8→32 and two measured requests per process. Jittor medians were 238.954→210.052→241.278→210.732 ms; fresh native PyTorch was 158.489 ms. All eight Jittor 64-token outputs matched native exactly; shutdown was clean. The 32-warp option reduced Jittor request latency by about 12% against adjacent 8-warp runs, raising native-relative throughput from about 66% to 75%, still short of the 90% target. The warp setting remains opt-in because these are two models at one long-context shape; short prompts, other batches, TP, and long-running graph shape changes have not been sufficiently characterized for a default policy.

TP2 Qwen3-0.6B on physical GPUs 2 and 3, 512+64, confirmed that 32 warps was not single-card-only: Jittor 222.028 ms at 8 warps versus 197.455 ms at 32 warps; native PyTorch was 140.614 ms. Both measured 64-token outputs matched native in both Jittor runs. Jittor workers exited cleanly; the native vLLM process completed and wrote its JSON, but its default five-second worker-exit grace then triggered SIGTERM. This does not affect the already recorded request times, but native shutdown is not marked clean for that run.

An additional **default-off** candidate, `JITTOR_VLLM_EXPERIMENTAL_BATCH_H2D_SYNC=1`, coalesces the host-metadata publication boundary only for one-request/one-token steady CUDA decode when async fetch is also enabled. Each mutable NumPy source is copied to owned bytes and retained in worker-thread-local storage until `prepare_inputs` finishes; a single blocking sync on that worker thread then publishes the batch and drains pending fetch callbacks. New or finished requests, dummy/profile runs, prefill, batches other than one, and the NPU path retain their prior behavior. Unlike the rejected output-thread sync experiment, this candidate never invokes Jittor core from the output thread. Six focused unit tests pass, including source ownership and boundary cleanup, but this is still a limited prototype rather than a production guarantee.

For Qwen3-0.6B TP1 512+64 with 32 warps held fixed, the H2D-batch candidate took 178.110 ms versus the earlier 32-warp-only 210.052/210.732 ms and a same-GPU native run of 158.489 ms, or 89.0% relative output throughput. All three candidate 64-token sequences were exact. A Qwen2.5 single-engine graph-shape sequence 1→4→1→4 also completed: all 20 measured sequences (320 generated IDs) matched a fresh native run, with clean shutdown. Its first batch-4 graph/JIT warmup took over a minute; this is excluded from steady latency. TP2 Qwen2.5 128+64 completed at 163.335 ms with both measured outputs exact against native and both Jittor workers clean. A diagnostic 128+16 `execute_model` cProfile with the candidate showed 79 `copy_to_uva` calls, 43 `cuda.synchronize` calls and 73 total core `sync_all` calls over the traced steps; the adjacent default had 79, 79 and 79 respectively. Core `sync_all` cumulative CPU time fell from 84 to 62 ms in this profiler-perturbed run, and profiled request medians were 75.084→64.205 ms. Two non-Qwen CUDA models extend the H2D-batch correctness check at TP1, 128+64. ### Qwen3-4B TP1 long-output correctness exception

A new same-version Qwen3-4B TP1/64 run on physical NPU 2 used the same prompt, BF16, eager mode, 512 MiB KV cache, vLLM 0.24.0 and CANN 9.0.1 as the previous short-output comparison. Later IDs also diverged, so this run is **not** in the exact-output table and cannot be called a correctness pass. Both sides were internally repeatable, and the same model's earlier TP2/64 run was exact against its TP2 native reference.

Separate `logprobs=5` runs localized the initial divergence: native TP1 reported ID 3783 at -1.494151 and ID 358 at -1.619151 (a 0.125 logprob lead), while Jittor TP1 reported both IDs at -1.557552 to six decimal places and its greedy tie-break selected 358. This is stronger evidence than a merely rounded tie in both implementations: the Jittor distribution collapsed a native 0.125 margin at this step. It does not yet identify which layer/operator caused the BF16 discrepancy. These logprob runs were not used for the throughput numbers.

The precision diagnostic switched **both** same-version Qwen3-4B TP1 launchers to FP16 for 64 output tokens. Jittor and native produced all 64 token IDs identically; that FP16 sequence also matched the native BF16 sequence. However, the warmed measured requests were 15.124947 s Jittor versus 4.740145 s native, only 31.3% relative throughput. The first fused run took 14.032674 s and was excluded. Avoiding an intermediate BF16 rounding is a plausible explanation for the changed greedy decision; a layer-level numerical A/B is still needed to prove the mechanism. The next probe found the Torch-shim module dispatcher intercepted vLLM's patched RMSNorm and used a split `unit-weight RMSNorm -> BF16 weight multiply` path. Snapshot hooks synchronize execution and **must not** be used as performance samples. The opt-in remains default-off pending long-output multi-model regression.

An initial no-FP32-prefill-policy probe (`JITTOR_VLLM_F32_FUSED_PREFILL=0`) did not reach any measured request: the alternative cuDNN SDPA bridge failed loading its cached shared object with undefined symbol `nvrtcGetCUBINSize`. `ldd` showed the bridge intentionally left CUDA/cuDNN/NVRTC symbols unresolved and its loader preloads cuDNN but not NVRTC; the matching CUDA 12.2 toolkit does contain `libnvrtc.so`. ## Qwen3 same-model recheck and bare-model control

A fresh CUDA Qwen3-0.6B TP1/batch-1 4090-GPU-2 A/B/A used vLLM 0.24.0, FP16, decode-only Graph size 1, identical 128-token math prompt, greedy 64 output tokens, one warmup and 11 measured requests per process. Order was Jittor async-fetch plus experimental input-H2D batching → native PyTorch → Jittor async-fetch-only control → Jittor candidate repeat. Median full-request times were **169.142 → 157.173 → 200.367 → 168.469 ms**. These correspond to **378.4 → 407.2 → 319.4 → 379.9 output tok/s** for the single request. Both candidate rounds were 15.6–15.9% lower latency than the intervening Jittor control and reached 92.9–93.3% native throughput; all 33 Jittor measured outputs matched the same native 64 token IDs exactly. Median TTFT was candidate 20.43/20.08 ms, native 11.69 ms, Jittor control 20.58 ms; median decode ITL was candidate 2.348/2.344 ms, native 2.296 ms, control 2.816 ms. This is strong same-model evidence for the input-H2D optimization, not an effect of switching to Qwen2.5. It remains an opt-in prototype and this one-GPU one-shape experiment is not a general 90%-of-PyTorch claim.

The no-vLLM control used the **same Qwen3-0.6B weights** via Transformers directly, without vLLM scheduler, paged KV, sampling, or CUDA Graph. It teacher-forced 128 synthetic input IDs followed by the same preallocated token ID 733 for 64 decode steps; FP16, TP1, batch 1, two warmups, five measured sequences, per-sequence device sync. The Jittor Torch shim required its existing RoPE repair flag; no backend fallback occurred. A first `sdpa` attempt failed before timing because the cuDNN bridge lacked the matching `nvrtcGetCUBINSize` symbol. Preloading the host's matching CUDA-12.2 `libnvrtc.so` resolved the loader issue without changing the model kernels. With SDPA, Jittor's prefill/decode-per-token medians were **20.804/16.609 ms** versus native PyTorch **17.741/16.065 ms**; the Jittor repeat was **20.610/17.035 ms**, so decode throughput reached **94.3–96.7%** of native across the two Jittor rounds. This bare result does **not** predict vLLM throughput because it excludes the scheduler, metadata, sampling, paged cache, and Graph. An additional both-sides `eager` attention control gave Jittor prefill/decode 17.349/15.864 ms and native 20.890/18.886 ms; both eager and SDPA comparisons used the same mode on both sides. The bare saved logits were not bitwise equal: for SDPA, first-token top-1 and all 64 teacher-forced step top-1 IDs agreed, but 933 of 9,723,904 decode-logit elements exceeded a tolerance of `0.02 + 0.02*abs(native)`; this is a small floating-point difference, not a strict logits-equality pass.

On NPU, a new default-off Jittor ACL `FusedInferPrefill` wrapper around CANN `aclnnFusedInferAttentionScore` reproduced the native saved layer-21 attention output exactly (20,480/20,480 BF16 elements), whereas the prior `FlashAttentionScoreV2` route differed in one element. In the same Qwen2.5-3B ten-token first-prefill snapshot, **all 36 layer outputs** were bitwise identical to native when direct patched RMSNorm, fused QKV linear, fused Add+RMSNorm, direct full prefill and the new attention wrapper were all opt-in enabled. Nevertheless, the two-request TP1/64 model run still first diverged from the native same-TP greedy sequence at zero-based token 39 (Jittor 6172, native 4621); its warmed measured request was 7.171 s, not a paired performance A/B. Thus the full NPU correctness bug is **not fixed**. The remaining mismatch now needs a decode-step and/or sampling-logit trace; the experimental flags stay off by default. The new runner passed standalone compilation, execution and Python compile checks, but has not passed multi-model/TP2 or production-lifetime validation.

## Longer CUDA output stress and limits of the short-shape result

To test whether the 128+64 Qwen3 result extrapolates, the same RTX 4090 GPU 2, FP16, TP1/batch-1, vLLM 0.24, greedy-output harness was run at **512 input + 256 output tokens**, one warmup and 11 intended measurements per process. The native PyTorch run completed all 11 with a 609.491 ms request median (420.0 output tok/s). Jittor with async fetch but **without** H2D batching, and with the 32-warp fused decode option, completed all 11, matched the native 256 IDs in every request and shut down cleanly: 807.146 ms (317.2 tok/s), or **75.5%** of native output throughput. The H2D-batched 8-warp candidate also completed all 11, was token-exact and shut down cleanly: 882.303 ms (290.1 tok/s), or **69.1%** of native. These are different Jittor kernel settings, so their timings are not a clean ablation of H2D batching.

Experimental H2D batching is **intermittently unstable at this long shape**. With 32-warp fused decode, its first process completed warmup and three 256-token measured requests (all token-exact, 675.812–678.949 ms) but then its worker segfaulted with exit code -11 during the next request. A repeat segfaulted in warmup at about generated token 189. A third process with the same settings completed all 11 measured requests, all token-exact, with a 678.016 ms median (377.6 output tok/s, **89.9%** of the native 420.0 tok/s). A subsequent uninstrumented 100-measurement process completed cleanly, matched every native 256-ID sequence, and had 678.125 ms median and 690.406 ms p95; a separate 50-measurement run under gdb also exited normally but its timing is diagnostically perturbed. These passes do not erase the crashes or establish production stability. GDB later caught an invalid `Op*` virtual call in Jittor's `count_fuse` during `sync_all` planning, but has not identified when that object was freed or overwritten. Both alternative targeted-sync variants also crashed. Crucially, an extended **H2D batching plus 8-warp** control crashed at the 43rd measured request, disproving the earlier suspicion that 32 warps were required; the **no-H2D plus 32-warp** control completed all 100 measured requests, all 25,600 generated IDs exact, and shut down cleanly (793.148 ms median). These are evidence that H2D batching exposes the fault under this workload, not proof of its exact underlying lifetime mechanism. Both experimental flags remain default-off. The native and safe Jittor controls demonstrate that model size, context length, output length, batch and TP must all be swept before extrapolating a single 0.6B/128+64 ratio to production workloads.

An exploratory same-model **4096 input + 64 output** run exposed an important scaling regression. On the same RTX 4090 GPU 2, Qwen3-0.6B FP16 TP1/batch-1, Graph decode, one warmup and three measurements, native PyTorch took **232.546 ms** median (275.2 output tok/s), Jittor async-only plus 32-warp decode **497.352 ms** (128.7 tok/s, 46.7% relative), and Jittor H2D-batched plus 32-warp decode **468.377 ms** (136.6 tok/s, 49.6% relative). Every measured Jittor 64-ID sequence matched native exactly and each worker exited normally. Median TTFT was 48.438 ms native versus 174.410/174.652 ms Jittor; median decode ITL was 2.943 ms native versus 5.091/4.656 ms Jittor. The harness truncates a repeated prompt to **exactly 4096 token IDs**; this is not merely `max_model_len=4096`. A first Jittor attempt failed before timing because the cuDNN bridge could not resolve `nvrtcGetCUBINSize`; preloading the matching CUDA 12.2 `libnvrtc.so` let the control run, and a narrow loader repair is undergoing validation. Three samples are exploratory rather than a confidence interval. They nevertheless falsify extrapolating the 128+64 approximately 93% figure to this longer input; the 512+256 crash is still unresolved and the candidate remains opt-in.

The long-output crash investigation ran stronger controls. H2D batching plus 8 warps also failed at measured request 43/100, while no H2D batching plus 32 warps completed 100/100 and matched all 25,600 generated IDs. Keeping the H2D NumPy source and returned Jittor tensor alive through the whole `execute_model` did not fix it (segfault at request 100/100); two variants replacing global `sync_all` with targeted tensor sync also failed (requests 23/100 and 11/100). All three diagnostic edits were withdrawn. Disabling CUDA Graph and keeping H2D batching plus 8 warps completed 30/30 requests, all 7,680 IDs exact, at a much slower 2.686 s/request median; 30 passes do not prove Graph is required for the crash. GDB repeatedly caught a virtual `requested_backend()` call through an invalid `Op*` inside `jittor::count_fuse`, so the immediate failure is host graph-plan memory safety, not a device attention-kernel fault. A default-off C++ experiment locking the graph around planning deadlocked in its first request: one thread held the graph lock while reacquiring the Python GIL, and another held the GIL while waiting for the graph lock in `VarHolder` destruction. The test's exact processes were terminated and the C++ lock edit was fully removed. No 512+256 crash fix is claimed.

A second, default-off C++ experiment used nonblocking graph-lock acquisition while holding the GIL and yielded the GIL only between failed attempts. Its one-request smoke completed, but the 100-request H2D+8-warp target segfaulted at request 25. A temporary worker-side vLLM RPC confirmed both guarded-plan and H2D-batch flags were `1` in the worker; thus the crash cannot be dismissed as a missing environment switch. The guarded-plan edit and RPC instrumentation were removed. An opt-in Op-lifetime diagnostic now records construction/destruction and checks operator addresses before the `count_fuse` virtual call; its first 1-warmup+1-measurement smoke completed after an expensive fresh Jittor core compilation, without catching an invalid Op. The diagnostic is being reduced in overhead before long stress; it is not a performance candidate.

On NPU, a generation-step layer probe located the Qwen2.5-3B TP1 BF16 10+64 first token mismatch at zero-based output index 39. The native reference selected ID 4621, Jittor selected 6172. Native raw logits for both candidates were exactly 23.25, but Jittor's were 23.375/23.5 respectively, proving this is not solely a sampler tie-break. At that step the embedding and layer 0–9 outputs were bitwise identical; the first layer boundary discrepancy was layer 10. A same-physical-NPU-5 native/Jittor internal probe narrowed the first difference further: layer-10 norm, QKV, RoPE and current-step attention Q/K/V were bitwise identical; the attention output was 96.73% exact with maximum absolute difference 0.001953125. Native snapshots on NPUs 2 and 5, with 64 versus 40 maximum outputs, were themselves bitwise identical at this generation step, ruling out physical card or output-limit as this observed discrepancy's cause. An isolated BF16 Qwen2.5-shape KV=49 synthetic test gave bitwise-identical native FIA and Jittor paged-incremental attention outputs, so the real-model difference is not yet attributed to the decode arithmetic kernel. The next required evidence is the *actual* layer-10 historical KV cache contents and block/slot/sequence metadata versus native; no NPU production-path correctness fix is claimed.
