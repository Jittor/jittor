# Inference acceptance of Qwen3-0.6B FP16 on Ascend 310P3

This page preserves the historical acceptance from 2026-09-22. For the current code's attention path, explicit weight pre-conversion, and synchronized timing comparison, see the [2026-10-12 performance report](2026-10-12-qwen3-ascend310p-performance.en.md).

- Status: Accepted for Qwen3-0.6B float16 greedy inference on one Ascend 310P3
- Last reviewed: 2026-09-22
- Source baseline: `1a3e184e` (310P operator-layer adaptation) plus this report's compat fixes
- Owner: Torch compatibility and ACL backend maintainers
- Review when: the Torch shim's meta device semantics, `Module.get_parameter`/`get_buffer` membership determination, RoPE FP32 frequency computation, or `acl_allow_hf32` behavior change

## Conclusion

The 310P adaptation had previously only completed operator-layer acceptance (`tests/backends/acl/` 214/11/0). This time, on the same 310P3, the first model-level end-to-end use case was run successfully with Transformers 4.56.2 through the Torch shim: **Qwen3-0.6B, loaded in FP16, 8-token greedy generation, three repeated runs producing identical output, and `fallback_count=0` under `backend_fallback=error`**.

`QWEN_RESULT` summary:

- `dtype: torch.float16`, `parameters: 596049920` (tied lm_head)
- Generated text `2 + 2 = 4.`, token ids `[17, 488, 220, 17, 284, 220, 19, 13]` ×3
- Load 6.88 s; first generate 17.58 s (including operator JIT), warm median 0.667 s (≈12.0 tok/s); NPU memory after load 1856 MB / 44213 MB
- `has_acl=1`, `use_acl=1`, `use_cuda=1`, `fallback_count=0`

Numerical comparison: real PyTorch 2.14.0+cpu / Transformers 4.56.2 in an independent venv, running greedy generation on the same prompt in FP32, produces token ids `[17, 488, 220, 17, 284, 220, 19, 13]` **token-for-token identical** to 310P FP16 (including RoPE hf32 precision reduction).

## Reproduction

```bash
source /usr/local/Ascend/cann-9.1.0/set_env.sh
ASCEND_RT_VISIBLE_DEVICES=0 JITTOR_TORCH_SHIM=1 \
backend_fallback=error acl_allow_hf32=1 \
PYTHONPATH=python python tests/backends/acl/manual/run_qwen3_transformers.py \
    --model <local-snapshot> --dtype float16 --max-new-tokens 8 --runs 3
```

`acl_allow_hf32=1` is required: HF's Qwen3 RoPE computes `inv_freq @ position_ids` in FP32 and then converts back to FP16; the 310P cube does not support FP32 `KEEP_DTYPE`, so by design it takes an explicit precision reduction (internal FP16 splitting, ~1e-3). decode output correctness is unaffected.

## compat gaps found and fixed this time

All three gaps were fixed after being confirmed with a minimal reproduction:

1. The `torch.empty(..., device="meta")` factory argument was unsupported: Transformers 4.56.2 uses a meta state dict to enumerate checkpoint keys. Following the established "real allocation + observable meta marker" semantics, added `_is_meta_device_request` + `_invoke_factory` marker + `Tensor.device`/`is_meta` reporting (`compat/torch/types.py`, `installers/factories.py`, `installers/tensor/method_api.py`).
2. `Module.get_parameter`/`get_buffer` used the globally deduplicated `named_parameters()` to determine membership, misreporting the tied `lm_head.weight` as an AttributeError. Changed to look up the leaf module's local `_parameters`/`_buffers` tables, consistent with torch semantics (`installers/nn/module_methods.py`).
3. The probe itself: `generate()` inputs were not moved to the NPU (Transformers only warns and does not migrate), and the shim activation check mistakenly used a `torch is jt` identity test; changed to check the shim marker. The probe also added a `float16` dtype option (`tests/backends/acl/manual/run_qwen3_transformers.py`).

Also: `MANIFEST.in` added a missing entry for `docs/guides/ascend-310p.md` (omitted in the previous commit).

## Speed comparison (same checkpoint, same prompt, greedy)

Three-way comparison: real PyTorch 2.14.0+cpu FP32 (i9-13900H 20 cores), official torch_npu 2.12.0 FP16, and this tree's Jittor shim FP16; the latter two run on the same 310P3.

| Context | Phase | torch CPU FP32 | jittor→310P FP16 | torch_npu→310P FP16 |
| --- | --- | --- | --- | --- |
| 502 tok | prefill | 1.81 s (277 tok/s) | 0.165 s (3050 tok/s) | **0.088 s (5736 tok/s)** |
| 502 tok | decode | 11.16 tok/s | 11.68 tok/s | **32.64 tok/s** |
| 502 tok | generate 32 tok end to end | 4.59 s | 2.82 s | **1.04 s** |
| 1998 tok | prefill | 10.2 s (196 tok/s) | 1.03 s (1944 tok/s) | **0.70 s (2837 tok/s)** |
| 1998 tok | decode | 7.06 tok/s | 8.75 tok/s | **23.28 tok/s** |
| 1998 tok | generate 32 tok end to end | 14.6 s | 4.57 s | **2.04 s** |

Correctness: the 31 generated tokens at the 1998-token context are **bit-identical across all three**; in the 502-token scenario torch CPU FP32 has a tie-branch token difference (a greedy fork between FP32 and FP16), and the two FP16 engines agree with each other. On the Jittor side, `backend_fallback=error`, `fallback_count=0`. Native Torch has no corresponding counter, so the same-named field in the old tool cannot serve as evidence of its fallback count.

Performance interpretation: the gap between the jittor shim and the official torch_npu is ~1.5-1.9× on prefill and ~2.7× on decode — batch=1 decode is limited by per-token operator submission latency, and the shim's Python-side dispatch and per-operator submission overhead are the main sources of the gap (consistent with the submission-amplification analysis in the 910B report); at the time both used composite attention implementations. What 310P lacks is FlashAttentionScore, and its supported PFA/IFA inference interface was later integrated. torch_npu's first decode run includes one-off operator compilation (~460 s), while the corresponding cost on the jittor side is JIT cache warmup (~17 s).

## Scope and limitations

- Only FP16 inference was accepted; BF16 is physically unavailable on 310P, and FP32 requires `acl_allow_hf32` throughout.
- The table above preserves the old version's performance snapshot; the current SDPA path and the re-synchronized timing baseline are governed by the new report.
- Covers short Q&A and greedy generation on the two long prompts in the table above; batch and sampling were not accepted.
- Training was not accepted (310P does not claim training capability).
