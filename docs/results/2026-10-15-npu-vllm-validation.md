# Qwen2.5-3B NPU decode diagnosis (2026-10-14)

## 2026-10-16 default-off attention-output rebind candidate

Cache-layout dependency for any future single-op replacement: `adapters/jittor_adapters/vllm/backend.py` declares vLLM's allocated cache as block-major `[num_blocks,2,block_size,num_kv_heads,head_size]`; `backends/acl/kernels/native/flashattention_op_acl.cc` both writes K/V rows into this combined tensor and constructs strided key/value **read** views for `aclnnIncreFlashAttentionV4`. ATB's existing `ReshapeAndCache` op expects separate contiguous key/value cache outputs; its `WithStride` variant only describes the **input** K/V layout. Switching to ATB therefore entails either a custom combined-output kernel or a coordinated cache-layout and attention-backend migration, not a local replacement of two `aclrtMemcpyAsync` calls. The installed ATB `KvCacheOperation` advertises only float16/int8 in its op config, not this BF16 workload. This dependency assessment is source/API inspection, not an implemented optimization.

Residual bounded timeline after guarded rebind, for prioritization only: rank-0 32-step profiled span **4.906 s** and non-event task union **0.267 s** imply **4.639 s** outside useful device tasks. The earlier native same-shape window was **2.873 s** span, **0.219 s** union, **2.654 s** outside; the instrumented gap difference is therefore **1.985 s** versus only **0.048 s** useful-task-union difference. Separate profiler runs and runtime/event overlap prevent literal host-time attribution or using these spans as throughput numbers. They nevertheless argue against tuning one device FlashAttention kernel as the next main lever. Native's task CSV includes 7,167 EVENT_RECORD and 4,736 EVENT_WAIT rows; after excluding these, its rank-0 useful rows are about **18,843** versus guarded Jittor's **35,059**, roughly **507 additional non-event tasks per decode step**. This is a directional cross-backend task-count comparison, not a one-to-one operation mapping.

Correction to the standalone ATB feasibility note below: [Huawei's ATB input/output specification](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/82RC1alpha001/API/ascendtbapi/ascendtb_01_0231.html) defines `kStrides` and `vStrides` as **three-element strides of the input key/value tensors**, with `kOffset`/`vOffset` likewise relative to input memory. They do **not** describe output-cache block strides. The provisional probe supplied four-element strides to `Setup`; its crash is an invalid-descriptor diagnostic, not evidence of an ATB library defect. More importantly, the documented ATB operation writes separate contiguous key/value caches, so it cannot directly replace Jittor's combined `[blocks,2,block_size,heads,dim]` cache without a layout migration or custom kernel. No model-path change was attempted; this direct-replacement candidate is stopped.
