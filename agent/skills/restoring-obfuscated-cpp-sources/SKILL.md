# 还原混淆的 C++ 翻译单元

## 什么时候需要这个

症状：`src/` 下有 `foo.h` 但没有 `foo.cc`，而 `foo.h` 里声明的东西在运行时确实存在。
构建脚本里能找到一段「解压 → 写成一个 .cc → 单独编译成 .o → 追加到链接列表」的逻辑。
那个 .o 里就是被藏起来的翻译单元，通常好几个 TU 被拼进了一个文件。

**这类代码不可审计**：没人能 review 它，改一行核心逻辑都得靠猜。还原它的**唯一目的是可读**，
所以「编译过了」不是完成，「读得懂」才是。

## 0. 先把验收标准钉死：符号清单

**在动手之前**先做这一步，否则你没有办法证明还原是等价的。

```bash
# 1. 让构建照常跑一次，拿到那个 .o
#    （构建脚本一般把它放在缓存目录，例如 $JITTOR_HOME/.../data.o）
# 2. 存下它定义的全部符号，这是唯一的验收标准
nm -C --defined-only data.o \
  | grep -E '^[0-9a-f]+ [BDT] ' | sed 's/^[0-9a-f]* / /' | sort -u > baseline_syms.txt
wc -l baseline_syms.txt
```

只留 `B`（未初始化全局）、`D`（已初始化全局）、`T`（函数）。**不要留 `W`/`V`/`R`**：
那些是模板实例化与 vtable，取决于哪些头文件被 include、内联发生在哪，
拆成多个 TU 之后必然变多，比对它们只会得到假失败。

还原完之后，用同样的过滤器对**新编出的那几个 .o** 取并集再比：

```bash
nm -C --defined-only fuser.cc.o node.cc.o atomic_tuner_pass.cc.o parallel_pass.cc.o shared_reduce_pass.cc.o \
  | grep -E '^[0-9a-f]+ [BDT] ' | sed 's/^[0-9a-f]* / /' | sort -u > new_syms.txt
diff baseline_syms.txt new_syms.txt
```

**判据**：条数必须相等，差异必须**只有**你主动改名的那些内部符号，且是一一对应的
（一条 `< x12345(...)` 对一条 `> real_name(...)`，参数类型逐字相同）。
多出来或少掉任何一条，都说明你漏了一个函数或者把两个函数合并了。

> 这一步只能在**同一台机器、同一个编译器、同一套 flag** 下比。换机器比对没有意义。

**但符号清单只是冒烟检查，不是验收。** 它对函数体内部的一切改动完全失明：
改名串位、常量抄错、`||` 链漏一项、循环边界被「顺手整理」、少传一个参数、
多加两行日志——符号集合全都纹丝不动。它对 `static` 更是完全失明（static 不进符号表）。
「跑一遍门禁没变红」也补不上这个洞：反混淆的典型错误是**静默**的，而且默认关着的
代码路径（见第 8 节的 `para_opt_level` 例子）门禁一行都执行不到。
真正的验收是第 8 节的两步。

## 1. 认出混淆手法

打开那个 .cc，一般是这几件事叠在一起：

| 手法 | 长相 | 处理 |
| --- | --- | --- |
| 噪声行 | 整行 `_P(] x99898 x8006 ... )`，占了大半个文件 | 直接删。构建时 `-include` 了一个只写着 `#define _P(...)` 的文件（这里叫 `vdp`），它们本来就展开成空 |
| 单字符宏 | `#define x65239 _` / `#define x55906 a`，一两百条 | 交给 `cpp` 展开 |
| 拼接宏 | `#define XX3(x0,x1,x2) _XX3(x0,x1,x2)` 配合 `_XX3` 做 token paste；调用形如 `XX3(x82148,x8629,x50438)` | 同上，`cpp` 展开后变回 `int` 这类真标识符 |
| 十六进制字符串 | `"\x72\x76\x61\x6c\x75\x65"` | 展开后统一转回可见字符 |
| 标识符改名 | 剩下的 `x10364`、`x57074` 是真正的函数名/变量名 | 见第 3 步，用头文件当字典 |
| **`#include` 不混淆** | `#include "opt/pass/atomic_tuner_pass.h"` 原样保留 | 这是**分割翻译单元的依据**，见第 2 步 |

## 2. 展开宏，但**不要**真的 include

直接跑 `cpp` 会把 `var.h` 之类整个展开进来，几十万行没法看。做法是先把 include 行换成标记：

```bash
sed -E 's|^#include (.*)$|JTINCLUDE \1 JTENDINCLUDE|' data.cc > noinc.cc
cpp -P noinc.cc > expanded.cc          # 只展开 XX* 与单字符宏
```

然后把十六进制字符串转回来，再用一个小的 C++ tokenizer 重新排版（`cpp -P` 出来的是一行几十万字符）。
排版器只需要：`{` 换行加缩进、`;` 换行、`}` 减缩进，不需要懂 C++ 语法。

## 3. 按 include 分回各个翻译单元

`JTINCLUDE` 标记是连续成组出现的，一组就是一个 TU 的头部：

```
JTINCLUDE <sstream> ... JTINCLUDE "opt/pass/atomic_tuner_pass.h" ...   <- TU 1
JTINCLUDE "node.h" JTINCLUDE "op.h" ...                                 <- TU 2
JTINCLUDE "fuser.h" ...                                                 <- TU 3
```

**TU 名字由那一组里的「自家头文件」决定**：含 `opt/pass/atomic_tuner_pass.h` 的那段就是
`opt/pass/atomic_tuner_pass.cc`。分界点在下一组 `JTINCLUDE` 出现之前的最后一个顶层
`}`（`namespace` 的收尾）。

交叉验证：把 `nm` 出的符号按类名分组（`AtomicTunerPass::run` 属于 atomic_tuner_pass），
每个 TU 的符号应当正好落在你切出来的那一段里。

## 4. 用头文件当字典恢复命名

剩下的 `xNNNNN` 分三类，按可靠性从高到低还：

1. **头文件里有声明的** —— 最可靠。`node.h` 里 `void memcheck_all_exist() const;`，
   混淆文件里就有一个签名一致的成员函数，直接对上。
   把该 TU 的所有相关头文件（自家的 + 它 include 的）里的声明列出来，按**签名**匹配。
2. **`nm -C` 的参数类型** —— 次可靠。`x95099(unique_ptr<KernelIR>&, FusedOp*)` 告诉你
   参数类型，配合函数体里对 `op->ops[i]->name()=="reduce"` 的检查，就能确定它叫
   `find_reduce_op_id` 之类。**这一类是你自己起的名字**，起完要在提交说明里列出对照表。
3. **局部变量与静态函数** —— 最自由，随便起，但要起得对得上函数体在做的事。
   静态函数不出现在符号表里（`nm` 看不到），所以**改名不会被符号比对发现，也就更要小心**：
   它们的行为只能靠读懂函数体保证。

还名的顺序：**先全局后局部**。全局名一改，很多局部名的用途就自明了
（`get_reduce_init_code` 的返回值赋给谁，那个局部就叫 `init_code`）。

字符串常量是最好的锚点：`"atomictuner: move "`、`"rvalue"`、`"tn"` 这些在展开后已经可读，
搜一下就知道这段代码在生成什么。

## 5. 读不懂的段落怎么写

**不要臆测。** 还原的价值在于下一个人能相信注释。读不懂的地方写成：

```cpp
// NOTE: 行为与原实现逐条对照过，逻辑未完全理解：
// <你确实观察到的事实，例如「rely 列表的最后一项恒为空串，所以循环从 size()-2 开始」>
```

宁可留一句「未完全理解」，也不要写一句听起来很懂但是错的注释——后者比混淆更有害。

## 6. 收尾：删掉整条旧路径

还原完之后，旧路径必须整条删掉，否则两份代码会同时参与链接（重复符号）或者悄悄分叉：

- 构建脚本里的解压/编译/追加 `.o` 逻辑，以及它的开关 flag；
- `-include` 的那个噪声宏定义文件（`vdp`）；
- 打包清单（`MANIFEST.in`）与断言它存在的结构测试；
- 指向一个**根本不存在的目录**的回退分支——这类分支是死代码，删的时候顺手确认一下
  它引用的路径确实不存在（`ls`），不要因为「看起来像备用方案」而留着；
- 文档里把它列为「运行期资源」的条目。

`grep -rn '<那个文件名>\|<那个 flag 名>'` 全仓库扫一遍，一条不留。

扫出来的东西分三类，别一刀切：**历史快照**（`agent/baselines/` 里记录过去 wheel 内容的
清单）本来就该继续列着它，不要改；**死代码**（引用一个不存在的目录、进函数就 `raise`）
如果归别的任务，留着但在提交说明里点名；**给人读的文档与 skill** 必须当场改——
一份还说着「实现藏在 data.gz 里，日志前缀要写 `data=100`」的 skill，
会让下一个 agent 抓不到日志然后去查一个不存在的问题。

## 7. 一轮完整验证

```bash
# 1. 清空缓存，从零构建一次（旧缓存里可能还留着老的 data.o）
rm -rf $JITTOR_HOME && <正常的构建/import 命令>
# 2. 符号比对（见第 0 步）——这一步不过，后面都不用跑
# 3. 三套门禁
```

第 1 步必须**清空缓存**：构建系统按内容哈希缓存，老的 `.o` 会被复用，让你以为编过了。

跑完这三步你只知道「还原后能编、能跑、符号没变」。**这不等于还原是忠实的**，
下一节才是。

## 8. 怎么证明还原是忠实的

反混淆的错误是静默的：一处改名串位、一个十六进制常量抄错、`||` 链里漏一个子句，
都不会报错、不会让门禁变红。所以要的不是「看起来没问题」，而是两条可复现的证明链。

**先想清楚要证明的是两件事，别混在一起：**

1. **我读的东西就是原文**——`cpp` 展开、十六进制解码、重排版这条流水线自己没有出错；
2. **还原就是那份原文**——你敲进 `.cc` 的代码与原文逐字对应。

第 1 步不做，第 2 步就是拿一份可能已经错了的东西当基准，全部悬空。

### 8.1 证明展开出来的原文就是原文：编回去，比助记符

把展开结果补回 `#include` 编成 `.o`，与随包那个 `.o` 用**同一套 flag**（记得复刻构建
脚本对 flag 的那些 `replace`，例如去掉 `-Wall`/`-Werror`）比：

```bash
# 先确认你的 flag 复现了构建自己产出的那个 .o（只应差 TU 名符号）
nm --defined-only data.o    | awk '{print $2,$3}' | sort > s_ship.txt
nm --defined-only myexp.o   | awk '{print $2,$3}' | sort > s_mine.txt
grep -v ' \.LC' s_ship.txt > a.txt; grep -v ' \.LC' s_mine.txt > b.txt
diff a.txt b.txt            # 只该剩 _GLOBAL__sub_I_<TU名>

# 指令流：地址、常量池标签、TU 名都归一掉再比
for f in data myexp; do
  objdump -d --no-show-raw-insn $f.o \
  | sed -E 's/^[[:space:]]*[0-9a-f]+:[[:space:]]*//; s/0x[0-9a-f]+/H/g;
            s/\b[0-9a-f]{3,}\b/H/g; s/\.LC[0-9]+/LC/g; s/(data|myexp)\.cc/TU.cc/g' \
  | grep -vE '^$|file format|Disassembly of' > $f.dis
done
diff origdata.dis myexp.dis | wc -l     # 少量差异是允许的，逐条要能解释
awk '{print $1}' data.dis  > m1.txt      # 只取助记符
awk '{print $1}' myexp.dis > m2.txt
diff m1.txt m2.txt                       # 这一条必须为空
```

**判据**：`.LC*` 常量池标签会重新编号（`__FILE__` 变了、字符串池随之微调），不比；
寄存器分配可以差几处（同样是 `__FILE__` 长度变化引起的），要能指着说清是哪几处；
但**助记符序列必须逐条相同**。相同就说明展开没有改变任何一条指令，
你手里那份可读原文可以当基准了。

### 8.2 证明还原就是那份原文：token 流逐字对齐

**不要用眼睛 diff**，一千多行、两套命名，人一定会漏。写一个百来行的比对器：

1. 两边都 token 化。**归一化必须做三件事**，否则会淹在假差异里：
   字符串/字符字面量解掉 `\xNN` 转义按内容比（`"\x72\x76"` 要等于 `"rv"`）；
   整数字面量按**值**比（`0x100` 等于 `256`——常量抄错就是靠这条抓）；
   丢掉注释、空白与 `#include`。
2. 贪心对齐：token 相同就前进；原文是 `xNNNN` 而还原侧是标识符，就记进改名表再前进；
   否则报为一处结构差异，用 `difflib.SequenceMatcher`（把 `xNNNN` 掩成同一个占位符）
   找回下一段长度 ≥8 的公共串重新同步。
3. 输出两样东西：**改名表**，和**每一处结构差异带上下文**。

**判据**：结构差异必须**逐条**给出「为什么不改变语义」。经验上真实的分布是
几十处，绝大多数属于下面这几类，认得出来就不慌：

| 类别 | 长相 | 怎么判 |
| --- | --- | --- |
| 死变量被删 | 原文有 `auto t = v.size();` 之后再不出现 | 数它在**该函数内**的出现次数；1 次就是死的。`-Wall` 的 `-Wunused-variable` 能替你抓一部分 |
| 逐字重复的子句被合并 | `f(A) \|\| f(A) \|\| f(B)` 变成 `f(A) \|\| f(B)` | 要证明 false 出口在任何修改之前，否则合并不安全 |
| 从不被读的参数被删 | 形参在函数体里 0 次出现，调用点全传同一个常量 | static 函数才不影响符号；非 static 会被 8.1 抓到 |
| 有符号/无符号被改 | `int i` 变 `uint`，新增 `(int)` 强转 | **先查仓库是不是已经全局压掉了 `-Wsign-compare`**（`grep -rn 'diagnostic ignored' --include='*.h'`）。压掉了，这类改动就是多余的，要按「未必要的改动」记账，别当成必需 |
| 排版 | 多余花括号、末尾 `return;`、末尾逗号 | 无害 |
| **多加的东西** | 原文没有的 `LOG*` 行、新的断言 | **这是「加」不是「还原」，必须在提交说明里写出来。** 一个只有定义、没有调用点的静态函数，往往就是「上游有日志、随包这份没有」的痕迹 |

### 8.3 串位检查：α 等价，而且必须按函数做

全局改名表里出现「一个 `xNNNN` 对多个名字」和「一个名字对多个 `xNNNN`」是**正常的**，
不是错误信号——混淆器按原名映射，所以同一个 `xNNNN` 会横跨多个不相交的作用域
（每个 `for` 里的 `i` 都是同一个 `xNNNN`）。**拿全局表判串位一定得出满屏假警报。**

要判就按**函数内**判，而且别去比名字，比结构：把两侧参与改名的 token 各按
**在该定义内首次出现的顺序**编号，逐位比较两条序号序列。

- 序列相同 ⇒ 该函数是纯改名（α 等价），选了什么英文名无所谓；
- 还原侧序号**更大** ⇒ **拆分**：原文一个名字在不相交作用域里复用，还原按用途分别
  命名了。安全，通常还更好读；
- 还原侧序号**更小** ⇒ **合并方向，这才是要查的**：还原侧复用了一个更早的名字。
  多数情况是无害的（同名跨两个不相交的 lambda；或前面删了个死变量导致序号平移），
  但**每一个都必须人工读一遍**，确认那两个变量不会同时活着。

### 8.4 差分测试：比生成物，不要只比 pass/fail

用 `git archive <还原前的提交>` 和 `git archive <还原后的提交>` 各导出一棵树
（不要新建 worktree、不要动分支），各建一份核心，**串行、同一顺序**跑同一批用例。

```bash
git archive <commit>^ | tar -x -C /tmp/tree_old     # 还带着混淆资源
git archive <commit>  | tar -x -C /tmp/tree_new
```

两份日志去掉树路径前缀与耗时后应当**逐字节相同**——不只是通过数相同，
还要是同样的用例跳过、同样的警告出现在同样的行号。

**如果被还原的是代码生成器（pass），pass/fail 是钝器。** 改成比生成物：跑一批固定
负载，把 JIT 生成的每个 kernel 源码整篇存下来，两侧逐字节比。生成物相同，
就把「pass 的每一个决策都一样」钉死了，比任何断言都强。

两个坑：

- **浮点非确定性**。GPU 上原子加的求和顺序不固定，同一份代码两次跑就能差
  `1e-7`。所以数值一旦有差异，**先做对照实验**：把同一侧**再跑一遍**跟它自己比。
  如果「不稳的负载集合」两边一模一样、且没有任何负载是「跨版本不同但同版本能复现」的,
  那这些差异就与还原无关。**没做这个对照就报「数值不一致」，是在制造假警报。**
- **默认关着的 pass 一行都跑不到**。先读还原出来的 `run()` 开头有没有
  `if (<某个 opt level> < N) return;` 这类闸门，再去查那个 flag 的默认值。
  真关着，就临时打开它跑一轮（生成物照样逐字节比），并在报告里写明
  「门禁对这个 pass 的覆盖是零，两侧都是零」——否则「门禁不变」是在用没执行过的
  代码作证。
