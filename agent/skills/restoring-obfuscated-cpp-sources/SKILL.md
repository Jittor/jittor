# 还原混淆的 C++ 翻译单元

## 什么时候需要这个

症状：`src/` 下有 `foo.h` 但没有 `foo.cc`，而 `foo.h` 里声明的东西在运行时确实存在。
构建脚本里能找到一段「解压 → 写成一个 .cc → 单独编译成 .o → 追加到链接列表」的逻辑。
那个 .o 里就是被藏起来的翻译单元，通常好几个 TU 被拼进了一个文件。

**这类代码不可审计**：没人能 review 它，改一行核心逻辑都得靠猜。还原它的**唯一目的是可读**，
所以「编译过了」不是完成，「读得懂」才是。

## 0. 先把验收标准钉死：符号清单

**在动手之前**先做这一步，否则你没有办法证明还原是等价的。

```bash
# 1. 让构建照常跑一次，拿到那个 .o
#    （构建脚本一般把它放在缓存目录，例如 $JITTOR_HOME/.../data.o）
# 2. 存下它定义的全部符号，这是唯一的验收标准
nm -C --defined-only data.o \
  | grep -E '^[0-9a-f]+ [BDT] ' | sed 's/^[0-9a-f]* / /' | sort -u > baseline_syms.txt
wc -l baseline_syms.txt
```

只留 `B`（未初始化全局）、`D`（已初始化全局）、`T`（函数）。**不要留 `W`/`V`/`R`**：
那些是模板实例化与 vtable，取决于哪些头文件被 include、内联发生在哪，
拆成多个 TU 之后必然变多，比对它们只会得到假失败。

还原完之后，用同样的过滤器对**新编出的那几个 .o** 取并集再比：

```bash
nm -C --defined-only fuser.cc.o node.cc.o atomic_tuner_pass.cc.o parallel_pass.cc.o shared_reduce_pass.cc.o \
  | grep -E '^[0-9a-f]+ [BDT] ' | sed 's/^[0-9a-f]* / /' | sort -u > new_syms.txt
diff baseline_syms.txt new_syms.txt
```

**判据**：条数必须相等，差异必须**只有**你主动改名的那些内部符号，且是一一对应的
（一条 `< x12345(...)` 对一条 `> real_name(...)`，参数类型逐字相同）。
多出来或少掉任何一条，都说明你漏了一个函数或者把两个函数合并了。

> 这一步只能在**同一台机器、同一个编译器、同一套 flag** 下比。换机器比对没有意义。

## 1. 认出混淆手法

打开那个 .cc，一般是这几件事叠在一起：

| 手法 | 长相 | 处理 |
| --- | --- | --- |
| 噪声行 | 整行 `_P(] x99898 x8006 ... )`，占了大半个文件 | 直接删。构建时 `-include` 了一个只写着 `#define _P(...)` 的文件（这里叫 `vdp`），它们本来就展开成空 |
| 单字符宏 | `#define x65239 _` / `#define x55906 a`，一两百条 | 交给 `cpp` 展开 |
| 拼接宏 | `#define XX3(x0,x1,x2) _XX3(x0,x1,x2)` 配合 `_XX3` 做 token paste；调用形如 `XX3(x82148,x8629,x50438)` | 同上，`cpp` 展开后变回 `int` 这类真标识符 |
| 十六进制字符串 | `"\x72\x76\x61\x6c\x75\x65"` | 展开后统一转回可见字符 |
| 标识符改名 | 剩下的 `x10364`、`x57074` 是真正的函数名/变量名 | 见第 3 步，用头文件当字典 |
| **`#include` 不混淆** | `#include "opt/pass/atomic_tuner_pass.h"` 原样保留 | 这是**分割翻译单元的依据**，见第 2 步 |

## 2. 展开宏，但**不要**真的 include

直接跑 `cpp` 会把 `var.h` 之类整个展开进来，几十万行没法看。做法是先把 include 行换成标记：

```bash
sed -E 's|^#include (.*)$|JTINCLUDE \1 JTENDINCLUDE|' data.cc > noinc.cc
cpp -P noinc.cc > expanded.cc          # 只展开 XX* 与单字符宏
```

然后把十六进制字符串转回来，再用一个小的 C++ tokenizer 重新排版（`cpp -P` 出来的是一行几十万字符）。
排版器只需要：`{` 换行加缩进、`;` 换行、`}` 减缩进，不需要懂 C++ 语法。

## 3. 按 include 分回各个翻译单元

`JTINCLUDE` 标记是连续成组出现的，一组就是一个 TU 的头部：

```
JTINCLUDE <sstream> ... JTINCLUDE "opt/pass/atomic_tuner_pass.h" ...   <- TU 1
JTINCLUDE "node.h" JTINCLUDE "op.h" ...                                 <- TU 2
JTINCLUDE "fuser.h" ...                                                 <- TU 3
```

**TU 名字由那一组里的「自家头文件」决定**：含 `opt/pass/atomic_tuner_pass.h` 的那段就是
`opt/pass/atomic_tuner_pass.cc`。分界点在下一组 `JTINCLUDE` 出现之前的最后一个顶层
`}`（`namespace` 的收尾）。

交叉验证：把 `nm` 出的符号按类名分组（`AtomicTunerPass::run` 属于 atomic_tuner_pass），
每个 TU 的符号应当正好落在你切出来的那一段里。

## 4. 用头文件当字典恢复命名

剩下的 `xNNNNN` 分三类，按可靠性从高到低还：

1. **头文件里有声明的** —— 最可靠。`node.h` 里 `void memcheck_all_exist() const;`，
   混淆文件里就有一个签名一致的成员函数，直接对上。
   把该 TU 的所有相关头文件（自家的 + 它 include 的）里的声明列出来，按**签名**匹配。
2. **`nm -C` 的参数类型** —— 次可靠。`x95099(unique_ptr<KernelIR>&, FusedOp*)` 告诉你
   参数类型，配合函数体里对 `op->ops[i]->name()=="reduce"` 的检查，就能确定它叫
   `find_reduce_op_id` 之类。**这一类是你自己起的名字**，起完要在提交说明里列出对照表。
3. **局部变量与静态函数** —— 最自由，随便起，但要起得对得上函数体在做的事。
   静态函数不出现在符号表里（`nm` 看不到），所以**改名不会被符号比对发现，也就更要小心**：
   它们的行为只能靠读懂函数体保证。

还名的顺序：**先全局后局部**。全局名一改，很多局部名的用途就自明了
（`get_reduce_init_code` 的返回值赋给谁，那个局部就叫 `init_code`）。

字符串常量是最好的锚点：`"atomictuner: move "`、`"rvalue"`、`"tn"` 这些在展开后已经可读，
搜一下就知道这段代码在生成什么。

## 5. 读不懂的段落怎么写

**不要臆测。** 还原的价值在于下一个人能相信注释。读不懂的地方写成：

```cpp
// NOTE: 行为与原实现逐条对照过，逻辑未完全理解：
// <你确实观察到的事实，例如「rely 列表的最后一项恒为空串，所以循环从 size()-2 开始」>
```

宁可留一句「未完全理解」，也不要写一句听起来很懂但是错的注释——后者比混淆更有害。

## 6. 收尾：删掉整条旧路径

还原完之后，旧路径必须整条删掉，否则两份代码会同时参与链接（重复符号）或者悄悄分叉：

- 构建脚本里的解压/编译/追加 `.o` 逻辑，以及它的开关 flag；
- `-include` 的那个噪声宏定义文件（`vdp`）；
- 打包清单（`MANIFEST.in`）与断言它存在的结构测试；
- 指向一个**根本不存在的目录**的回退分支——这类分支是死代码，删的时候顺手确认一下
  它引用的路径确实不存在（`ls`），不要因为「看起来像备用方案」而留着；
- 文档里把它列为「运行期资源」的条目。

`grep -rn '<那个文件名>\|<那个 flag 名>'` 全仓库扫一遍，一条不留。

## 7. 一轮完整验证

```bash
# 1. 清空缓存，从零构建一次（旧缓存里可能还留着老的 data.o）
rm -rf $JITTOR_HOME && <正常的构建/import 命令>
# 2. 符号比对（见第 0 步）——这一步不过，后面都不用跑
# 3. 三套门禁
```

第 1 步必须**清空缓存**：构建系统按内容哈希缓存，老的 `.o` 会被复用，让你以为编过了。
