# 给核心记账改动定价

整改计划里有一批任务是「把某个per-node 的共享槽位换成局部数据结构」（2.02、2.03、2.06、2.10）。
这类改动**功能上等价、正确性上更好、性能上不免费**：`run_sync` 每执行一次要在图上做
几万次「给我这个节点的下标」。**没有量过就不要提交**——实测把 `Node::custom_data` 全部
换成局部哈希表是 `run_sync` **+43%**。

## 1. 基准长什么样

要量的是**规划开销**（run_sync 自己的 CPU 时间），不是 kernel 时间。所以：

```python
# 一张大的惰性图，一次 sync
def one_round():
    keep = []
    base = jt.array(np.ones(SIZE, "float32"))
    for b in range(BRANCH):                 # 30
        v = base + float(b)
        for i in range(CHAIN):              # 40
            v = v * 1.0001 + 0.5
            if i % 10 == 0:
                keep.append(v)              # 见下：必须留
        keep.append(v)
    t0 = time.perf_counter(); jt.sync_all(); t1 = time.perf_counter()
    return t1 - t0
one_round()                                  # 预热：JIT 编译不计入
times = [one_round()[0] for _ in range(21)]  # 取中位数
```

四条都不能省：

- **`jt.flags.use_parallel_op_compiler = 0`。** 并行算子编译器不是被改的东西，而且它会
  把第一轮变成几分钟的线程调度噪声。**更糟的是它会挂死**：一次 ~9600 个算子的图在
  预热轮里卡在编译池上超过 20 分钟不动（父进程 `pipe_read`，池里的 worker 全在睡），
  两棵不同的树上都复现。规划开销的基准里关掉它，顺便绕开这个坑。
- **每隔几个中间结果留一个 Python 引用。** 只留最后一个，惰性图会把要计时的活删掉，
  量出来是假快。留住它们还有第二个作用：被持有的 var 必须落到内存，这正是
  执行器与 `FusedOp` 之间那套「哪些 var 不能融合」的协议，也就是被改的东西。
- **CPU-only。** 有 CUDA 的话规划开销藏在异步队列后面，看不见。
- **同一段核、交替跑三遍。** 这台机器上常驻十几个 agent，跨核段比不同版本会得到
  相反的结论（实测同一份代码在两个核段上中位数差 30%）。

## 2. 判据：常数还是比例

**改一次张量大小再量一遍。** 规划开销与张量大小无关，kernel 时间随它涨。两次的**差值**
如果是常数，那个常数就是你的真实代价，可以按「每个算子多少微秒」报出来：

| 元素数 | 改前 | 改后 | 差 |
| --- | --- | --- | --- |
| 4 | 2.21 ms | 2.55 ms | +0.34 ms（+15%） |
| 65536 | 2.93 ms | 3.15 ms | +0.22 ms（+7.5%） |
| 262144 | 5.34 ms | 5.64 ms | +0.30 ms（+5.6%） |

同一份改动，百分比从 15% 掉到 5.6%，**而差值是常数** ≈ 0.3 ms / 2400 算子
≈ **0.12 µs/算子的规划开销**。报百分比会让人以为负载越大越糟，正好反了。

## 3. 定价之后怎么选

按「每个算子多少纳秒」把候选排开，实测（2400 算子的图，同一段核）：

| 做法 | run_sync | 相对 |
| --- | --- | --- |
| 共享的 `Node::custom_data`（原状） | 2.26 ms | 基准 |
| 有主的节点字段 + stamp + **inline** 的 `ASSERT` 读校验 | 2.51 ms | +11% |
| 同上，读校验改成「预测不跳转的分支 + out-of-line 冷函数」 | 2.44 ms | +8% |
| 全部改成局部开放定址哈希表 | 3.15 ms | +43% |

一次指针键的哈希探测大约 10 ns，而它替代的是一次「本来就在被访问的 cache line 上」的
字段读。**这条差距是结构性的，优化不掉**：换成世代计数省掉 memset、把装填因子从 1/2
调到 3/4、把槽压到 16 字节，三样加起来没有可测的改善（3.18 → 3.15 ms）。

**但校验本身的写法有得优化，而且差别不小。** 把「读的时候校验 stamp」直接写成
`ASSERT(cond) << "..."`，失败路径的代码会落在执行器每一个紧循环里——**一次都不执行，
也要花每算子约 0.09 µs**（2.30 → 2.51 ms）。改成

```cpp
    void batch_index_mismatch(int64 stamp) const;   // 定义在 .cc 里，LOGf
    inline int batch_index_at(int64 stamp) const {
        if (PREDICT_BRANCH_NOT_TAKEN(batch_stamp != stamp))
            batch_index_mismatch(stamp);
        return batch_index;
    }
```

检查一模一样，代价掉回 2.44。**热路径上的断言要按代码体积算钱，不是按分支算钱。**

所以结论一般是**分层**：冷路径（`grad()`、`dump_all_graphs`、拓扑排序、内存分析器）
一律改成局部表，代价量不出来；**热路径（`run_sync` 的批下标）留在节点上，但把
「共享且无人负责」改成「一个所有者 + 一个 stamp + 读的时候校验」**。后者拿到了这类
任务真正要的东西——两个遍历交错时会报错而不是静默串号——而只花约 8%（每算子 0.075 µs）。

还有一类用法**不该按性能取舍，而是根本不属于这个任务**：`FusedOp` 往同一个字段里打包的
`(vid<<2)|已访问|不可融合` 不是遍历标记，而是要跨整条 JIT 管线保持有效的映射
（`do_jit_prepare`、`get_loop_options`、`context->vrm` 都读它）。**判据是「这个值活到
什么时候」**：活到本次遍历结束的是标记，活到 JIT 编译的是映射，后者要改就得连同它的
读取点一起改，那是另一条任务（2.24）。审计里那句「遍历用局部 vector 按 node id 索引」
对前者成立、对后者不成立——**动手前先按生命周期把用法分类，别按字段分类。**

## 4. stamp 不要复用 `tflag`

复用 `tflag` 当 epoch 是免费的，也是错的：**`tflag` 是全局计数器，任何遍历都会重写它，
而且真的有人在批跑到一半时重写**——`MemoryProfiler::check()` 从 `run_sync` 的算子循环
里面调用，它的 `bfs_both` 会把走到的每个节点的 `tflag` 改掉。实测后果：
「这个节点属于当前批」在批中途变成假，`FusedOp` 认为所有 var 都必须落内存，
生成的 kernel 编译失败。

判据：**你的 epoch 字段必须只有你写。** 加 8 字节的专用 stamp 比复用 `tflag` 贵不了
什么（量不出来），而复用会在最需要它的那条路径上失效。

## 5. 顺带：怎么证明那个共享槽位真的是共享的

不要试图构造两个遍历交错的时序。**去找已经写在代码里的那份「手工补丁」，把它删掉。**
补丁的存在就是证据：

- `memory_profiler.cc` 把 `custom_data` 整个抄出来、跑完拓扑排序再抄回去；
- `grad.cc` 在开始构造反向算子之前把所有下标抄进 `id_buffer`，因为构造算子会重入
  `run_sync`。

删掉 `memory_profiler.cc` 那六行、别的都不动，一张可融合的图立刻死在
`fused_op.cc Check failed: outputs().size()`。**这就是修前失败**，而且失败点离原因隔了
两个文件——正是这类缺陷的形状。修完之后同一个探针（开着 `profile_memory_enable=1`
跑可融合的图与一次反向，比对关掉时的数值）变成回归测试。
