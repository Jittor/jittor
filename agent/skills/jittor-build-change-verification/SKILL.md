# 验证核心与构建改动

## 编辑与产物

先读[隔离验证](../isolated-validation/SKILL.md)。记录源码 SHA、dirty 补丁、编译器与 SDK、
构建选项、实际 `jittor.__file__` 和 `jittor.compiler.cache_path`。相同源码不保证构建能力相同；
MPI、CUDA、ACL、编译器及环境探测可能改变配置指纹。

修改 `src/` 后，以当前配置串行导入触发重编，并从日志和产物确认改动进入实际加载的库。
头文件变更尤其要核对依赖跟踪。不要用另一个缓存中的时间戳或“最新文件”代替产物证据。
仅对维护入口明确识别的 `JIT_UTILS_UPDATED_EXIT_CODE` 按入口协议重试；普通编译失败必须保留。

## 按改动选择验证

| 改动 | 定向验证 |
| --- | --- |
| C++ 算子或执行语义 | 最小复现、对应核心测试、实际目标设备上的数值与梯度 |
| 缓存键/配置检测 | 全新缓存、同配置热启动、改变相关 flag 后再运行并核对产物 |
| 构建锁/并发 | 独立任务缓存中预热后启动受控 worker，检查退出码、锁释放和完整产物 |
| 可选能力 | 有/无依赖两种明确环境；缺失时报错或禁用行为符合公开契约 |

若改动涉及首次产物创建的锁，在专用实验缓存另做受控冷启动竞争，验证等待与清理；
这不替代日常首次 JIT 串行准备的规则。

基线和候选使用独立 worktree 与缓存，包含相关未提交改动的候选快照应有补丁身份。
CUDA 同样可以用独立源码目录验证，不要求覆盖当前工作树。停止并确认本任务所有 worker
退出后才能处理其缓存；优先分配新目录，不删除任意传入的 `JITTOR_HOME`。

## 导入成本诊断

[scripts/measure_import_cost.py](scripts/measure_import_cost.py) 在子进程拆分导入开销，
先设置 `EXPECT_JITTOR_SRC="$PWD/python"` 与同源 `PYTHONPATH`，
用 `--json <外部路径>` 保存数据。它是计时工具，不替代构建正确性或设备验收。
重新调用生成器的部分是热态工作量，不代表首次生成。冷热状态、工具链、能力和实际导入路径一致时再比较；首次编译与稳态导入分开报告。
