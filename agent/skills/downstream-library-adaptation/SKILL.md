# 下游问题的归属与验证

本 skill 是主仓与 [JittorEcosystem](https://github.com/JittorEcosystem) 的交界规则。
具体库的固定版本、安装方式、adapter、官方测试、教程、基准和功能/芯片支持表，
以对应独立仓库为准；不在主仓为每个库再建一份操作手册。

## 先确定改哪里

| 问题 | 修改位置 | 主仓需要的回归 |
| --- | --- | --- |
| Jittor 缺少计算能力或计算结果错误 | 主仓核心与对应后端 | 尽量不依赖下游库的最小算子、梯度或运行时测试 |
| 已有能力的公共 Torch 签名、对象身份或语义不兼容 | 主仓 `compat/` | 公共 Torch API 的行为或结构测试 |
| 下游库私有 API、插件注册、模型入口或版本差异 | 对应生态仓库 | 主仓无需复制其专属测试；共享接口变化才增加主仓回归 |

不要为通过某个库而增加第二套数学实现、伪造版本，或修改全进程框架身份。
需要新的公共接口时，先在核心或 compat 定义并验证，再由独立集成使用。
具体边界见[兼容原则](../../../docs/development/compatibility/principles.md)。

## 开始一次排查

1. 按根 `AGENTS.md` 同步本次涉及的仓库，记录各自完整提交 SHA，保留已有改动。
2. 在生态仓库确认上游版本、安装组合、目标功能和设备；先复现，再判断归属。
3. 能归约为公共 API 问题的，提取不依赖大模型或下游训练框架的最小脚本。
4. 核心或 compat 修复随主仓测试提交；完整下游场景在生态仓库复验。
5. 下游支持表只更新实际执行通过的功能、规格、版本和设备，引用修复提交与验证证据。

上游 checkout、模型、日志和编译状态放在外部 `JITTOR_LAB_ROOT`，目录与并发规则见
[环境手册](../../manuals/environment.md)。不要把外部 checkout 或手动补丁复制进主仓。

## 什么证据能支持什么结论

- **可导入/可运行**：只能证明所执行入口没有报错，不能证明数值、训练或整库支持。
- **数值一致**：独立的原生 PyTorch 与 Jittor 解释器，固定相同上游版本、权重和输入，
  比较前向输出、所请求的全部参数及输入梯度，记录容差、缺失项与非有限值。
- **可训练**：补充多步 loss、梯度与更新后参数轨迹，验证冻结参数没有被修改。
- **目标芯片可用**：在声明的真实设备执行，记录实际后端与零 fallback 证据。
  CPU 结果不授予 CUDA、ROCm 或 NPU 支持；无法使用独立同设备参考栈时，明确标注证据降级。
- **性能结论**：先有同规格正确性证据，再比较预热后的时间与同口径内存；区分首次运行和稳态。

先在 CPU 收敛公共语义，再验证所声明的加速设备；核心既有的跨设备 parity 测试继续保留。
两侧依赖和运行条件必须可核对，参考解释器不得载入 shim。缺环境或硬件就记录未验证，
不以 skip、导入成功或旧报告冒充通过。

一个代表模型不等于整库。支持范围按功能、模型/方法、dtype、芯片和上游版本分别列出。
涉及覆盖率时，分母来自固定上游提交的真实注册表，未执行项不能进入通过数。
详细证据字段见[下游验证协议](../../../docs/development/testing/downstream-scorecards.md)。

## 主仓现有工具的边界

`compat/tests/torch/` 中已有的通用生态回归用于发现共享语义回归，不替代各生态仓库的
完整官方测试。仍被主仓测试和 CI 调用的验证脚本集中在
[`tools/ecosystem/`](../../../tools/ecosystem)，其存在不代表对应库已经通过验收。
新增库的专属用例和执行流程放在生态仓库，不继续向主仓扩充逐库操作手册。

任务和运行证据写入 GitHub issue/PR；主仓未解决的核心/compat 缺陷记录在
[问题总账](../../manuals/known-issues.md)，待设备验证记录在
[硬件验收清单](../../manuals/deferred-hardware.md)。不在 `agent/` 维护第二份支持矩阵或运行历史。
