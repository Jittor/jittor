## 2. 结论摘要

1. **SDPA 的主要差距不只在 attention 内核。** 在逐次同步的同形状 fp16 测试中，Jittor `F.sdpa` native 路径为 `0.1968 ms`，直接向 native backend 传 BSHD 连续张量为 `0.1180 ms`，而 PyTorch flash 为 `0.0273 ms`。后续独立消融确认，显著差距来自整个 BHLD→BSHD layout materialization 与 wrapper，而不是末尾 `.clone()` 单独造成：64 轮交错配对中删 clone 只快 `3.6%`，lazy packed QKV 输入下反而更慢。
2. **现有 native flash 路径只能加速无梯度推理。** 路径要求 CUDA + `no_grad` + `dropout_p=0` + 无 mask，且构建显式定义 `FLASHATTENTION_DISABLE_BACKWARD` 和 `FLASHATTENTION_DISABLE_DROPOUT`，因此尚不能解决 Transformers 训练 SDPA 的 backward/dropout 瓶颈。
3. **梯度裁剪去掉主机分支只在确实发生裁剪时稳定获益。** 128/512 个梯度张量时约快 `23.1%/22.3%`；不触发裁剪时反而慢 `19.5%/7.3%`，因为新路径仍逐个写回所有梯度。应把裁剪系数融合进 optimizer update，或提供 foreach/multi-tensor scale。
4. **GradScaler 必须走 flat/foreach。** 本 agent 最初审计的“每张量 finite reduction，再合并标量”快照在 512 张量时慢 `41.3%`。共享树随后改成平铺后一次 finite check；后续共享结果显示 512 张量由 `12.80 ms` 降至 `9.09 ms`，说明 flat 方向正确，最终仍建议实现原生 multi-tensor unscale + nonfinite kernel。
5. **`Tensor.backward()` 有无条件 forward materialization 边界。** `torch_compat.py::_backward()` 在 `jt.grad` 前调用 `self.sync()`。其默认参数 `device_sync=false`，不是 CUDA device synchronize，但会提前执行 forward、截断 Jittor 原本可联合调度/融合的图。它是为外部 CUDA extension 正确性加入的，不能直接删除；应只对需要 out-of-band 写入的 extension 图启用。

## 3. SDPA 性能分解

形状均为 `B=4,H=12,L=128,D=64`，fp16，GPU3。下表为每次调用后立即 device synchronize 的 20 次测试，比“先排队 N 个 lazy graph、最后统一同步”更接近训练/服务单步延迟。

| 路径 | mean (ms) | median (ms) | min (ms) | 相对 PyTorch flash |
|---|---:|---:|---:|---:|
| Jittor math | 0.216294 | 0.247541 | 0.135892 | 7.93x |
| Jittor `F.sdpa` native | 0.196755 | 0.180724 | 0.117547 | 7.21x |
| Jittor native direct BSHD | 0.117995 | 0.104265 | 0.030849 | 4.33x |
| PyTorch forced math | 0.158920 | 0.157614 | 0.154768 | 5.82x |
| PyTorch flash | 0.027283 | 0.026086 | 0.025148 | 1.00x |

解释：

- `F.sdpa` native 相对 Jittor math 均值只快 `9.0%`。
- 绕过 `torch_compat.py` 中 Q/K/V 的三组 `permute(...).reshape(...).clone()` 后，均值下降 `40.0%`（`0.1968 -> 0.1180 ms`）。后续消融表明这是整个 layout 转换与 wrapper 的成本，不能归因成 `.clone()` 本身的可回收开销。
- direct 路径最小值 `0.0308 ms` 已接近 PyTorch flash，但均值明显更高且最大值约 `0.370 ms`。这表明 kernel 本体具备接近对照的可能，桥接/调度抖动和 layout materialization 更值得优先剖析；单看最小值不能作为最终吞吐结论。
- 现有 `benchmark_training_hotspots.py` 会排队全部输出后统一同步，Jittor math 可以跨多个独立 lazy graph 摊薄 executor 开销，因此结果随 repeats 明显变化：math 在 repeats=50/100 时分别为 `0.1453/0.0739 ms`，native 为 `0.0974/0.0875 ms`。这类批量排队数据不能单独用于判断单步 native 与 math 的快慢。

### Q/K/V layout 物化独立消融

探针：`probe_sdpa_layout_materialization.py`。原始结果：

- `results/sdpa_layout_gpu3_20260711.jsonl`
- `results/sdpa_layout_gpu3_rerun_20260711.jsonl`
- `results/sdpa_layout_gpu3_paired_20260711.jsonl`
- `results/sdpa_layout_gpu3_lazy_packed_20260711.jsonl`

所有模式使用 fp16 `B=4,H=12,L=128,D=64`，official native backend 和逐次 device sync。每个模式还会把同一输入连续排队多次、保留全部输出后统一同步，用于暴露临时 Var metadata 或输入生命周期问题。

| 方案 | 首轮 median (ms) | 反序复测 median (ms) | 正确性/重复稳定性 |
|---|---:|---:|---|
| 当前 `permute -> reshape -> clone` | 0.08302 | 0.07319 | 通过，零漂移 |
| `permute -> reshape`，无 clone | 0.07175 | 0.07636 | 通过，零漂移 |
| `.contiguous()` 替代 clone | 0.06869 | - | 通过，零漂移；实际为 identity |
| 无 clone，但 Q/K/V 分别 `sync()` | 0.07354 | - | 通过，零漂移；增加 3 个 executor 边界 |
| 上游预先提供 BSHD contiguous | 0.03810 | 0.03877 | 通过，零漂移 |

短测试容易受单次 outlier 与模式顺序影响。例如首轮 clone 最大值 `0.253 ms`，反序复测无 clone 最大值 `0.264 ms`。因此又做了 64 轮 clone/no-clone 交错配对：

| 方案 | mean (ms) | median (ms) | max (ms) |
|---|---:|---:|---:|
| 当前 clone | 0.059865 | 0.058720 | 0.072586 |
| 无 clone | 0.057702 | 0.056481 | 0.070782 |

无 clone 在配对测试中只快 `3.6%`（median 快 `3.8%`）。当 Q/K/V 来自本次调用内新建的 lazy packed QKV view 时，16 个不同输入和 16 次排队重复仍然数值正确、零漂移，但无 clone median 为 `0.13942 ms`，比 clone 的 `0.13014 ms` 慢 `7.1%`，并出现一次 `0.921 ms` 抖动。

所有消融输出相对 float32 reference 的最坏 `max_abs=5.058e-4`、平均 `mean_abs≈2.907e-5`；重复同输入的输出间 `max_abs=0`。因此在**本次固定 inference 形状**上，无 clone 功能上通过。但不能据此认定可以全局安全删除三次 clone：

- 当前源码注释记录了 lazy expression 跨 extension 边界的历史 transient-metadata 问题，本探针没有覆盖其它 head_dim/dtype、causal、不同 Q/K/V 序列长度或 allocator 压力组合。
- torch compatibility 安装后，`Var.contiguous = lambda self: self`；实测 `contiguous_is_identity=true`。所以 `.contiguous()` 不是物化替代，只是语义不清晰的 no-clone 写法。
- clone/no-clone 稳态延迟几乎相同，lazy packed 场景无 clone 还更慢，没有足够性能收益去承担扩大正确性回归面的风险。
- 显著且重复的收益来自上游直接提供 BSHD contiguous：中位数约 `0.038-0.039 ms`，比转换路径约低 `47%`。这需要让 QKV projection/attention 模块直接生成 native backend 布局，或提供专门的 packed QKV 入口，而不是在通用 `F.sdpa` 内机械删除 clone。

结论：**目前不建议直接删 clone，也不建议替换为 `.contiguous()`。** 可先给 readonly bridge 增加覆盖多 dtype/head_dim/causal/lifetime/allocator-pressure 的回归，再考虑 guarded no-clone；近期更安全、更有收益的方向是上游 BSHD/packed 直传。

## 4. 梯度管理性能

### clip_grad_norm_（本 agent GPU3 快照）

总元素 `262144`，下表采用较长 repeats 的稳定结果。

| 张量数 | 情况 | old (ms) | new (ms) | new 变化 |
|---:|---|---:|---:|---:|
| 128 | 发生裁剪，max_norm=1 | 3.2658 | 2.5104 | -23.1% |
| 512 | 发生裁剪，max_norm=1 | 12.3983 | 9.6316 | -22.3% |
| 128 | 不裁剪，max_norm=1e9 | 2.1880 | 2.6151 | +19.5% |
| 512 | 不裁剪，max_norm=1e9 | 8.5418 | 9.1640 | +7.3% |

大 tensor 组（128 张量、总元素 `16,777,216`、发生裁剪）从 `3.3765` 降至 `2.9879 ms`，快 `11.5%`。收益主要来自移除 `total.item()` 后的 Python/D2H 系数分支；无裁剪回归来自无条件 `g.update(g * coef)`。

优先方案是将 device 上的 clip coefficient 交给 optimizer，在参数更新 kernel 中乘入；其次是原生 foreach/multi-tensor scale。继续组合 Python 级 reduction/concat 的收益有限。

### GradScaler

本 agent 测试的早期快照：

| 张量数 | old (ms) | 当时 new (ms) | new 变化 |
|---:|---:|---:|---:|
| 128 | 4.0398 | 4.1401 | +2.5% |
| 512 | 13.3947 | 18.9259 | +41.3% |

它虽然把 N 次 `.item()` 降为 1 次，但仍创建 N 组 unscale/finite 子图，kernel launch 与图构建成本超过了同步收益。共享树之后改为 `concat(unscaled grads) -> isfinite -> all -> item`；共享后测（非本 agent GPU3 原始快照）在 512 张量上得到：

- 总元素 `262144`：old `12.801 ms`，当前 flat new `9.087 ms`，快 `29.0%`。
- 总元素 `16,777,216`：old `14.161 ms`，当前 flat new `8.052 ms`，快 `43.1%`。

因此旧回归已经被后续 flat 改动显著扭转，但最终形态仍应对齐 PyTorch `_amp_foreach_non_finite_check_and_unscale_`：一个 multi-tensor CUDA op 同时完成写回与 overflow flag reduction，避免大 flat concat 的额外存储和 graph 节点。

## 5. 同步点审计

`torch_compat.py::_backward()` 在每次 `.backward()` 开头执行：

```python
try:
    self.sync()
except Exception:
    pass
```

底层 `VarHolder::sync(bool device_sync=false, bool weak_sync=true)` 调用 `jittor::sync({this}, false, true)`。所以：

- 它不是 `cudaDeviceSynchronize`，不必按完整 GPU host barrier 估算。
- 它仍会令 loss 的 forward 图在 `jt.grad` 前落地，形成 executor/fusion 边界。
- 当前注释说明该同步用于 3DGS rasterizer/fused-ssim 等 out-of-band 写输出的 extension；去掉后会在 grad 构图重跑 factory op，导致垃圾值/NaN。因此不能全局删除。
- 现有 `benchmark_training_hotspots.py` 使用 `torch.autograd.grad`，不会进入 `_backward()`，所以已有热点数据没有覆盖这个边界；报告中不伪造一个未测量的加速比例。

建议实现一个明确的 extension capability/Var 标记（例如“forward 必须先 materialize”），仅当 loss 依赖此类 op 时同步；纯 Jittor/Transformers 图直接进入 `jt.grad`。需要用至少两组回归共同验收：纯 Transformer 训练步性能，以及 3DGS/fused-ssim 有限性与梯度正确性。

## 6. 正确性审计

- `test_torch_compat_grad_management.py`：CPU + GPU3 共 5 项通过，覆盖 clip 数值/非有限值、无 `.item()` 常规路径，以及 GradScaler 有限/溢出跳步。
- fp16 探针：scale=2 时 `[8,-4],[2] -> [4,-2],[1]`；Inf/NaN 会设置 `_found_inf=True` 并跳过 optimizer step。
- API 差异：Jittor fp16 `clip_grad_norm_` 返回的 total norm 为 float32，PyTorch 返回 fp16；更新值正确，但 dtype parity 尚未完全一致。
- attention targeted：SDPA `dropout_p=1`、native bool mask、MHA train/eval dropout 在 CPU/GPU3 通过。
- 审计发现 fully-masked row 残留：bool 全 False 时旧 torch_compat 返回 V 均值，native 产生 NaN。共享树已增加 row-valid 前后 softmax 防护；父任务回报 fully-masked forward + 随机上游 backward 的 CPU/CUDA targeted 测试通过。
- 全 attention suite 当时为 8 pass、1 fail、2 skip。唯一失败 `test_flash_attn_packed_split_cuda` 会先清除 `JITTOR_FLASH_ATTN_FUSED_PACKED_SPLIT`，随后又要求 gated helper 返回非 None，属于测试自身 gate 前提冲突，不是本轮 SDPA/dropout 改动回归。

## 7. 优化优先级

1. **P0：避免整个 BHLD→BSHD layout materialization。** 让 QKV projection/attention 模块直接产出 backend 所需 BSHD contiguous 或 packed layout。不要把 `.clone()` 机械换成 `.contiguous()`；单删 clone 的配对收益只有约 3.6%，且 lazy packed 场景可能回归。
2. **P0：补齐 native flash backward + dropout。** 否则 Transformers 训练永远回落 math；同时保留 math mask/GQA fallback。
3. **P1：做原生 multi-tensor GradScaler 与 clip scale。** 将 overflow reduction、unscale、clip coefficient 融入少量 CUDA kernel/optimizer step，避免按参数张量扩大的 Python 图和 kernel launch。
4. **P1：条件化 `.backward()` 前的 `self.sync()`。** 用 extension capability 标记保护 3DGS 等正确性，同时释放纯 Transformer 图的联合调度空间。
5. **P2：给 benchmark 增加两种明确模式。** `queued-throughput` 与 `per-call-sync-latency` 分开报告，并记录 native hit/miss、layout copy bytes、桥接统计，避免 repeats 对 lazy graph 摊销造成误判。
