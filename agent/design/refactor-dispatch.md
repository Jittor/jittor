# 怎么派活给接手的模型

2026-09-02。配套 [交接说明](refactor-handoff.md)。

上一轮是被额度打断的，不是做完的。这份说明只解决两件事：**让下一轮在任何时刻被打断都不亏**，
以及**让你用尽量少的话把状态交代清楚**——状态都在文档里，你不需要复述。

下文 `$LAB` 指 `$JITTOR_LAB_ROOT/refactor`。

## 0. 一句话的 goal

要它自己一直推到底，用这句：

```
在 2.0-refactor 分支上干活（工作目录 $LAB/coord，不要在主树里改代码），按
agent/design/refactor-handoff.md 与 agent/design/refactor-dispatch.md 的次序推进
agent/design/refactor-plan.md：先补验证合入五个 wip/* 分支并收尾六处未提交残留，
之后每波最多四个分区、每分区最多 5 条任务，一个任务一个提交、做完就推，每波结束前把
看板与交接文档更新到反映真实状态，直到 refactor-board.md 上不再有「待领」与「进行中」。
```

**终点写成「看板上不再有待领与进行中」而不是「完成所有任务」**，因为前者 `grep -c 待领` 一条命令
就有答案，后者只能反复问「做完了吗」。分支与工作目录必须写进去，理由见交接说明第 0 节。

## 1. 第一次会话：只收尾，不领新活

```
读 agent/design/refactor-handoff.md 和 $LAB/AGENT-BRIEF.md。

这次只做交接文档第 2、3 节，不要领新任务：
1. 五个 wip/* 分支逐个补验证（改了 C++ 的各跑一次 CPU 与 CUDA），过了就 rebase 合进
   2.0-refactor 并删分支；没过的留着，把原因写进交接文档。
2. 六个 worktree 的未提交残留逐个收尾或丢弃。cudabk 和 dist 有文件已经在索引里，
   提交前先看 git diff --cached --stat。
3. 看板 16 行「进行中」按实际改对：有提交的填提交号，只有残留的退回「待领」并注明
   残留在哪个 worktree。

每收完一件就提交并推送，不要攒。做完更新交接文档。
```

**为什么先收尾**：那十一处残留只存在于磁盘上，机器一动就没了；待领的 120 条任务躺在计划里，
丢不了。先救会消失的。

## 2. 之后每一波：给量，不给「剩下的」

```
读 agent/design/refactor-handoff.md、refactor-plan.md、refactor-board.md 和 $LAB/AGENT-BRIEF.md。

这一波开 N 个 subagent，分区用 dist / device / mem / build，每个分区从看板「待领」里挑不超过
5 条，优先挑前置依赖已经落地的。

- 一个任务一个提交，做完就推。
- 每个 agent 只用派给它的那张卡与那段核，缓存目录各用各的。
- 收工前把看板改对。
```

`dist / device / mem / build` 是上一轮没重启的四个分区，它们名下的待领任务前置依赖最少，
是最省事的起点。**开到四个就够**：这轮开九个，额度撑不到一波结束，中断时残留满地。

额度紧就直说，它能自己排：

```
这次会话的额度大概只够 <你的估计>。按这个排，排不下的写进交接文档留给下一轮，
不要开一半停在那。
```

## 3. 随时可以发的一句：干净地停

```
先停下来收尾：能推的都推了，看板改对，交接文档更新到反映现在的状态，然后告诉我停在哪。
```

这句不需要上下文，额度告急时直接发。上一轮如果每次中断前都发过这句，就不会有十一处残留
需要靠翻 `git status` 复原。

## 4. 验收问什么

**不要问「做完了吗」**——答案永远是做完了。问有确切答案、能对照的：

- 看板上现在几行已合并、几行进行中？进行中的分别在谁手里？
- 几处未提交残留？在哪几个 worktree？
- 这一波的提交号列出来，哪几个跑过 CUDA？

再抽查一条修「静默算错」的任务：

```
<编号> 你说合并了。把那个提交里新增的测试名字告诉我，以及它在修复前是怎么失败的。
```

答不出「修前怎么失败」，说明那条没有真测试——计划第 0 节要求的是修前失败、修后通过。

## 5. 会让它跑偏的话

| 别说 | 为什么 | 改成 |
| --- | --- | --- |
| 「把剩下的都做了」 | 120 条，它会开一大堆 subagent，一晚上烧光，中断时残留满地 | 给分区与条数 |
| 「顺便把 X 也改了」 | 一个提交只做一件事，是这轮 rebase 还能收敛的唯一原因 | 让它把 X 写成看板上的新任务 |
| 「这个测试红了，修一下」 | 分支起点本来就有已知失败（看板顶部有清单），它会去修一个本来就坏的东西 | 先问：这条在分支起点是否也红 |
| 「用 git stash 存一下」 | stash 栈是所有 worktree 共用的，这轮两个 agent 的 WIP 整包对调过 | `git diff > x.patch` + `git checkout --` |
| 「force push 一下」 | 分支上有九个来源的提交，覆盖掉就找不回来了 | rebase 再推 |

## 6. 出了错怎么让它自查

```
<描述现象>。先不要改代码：告诉我这个现象在 <某个已知好的提交> 上是否也出现。
不出现的话，用 git bisect 定位到具体提交再说。
```

这轮所有「大面积失败」最后都不是大面积——一次是损坏的 JIT 缓存，一次是磁盘满，一次是
Python 字符串里内嵌的 C++ 没跟着改。先分清是回归还是环境，再动代码。

## 7. 每一波结束时看一眼

有没有三个以上 agent 各自重新查明了同一件事？有就说明漏了一个 skill。
计划第 0 节要求这类知识当场写进 `agent/skills/`，与产生它的任务同一个提交——攒到最后就写不出来了。
