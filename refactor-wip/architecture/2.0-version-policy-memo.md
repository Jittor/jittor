# 备忘：2.0 的版本策略（9.10）

**状态：只陈述，不选择。** 这份备忘是给维护者在发布节点做决定用的，不替维护者选。
写它的原因是：`__version__` 决定 wheel 名、PyPI 上的版本、以及用户
`pip install jittor==?` 要写什么——这是**发布决定**，不是重构决定，不该由一个整改分支
顺手改掉。

---

## 一、查到的事实

| 事实 | 位置 | 说明 |
| --- | --- | --- |
| `__version__ = '1.3.11.0'`，而分支叫 `2.0` | `python/jittor/__init__.py:12` | 名实不符本身只是名实不符 |
| 包版本由它派生，没有第二处真源 | `pyproject.toml:7` `dynamic = ["version"]`；`:59` `version = { attr = "jittor.__version__" }` | 改一处即可改到 wheel 名与 PyPI 版本 |
| 缓存路径取 `rsplit('.', 1)[0]` = `jt1.3.11` | `jittor_utils/__init__.py` `version_dir_name()` | **不按 patch 版本分区** |
| 缓存不按 patch 分区**不是 bug** | `cache_compile` 逐文件 SHA-256 | 同一 minor 的两个 patch 若源码不同，内容哈希会重编改动的部分；目录不分区只意味着它们共用一棵树，这正是想要的增量行为。所以这条**没有技术上的紧迫性** |
| 发布流程断言 tag 等于 wheel 版本 | `.github/workflows/release.yml:60`、`:154`（`GITHUB_REF_NAME[1:]`） | 版本号一改，发布 tag 的写法跟着改 |
| 有一条硬编码断言 | `tests/compat/torch/test_torch_shim_aliases.py:277` `assert jittor.__version__ == '1.3.11.0'` | 属 shim 分区；改版本号必须同一批改它 |
| 仓库里**已经**区分「我是哪个包」与「我说哪套 API」 | 同文件 `:278-279`：`jittor.__torch_version__ == '2.11.0'`、`jittor.version.__version__ == '2.11.0'`；来源 `compat/torch/installers/cuda.py:938` `torch_api_version = "2.11.0"` | 这个形状已经在 torch 方向上实现了，只是没有在 jittor 自己的方向上实现 |
| 改版本号会再触发一次全量重编 | 版本是缓存路径的第一级分量 | 2026-09-03 的 9.04 刚让所有人重编过一次 |

**不在本备忘范围内的一条**：`jittor[cuda12]` 钉死 `nvidia-cudnn-cu12==8.9.7.29`，与任何
现代 torch 的依赖直接冲突（审计「17 个失败点」第 12 条）。**它的技术前置是 8.04**
（把 RNN 迁到 cuDNN v8 RNN API 之后，放开 `compile_extern.py` 对 major ≥ 9 的拒绝），
**不是版本策略**——那个矛盾不依赖版本号叫什么。已转给 CUDA 后端分区。

## 二、三个候选

### 候选 A：改成 `2.0.0`

名实相符，用户 `pip install jittor` 拿到的版本号与分支、与文档里的「Jittor 2.0」一致。

需要同时改：

- `python/jittor/__init__.py:12`
- `tests/compat/torch/test_torch_shim_aliases.py:277` 的硬编码断言（shim 分区）
- 发布 tag 的写法：`release.yml` 断言 `GITHUB_REF_NAME[1:] == metadata["Version"]`，
  所以 tag 要写 `v2.0.0`
- wheel 内容基线 `agent/baselines/wheel-contents-final.txt` 里 6 条
  `jittor-1.3.11.0.dist-info/*` 路径会全部改名（发版前本来就要重刷一次基线）
- `tests/compiler/test_clean_cache.py` 的 fixture 里 `jt1.3.11` 这个目录名（只是 fixture，
  不是断言真实版本，改不改都行）

代价：**所有人再全量重编一次**（缓存路径第一级分量变化）。语义代价：从 1.3.11.0 跳到
2.0.0 是一次 major 提升，对下游是「可能有破坏性变更」的信号——如果 2.0 确实是（整改
分支改了 shim 语义、缓存布局、构建行为），这个信号是**对的**；如果维护者认为 2.0 对
用户 API 是兼容的，这个信号会造成不必要的升级犹豫。

### 候选 B：保持 `1.3.11.0`，到发布节点再定

现状。零改动、零重编、不动发布流水线、不弄红别的分区。

代价：分支名与版本号在整个整改期内持续不一致；任何按 `jittor.__version__` 判断「这是
不是 2.0」的下游代码会拿到错误答案（目前仓库里没有这样的代码）；README 与文档里说
「Jittor 2.0」而 `pip show jittor` 说 1.3.11.0，对新用户是一处小混淆。

这个候选的实质是：**把决定推迟到信息最全的时刻**（发布前，破坏性变更的清单已经定下来
的时候），而不是在整改中途。

### 候选 C：引入两个版本号——包版本与 API 版本

`__version__` 继续跟随发布节奏（现在 1.3.11.0，发布时由维护者定），另外引入一个显式的
API/世代标识（例如 `__api_version__` 或 `jittor.version.generation = "2.0"`），由整改分支
维护，表示「这套代码属于 2.0 世代」。

需要同时改：新增常量与它的唯一真源、一条结构用例钉住它、README 说明两者的区别。
**不需要**动 wheel 名、PyPI、发布 tag、缓存路径，**不触发重编**。

先例就在仓库里：shim 已经这么做了——`jittor.__version__` 是「我是哪个包」，
`jittor.__torch_version__` / `jittor.version.__version__` 是「我声称说哪套 torch API」，
两者独立且都有用例钉住。候选 C 只是把同一个形状用在 jittor 自己身上。

代价：多一个概念，需要文档说明「什么时候看哪个」；如果最终发布时 `__version__` 也变成
2.x，这个额外常量可能显得冗余。

---

## 三、三个候选的共同前提

无论选哪个，下面两条都成立，**与选择无关**：

1. 缓存键不按 patch 版本分区**不需要改**（内容哈希兜着）。
2. 第 12 条（cuDNN 9）由 **8.04** 解决，不由版本策略解决。

## 四、决定之后要做什么

选 A：按上面「需要同时改」的清单一次改完，**推之前广播**（会全量重编）。
选 B：无需改动;本备忘保留，发布前重新读一遍。
选 C：加常量与用例，不需要广播。
