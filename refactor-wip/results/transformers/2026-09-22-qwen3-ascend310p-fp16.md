# Qwen3-0.6B FP16 在 Ascend 310P3 上的推理验收

- Status: Accepted for Qwen3-0.6B float16 greedy inference on one Ascend 310P3
- Last reviewed: 2026-09-22
- Source baseline: `1a3e184e`（310P 算子层适配）加上本报告的 compat 修复
- Owner: Torch compatibility and ACL backend maintainers
- Review when: Torch shim 的 meta device 语义、`Module.get_parameter`/`get_buffer`
  成员判定、RoPE FP32 频率计算、或 `acl_allow_hf32` 行为变化

## 结论

310P 适配此前只完成算子层验收（`tests/backends/acl/` 214/11/0）。本次在
同一张 310P3 上用 Transformers 4.56.2 经 Torch shim 跑通了第一个模型级
端到端用例：**Qwen3-0.6B，FP16 加载，8-token greedy 生成，三次重复输出
完全一致，`backend_fallback=error` 下 `fallback_count=0`**。

`QWEN_RESULT` 摘要：

- `dtype: torch.float16`，`parameters: 596049920`（tied lm_head）
- 生成文本 `2 + 2 = 4.`，token ids `[17, 488, 220, 17, 284, 220, 19, 13]` ×3
- 加载 6.88 s；generate 首次 17.58 s（含算子 JIT），热态中位 0.667 s
  （≈12.0 tok/s）；加载后 NPU 显存 1856 MB / 44213 MB
- `has_acl=1`，`use_acl=1`，`use_cuda=1`，`fallback_count=0`

数值对拍：独立 venv 中真实 PyTorch 2.14.0+cpu / Transformers 4.56.2 以
FP32 跑同一 prompt 的 greedy 生成，token ids `[17, 488, 220, 17, 284,
220, 19, 13]` 与 310P FP16（含 RoPE hf32 降精度）**逐 token 完全一致**。

## 复现

```bash
source /usr/local/Ascend/cann-9.1.0/set_env.sh
ASCEND_RT_VISIBLE_DEVICES=0 JITTOR_TORCH_SHIM=1 \
backend_fallback=error acl_allow_hf32=1 \
PYTHONPATH=python python tests/backends/acl/manual/run_qwen3_transformers.py \
    --model <local-snapshot> --dtype float16 --max-new-tokens 8 --runs 3
```

`acl_allow_hf32=1` 是必需的：HF 的 Qwen3 RoPE 用 FP32 计算
`inv_freq @ position_ids` 再转回 FP16，310P cube 不支持 FP32 `KEEP_DTYPE`，
按设计走显式降精度（内部 FP16 拆分，~1e-3）。decode 输出正确性不受影响。

## 本次发现并修复的 compat 缺口

三个缺口都是经最小复现确认后修复的：

1. `torch.empty(..., device="meta")` 工厂参数不支持：Transformers 4.56.2 用
   meta state dict 枚举 checkpoint key。按既定"真实分配 + 可观测 meta 标记"
   语义补 `_is_meta_device_request` + `_invoke_factory` 标记 +
   `Tensor.device`/`is_meta` 报告（`compat/torch/types.py`、
   `installers/factories.py`、`installers/tensor/method_api.py`）。
2. `Module.get_parameter`/`get_buffer` 用全局去重的 `named_parameters()` 判
   成员，把 tied `lm_head.weight` 误报为 AttributeError。改为查叶子模块的
   局部 `_parameters`/`_buffers` 表，与 torch 语义一致
   （`installers/nn/module_methods.py`）。
3. probe 自身：`generate()` 输入未搬到 NPU（Transformers 只警告不迁移），
   以及 shim 激活检查误用 `torch is jt` 身份判断，改为检查 shim 标记。
   probe 同时新增 `float16` dtype 选项
   （`tests/backends/acl/manual/run_qwen3_transformers.py`）。

另：`MANIFEST.in` 补登 `docs/guides/ascend-310p.md`（上一提交遗漏）。

## 速度对拍（同 checkpoint、同 prompt、greedy）

三方对比：真实 PyTorch 2.14.0+cpu FP32（i9-13900H 20 核）、
官方 torch_npu 2.12.0 FP16、本树 Jittor shim FP16，后两者跑同一张
310P3。

| 上下文 | 阶段 | torch CPU FP32 | jittor→310P FP16 | torch_npu→310P FP16 |
| --- | --- | --- | --- | --- |
| 502 tok | prefill | 1.81 s（277 tok/s） | 0.165 s（3050 tok/s） | **0.088 s（5736 tok/s）** |
| 502 tok | decode | 11.16 tok/s | 11.68 tok/s | **32.64 tok/s** |
| 502 tok | 生成 32 tok 全程 | 4.59 s | 2.82 s | **1.04 s** |
| 1998 tok | prefill | 10.2 s（196 tok/s） | 1.03 s（1944 tok/s） | **0.70 s（2837 tok/s）** |
| 1998 tok | decode | 7.06 tok/s | 8.75 tok/s | **23.28 tok/s** |
| 1998 tok | 生成 32 tok 全程 | 14.6 s | 4.57 s | **2.04 s** |

正确性：1998-token 上下文的 31 个生成 token **三方逐位一致**；
502-token 场景 torch CPU FP32 有一个并列分支 token 差异
（FP32 vs FP16 的 greedy 分叉），两个 FP16 引擎彼此一致。
两侧 NPU 全程 `fallback_count=0`（jittor 侧 `backend_fallback=error`）。

性能解读：jittor shim 相对官方 torch_npu 的差距在 prefill ~1.5-1.9×、
decode ~2.7×——batch=1 decode 是每 token 算子提交延迟受限，shim 的
Python 侧派发与逐算子提交开销是主要差距来源（与 910B 报告中的提交
放大分析一致）；310P 无 FlashAttention 核，两家 attention 均为组合
实现。torch_npu 首个 decode run 含一次性算子编译（~460 s），
jittor 侧对应成本在 JIT 缓存预热（~17 s）。

## 范围与限制

- 只验收了 FP16 推理；BF16 在 310P 物理不可用，FP32 需全程 `acl_allow_hf32`。
- SDPA 走设备侧组合实现（310P 无 `FlashAttentionScore` 核），吞吐低于 910B
  属预期；本结果只做正确性/回退验收，未做性能对拍。
- 对拍仅覆盖单 prompt 8 token greedy；更长生成、batch 与 sampling 路径
  未做数值对拍。
- 训练未验收（310P 不声明训练能力）。
